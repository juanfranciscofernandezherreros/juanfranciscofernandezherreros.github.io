00

The 60-second mental model

Think of it like a restaurant kitchen that never stops checking its own recipe book.

No jargon yet — just the shape of the idea. Every technical term below maps to one of these three things.

The recipe book

What should exist

A written, versioned description of the dish — ingredients, quantities, steps. Anyone can read it and know exactly what's supposed to be cooking.

in real life: the Git repo
The head chef

Keeps checking

Walks past the recipe book every few minutes. If the kitchen doesn't match the book, fixes it — no exceptions, no "close enough."

in real life: ArgoCD
The kitchen

Where it actually cooks

Stoves, prep stations, plates. The physical place where the dish gets made and kept warm, ready to serve.

in real life: the Kubernetes cluster

That's the whole idea. You never walk into the kitchen and cook by hand — you edit the recipe book, and the chef makes sure the kitchen catches up. Section 03 gives this loop its real name and its real behavior.

01

Meet the pieces

Same ideas as above, now with their real names — in the order you'll actually run into them.

Where your code lives

Git
A tool that saves a history of every change to your files. Each saved change is a commit — you can always go back to an earlier one.
Repository (repo)
A folder of code tracked by Git, with its own history. This project uses two: hello-world-argocd and gitops-config.
GitHub
A website that hosts the "official" copy of a repo in the cloud. git push uploads your commits there; git pull downloads them.
Commit
A snapshot of your changes, with a message explaining what and why. It's the smallest unit of history in Git.

Packaging the app

Microservice
A small, self-contained app that does one thing — here, replying Hello World — and gets deployed on its own.
Docker
Packages an app together with everything it needs to run (Java, libraries) into one sealed box that behaves the same on any machine.
Docker image
The packaged, frozen "template" (hello-world:local here). Built once with docker build.
Container
A Docker image that's actually running. You can start several containers from the same image.

Running it in Kubernetes (the kitchen)

Kubernetes (k8s)
A system that keeps many containers alive: if one crashes, it restarts it; if you ask for 3 copies, it watches that there are always 3.
Cluster
The set of machines (nodes) Kubernetes runs on. Ours is called hello-world.
kind
A tool that simulates a full Kubernetes cluster inside Docker, on your own laptop — no cloud needed, great for learning and testing.
kubectl
The command you use to talk to Kubernetes: create, list, or delete things in the cluster (e.g. kubectl get pods).
Namespace
A logical "folder" inside the cluster that groups one project's resources. Hello-world lives in the hello-world namespace.
Pod
The smallest thing that runs in Kubernetes. It usually wraps a single container.
Deployment
The recipe that tells Kubernetes which image to use and how many copies (replicas) of the Pod to always keep alive.
Service
A fixed "front door" to reach the Pods, even as they restart and their internal addresses change underneath.
Manifest / YAML
The text file describing what you want to exist (a Deployment, a Service...). It's the order form Kubernetes fulfills.

Deploying itself (the head chef)

ArgoCD
An application that lives inside the cluster itself, watches a Git repo, and applies any change it sees there — on its own.
GitOps
The practice of treating Git as the single source of truth: you never touch the cluster by hand, you edit the repo and a tool (Argo) applies it.
Application (Argo's)
The manifest that tells Argo "watch this repo, this folder, and deploy it to this namespace" — see applications/hello-world.yaml.
Sync / selfHeal / prune
Argo's three reconciliation actions — explained in detail in section 03.

None of the three knows how to build the other two. They only ever talk through Git and the Kubernetes API.

03

The reconciliation loop

Git is the only source of truth. Nobody ever runs kubectl apply by hand — you edit the repo, and Argo corrects the difference on its own.

sync
The repo has something the cluster doesn't → Argo creates it.
prune
The cluster has something no longer in the repo → Argo deletes it.
selfHeal
Someone edits something by hand in the cluster (kubectl edit) → Argo reverts it back to match Git.
refresh
Every ~3 minutes, or on demand, Argo re-compares repo vs. cluster even if nothing changed.
04

Bringing it all up — from a restart, or from zero

Section 05 assumes the cluster and ArgoCD already exist. Here's how to actually get there, on a fresh machine or after Docker Desktop was closed.

"Starting" Argo and "configuring" Argo are two different things

Installing it (the commands below) just means applying a Kubernetes manifest — ArgoCD isn't a program you launch, it's a handful of Deployments and a StatefulSet that Kubernetes schedules like any other app. Once those pods are Running, Argo is "started" — and watching nothing yet.

Configuring what it watches is a separate step: creating an Application resource (applications/hello-world.yaml, applied in the "starting from zero" path below). That's the only "configuration" this guide ever touches — the two ConfigMaps that configure ArgoCD's own behavior (argocd-cm, argocd-rbac-cm) are left at their defaults, which is normal for a setup this size.

just resuming

The cluster still exists — Docker Desktop (or the machine) was just closed for a while.

1 You Start Docker Desktop and wait for its engine to actually be ready — docker ps should stop erroring.
2 kind The cluster's container has a restart policy, so it comes back on its own as soon as Docker's engine is up — no kind create cluster needed. Confirm with kubectl get nodes; if it points at the wrong cluster, kubectl config use-context kind-hello-world.
3 Kubernetes + Argo Pods that show Unknown right after the restart flip back to Running on their own within about a minute — that's kubelet reconnecting, not a real failure. No action needed, just wait and re-check kubectl get pods -n argocd.
4 You What does not come back on its own: the two kubectl port-forward processes from the "Live locally" panel. Re-run both: 
kubectl -n argocd port-forward svc/argocd-server 8081:443 &
kubectl -n hello-world port-forward svc/hello-world 8080:8080 &

If a port-forward errors with unable to listen on any of the requested ports, an old one from before the restart is still holding it — find and kill that process first, then retry.

starting from zero

No cluster exists yet — first time on this machine, or you ran kind delete cluster.

1 You Clone both repos — everything below assumes you're inside them: 
git clone https://github.com/juanfranciscofernandezherreros/hello-world-argocd.git
git clone https://github.com/juanfranciscofernandezherreros/gitops-config.git
2 You Start Docker Desktop, then create the cluster: 
kind create cluster --name hello-world
3 You Install ArgoCD into it: 
kubectl create namespace argocd
kubectl apply -n argocd --server-side --force-conflicts \
  -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
kubectl -n argocd rollout status deploy/argocd-server

--server-side matters: a plain apply fails here because the ApplicationSet CRD is bigger than the 262144-byte limit on the last-applied-configuration annotation a normal apply writes.

4 You The cluster and ArgoCD are ready, but the app itself still isn't running. That's the next section — 05, right below — run from inside your hello-world-argocd clone: build the jar, build the image, load it into kind, then from your gitops-config clone, register it with Argo — with the real output of every step.
5 You Once that's done, open the two doors: same two port-forward commands as the "just resuming" path above, then curl http://localhost:8080/hello to confirm.
05

Terminal walkthrough — every command, for real

Steps 0 and 0b are the one-time setup from section 04, already done here. Steps 1-6 are the repeatable loop — build, load, sync, verify — with the real terminal output of each. The screenshots in section 06 show this same result in the browser; the bare commands, quick to copy, are in section 09.

0 — one-time setup, already done

The cluster exists and is Ready

kind get clusters lists the cluster; kubectl get nodes confirms Kubernetes itself is up on it.

0b — Argo is installed

All 7 ArgoCD pods Running

ArgoCD is itself just a handful of pods living in the argocd namespace — the application-controller, repo-server, the UI server, and a few helpers.

1 — build the jar

mvn clean package

Compiles the Spring Boot app, runs its one test, and produces hello-world-0.0.1-SNAPSHOT.jar in target/.

2 — build the image

docker build -t hello-world:local app

Wraps that jar and a JRE into the hello-world:local image, using the app/Dockerfile. Layers get cached, so re-runs after a code change are fast.

3 — get the image into the cluster

kind load docker-image

There's no registry in this base, so the image is injected straight into the kind node. The ID changes every time you rebuild, which is why it says "not yet present" here.

4 — register (or re-register) with Argo

kubectl apply -f applications/hello-world.yaml

Says unchanged here because the Application already existed from an earlier run — that's expected and fine. On a first run it would say created.

5 — sync on demand

argocd app sync hello-world

Forces the comparison instead of waiting for the automatic ~3-minute refresh. The table at the bottom is Argo's resource-by-resource report: Namespace, Service, Deployment — all Synced.

6 — final proof

kubectl get pods + curl

The Pod is Running, and the endpoint answers. This is the same result as the screenshot in section 06, step 1 — just seen from the terminal instead of the browser.

07

Sequence — changing the deployment

100% automatic

Example: scaling from 1 to 3 replicas by editing gitops-config/manifests/hello-world/deployment.yaml.

1 You Edit the YAML and git push to gitops-config.
2 ArgoCD Runs git fetch on the repo and compares HEAD against the cluster's real state.repeats every ~3 min, or on a forced refresh
3 Kubernetes API Argo applies the difference: creates, updates, or deletes resources as needed.
4 hello-world Pod The missing pods get created. The readinessProbe confirms they're ready.
5 ArgoCD Marks the Application as Synced · Healthy. Done — nobody touched kubectl.
08

Sequence — changing the code

manual in this base

There's no CI or registry yet, so building and publishing the new image is on you.

1 You mvn package in hello-world-argocd/app.
2 You docker build -t hello-world:local app.
3 You kind load docker-image hello-world:local --name hello-world — the image doesn't come from any registry, it's injected straight into the cluster's nodes.
4 You kubectl rollout restart deploy/hello-world -n hello-world — Argo doesn't notice this change on its own because the image tag never changed.
5 hello-world Pod Gets recreated with the new image and goes back to Ready.
