Checked vs Unchecked Exceptions

The difference is easy to memorize. The useful skill is deciding what an exception means for the caller, where it belongs in your architecture, and whether forcing compile-time handling improves the API or only adds noise.

00

The interview answer

A checked exception must be caught or declared with throws; an unchecked exception does not have that compile-time requirement. Checked exceptions are subclasses of Exception excluding RuntimeException. RuntimeException, Error, and their subclasses are unchecked.

That answer is correct, but senior-level discussion starts with the next question: why would you choose one over the other?

01

The hierarchy

Throwable
├── Error                         // unchecked
│   └── OutOfMemoryError
└── Exception
    ├── IOException               // checked
    │   └── FileNotFoundException
    ├── SQLException              // checked
    └── RuntimeException          // unchecked
        ├── NullPointerException
        ├── IllegalArgumentException
        └── IllegalStateException

The key is inheritance, not whether you happen to write a throws clause. Declaring a RuntimeException with throws does not turn it into a checked exception.

02

Checked exceptions

Java's compiler enforces the catch or specify rule for checked exceptions. If a method can produce one, the caller must handle it or propagate it.

public String readConfig(Path path) throws IOException {
    return Files.readString(path);
}

try {
    String config = readConfig(Path.of("app.conf"));
} catch (IOException ex) {
    // recover, translate, retry, or report the failure
}

A checked exception makes a failure visible in the method contract. This can be valuable when the caller can reasonably react to the condition.

Good fit

A recoverable condition that callers should consciously consider: a file cannot be read, a required external resource is unavailable, or an operation has an alternative path.

Cost

Every intermediate layer must catch or declare it, which can create noisy signatures when those layers cannot meaningfully recover.

03

Unchecked exceptions

Unchecked exceptions are not enforced by the compiler. A method can throw a RuntimeException without declaring it.

public Order findOrder(UUID id) {
    return repository.findById(id)
        .orElseThrow(() -> new OrderNotFoundException(id));
}

public final class OrderNotFoundException extends RuntimeException {
    public OrderNotFoundException(UUID id) {
        super("Order " + id + " was not found");
    }
}

This does not mean unchecked exceptions should be invisible or undocumented. It means Java does not force every caller to add handling code.

Typical use: programming errors, violated preconditions, invalid state, and application/domain failures for which most intermediate callers have no useful recovery strategy.

05

Catch, propagate or translate?

The important decision is often not checked versus unchecked, but which layer has enough context to act.

public Invoice loadInvoice(UUID id) {
    try {
        return externalClient.fetch(id);
    } catch (IOException ex) {
        throw new InvoiceProviderException(
            "Could not load invoice " + id,
            ex
        );
    }
}

Here the application translates an infrastructure-specific failure into an exception meaningful to its own abstraction while preserving the original cause.

Do not catch an exception only to log it and throw it again everywhere. Catch when you can recover, add useful context, translate abstractions, or perform required cleanup.

06

Custom exceptions

Extending Exception creates a checked exception:

public class PaymentRejectedException extends Exception {
    public PaymentRejectedException(String message) {
        super(message);
    }
}

Extending RuntimeException creates an unchecked exception:

public class InvalidOrderStateException extends RuntimeException {
    public InvalidOrderStateException(String message) {
        super(message);
    }
}

Choose based on the contract you want to expose, not because one version requires fewer lines of code.

07

What about Spring?

Modern Spring applications commonly use unchecked application/domain exceptions and translate them at boundaries, for example with @RestControllerAdvice. This keeps controllers and services from carrying checked exceptions through every method signature when those layers cannot recover.

@ExceptionHandler(OrderNotFoundException.class)
ProblemDetail handleNotFound(OrderNotFoundException ex) {
    return ProblemDetail.forStatusAndDetail(
        HttpStatus.NOT_FOUND,
        ex.getMessage()
    );
}

Also remember Spring transaction semantics: by default, runtime exceptions and errors trigger rollback, while checked exceptions do not unless rollback rules are configured. That framework behavior is a separate concern from Java's checked/unchecked classification, but it matters when designing service-layer exceptions.

08

Common mistakes

Catch Exception

Broad catches hide the failure model and can accidentally swallow problems you cannot handle.

Empty catch

Ignoring a failure makes debugging harder and can leave the application in an invalid state.

throws Exception

It destroys useful information in the contract. Prefer the narrowest meaningful type.

RuntimeException everywhere

Unchecked is not a shortcut for avoiding design. Exceptions should still express meaningful failure semantics.

// Bad
try {
    process();
} catch (Exception ex) {
    // ignored
}
09

A decision rule that scales

Ask whether the caller can reasonably be expected to recover from the condition. If recovery is part of the caller's normal responsibility, a checked exception can make that contract explicit. If the failure represents a programming error, broken invariant, invalid state, or something intermediate callers cannot meaningfully fix, an unchecked exception is usually more appropriate.

Then add architecture to the decision: do not leak SQLException, HTTP-client exceptions, or vendor-specific failures across your domain just because they happen to be thrown by infrastructure.

10

Interview questions

Can you catch an unchecked exception?

Yes. "Unchecked" only means the compiler does not require you to catch or declare it.

Can an unchecked exception appear in a throws clause?

Yes, but it is not required and does not change its classification.

Are all subclasses of Exception checked?

No. RuntimeException and all of its subclasses are unchecked.

Is Error a checked exception?

No. Error and its subclasses are unchecked and generally represent serious JVM or environment conditions that normal application code should not routinely catch.

Should every recoverable business error be checked?

No universal rule fits every architecture. The important question is whether forcing every caller to acknowledge the condition improves the API. In many Spring applications, domain failures are unchecked and handled at an application boundary.

Takeaway: checked versus unchecked is a compile-time distinction, but choosing between them is an API and architecture decision. Design exceptions around who can recover, preserve abstraction boundaries, and never use RuntimeException merely to silence the compiler.
