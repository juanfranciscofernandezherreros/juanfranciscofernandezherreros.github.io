Manejo de errores en Spring Boot

Una API no está bien diseñada solo porque el camino feliz devuelve 200 OK. La calidad aparece cuando algo falla: qué código HTTP devolvemos, qué información ve el cliente, qué registramos en logs y cómo evitamos que cada controlador invente su propio formato.

00

El problema real no es lanzar excepciones

El problema es convertir fallos de distintas capas en un contrato HTTP estable. Una excepción Java es un mecanismo interno. Un error REST es parte de la API pública. Confundir ambos conceptos suele producir endpoints que devuelven 500 para todo, mensajes inconsistentes o detalles internos que nunca deberían salir a Internet.

En este artículo construiremos una estrategia completa a partir de un pequeño dominio de pedidos. Veremos errores de negocio, recursos inexistentes, conflictos, validación de entrada y fallos inesperados. La meta es que el controlador permanezca limpio y que todos los errores sigan el mismo contrato.

01

Tres capas de error que no conviene mezclar

Dominio

Expresa qué salió mal para el negocio: pedido inexistente, transición inválida, stock insuficiente o versión obsoleta.

Aplicación

Decide qué operación estaba intentando ejecutar el caso de uso y propaga un fallo significativo, no detalles de infraestructura.

HTTP

Traduce ese fallo a status, headers y representación del error para el consumidor de la API.

Infraestructura

Puede producir SQLExceptions, timeouts, errores de red o disponibilidad. Normalmente no queremos exponerlos literalmente.

@Service
public class OrderService {

    public Order findById(UUID id) {
        return repository.findById(id)
            .orElseThrow(() -> new OrderNotFoundException(id));
    }
}

OrderNotFoundException puede existir sin conocer HTTP. Eso mantiene el servicio reutilizable y evita contaminar la lógica de negocio con HttpStatus, ResponseEntity o detalles de Spring MVC.

Modelo mental: el servicio describe el fallo; la capa web decide cómo representarlo fuera del proceso.

02

Elegir el código HTTP antes de escribir el handler

El código HTTP no debería depender del nombre de la excepción, sino del significado observable del fallo para el cliente.

StatusCuándo encajaEjemplo
400 Bad RequestLa petición no puede interpretarse o incumple reglas de entrada.JSON mal formado, parámetro con formato inválido.
401 UnauthorizedFalta autenticación válida.Token ausente o inválido.
403 ForbiddenEl usuario está autenticado pero no tiene permiso.Un usuario normal intenta ejecutar una operación administrativa.
404 Not FoundEl recurso solicitado no existe o no debe revelarse.GET /orders/{id} con un id desconocido.
409 ConflictLa petición es válida, pero entra en conflicto con el estado actual.Confirmar un pedido ya cancelado, email duplicado, optimistic locking.
422 Unprocessable ContentLa sintaxis es válida pero el contenido no puede procesarse semánticamente.Regla de negocio sobre un comando válido cuando se desea diferenciarla de 400.
500 Internal Server ErrorFallo inesperado del servidor.Bug o excepción no clasificada.
503 Service UnavailableDependencia o servicio temporalmente no disponible.Servicio downstream crítico indisponible y fallo explícitamente traducido.

No conviertas automáticamente toda excepción de negocio en 400. Un recurso ausente es 404; una transición incompatible con el estado actual suele expresarse mejor como 409. El status forma parte de la semántica de tu API.

03

@ExceptionHandler: manejar una excepción

@ExceptionHandler declara un método capaz de manejar determinadas excepciones lanzadas durante el procesamiento de una petición. Puede vivir dentro de un controlador concreto o en un advice global.

@RestController
@RequestMapping("/api/orders")
public class OrderController {

    @ExceptionHandler(OrderNotFoundException.class)
    ResponseEntity<ProblemDetail> handleNotFound(OrderNotFoundException ex) {
        ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.NOT_FOUND);
        problem.setTitle("Order not found");
        problem.setDetail(ex.getMessage());
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(problem);
    }
}

Funciona, pero tiene una limitación evidente: si cinco controladores pueden producir OrderNotFoundException, acabaríamos duplicando la misma traducción HTTP cinco veces.

Usa un handler local cuando la excepción realmente pertenece a la semántica de un controlador concreto. Para políticas comunes de API, normalmente queremos un advice global.

04

@RestControllerAdvice: una política global

@RestControllerAdvice combina el alcance global de @ControllerAdvice con respuesta en body. Spring detecta el bean y puede aplicar sus @ExceptionHandler a los controladores de la aplicación.

@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail handleOrderNotFound(OrderNotFoundException ex) {
        ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.NOT_FOUND);
        problem.setTitle("Order not found");
        problem.setDetail(ex.getMessage());
        return problem;
    }

    @ExceptionHandler(OrderStateConflictException.class)
    ProblemDetail handleConflict(OrderStateConflictException ex) {
        ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.CONFLICT);
        problem.setTitle("Order state conflict");
        problem.setDetail(ex.getMessage());
        return problem;
    }
}

Así el controlador vuelve a describir el camino feliz:

@GetMapping("/{id}")
public OrderResponse find(@PathVariable UUID id) {
    return mapper.toResponse(service.findById(id));
}

No hay try/catch, no se construye manualmente un error en cada endpoint y la misma excepción produce la misma respuesta en toda la API.

05

ProblemDetail y RFC 9457

Spring Framework incluye ProblemDetail para representar el formato estándar Problem Details for HTTP APIs definido por RFC 9457. En lugar de inventar un DTO distinto en cada proyecto, disponemos de campos con semántica conocida.

CampoSignificado
typeURI que identifica el tipo de problema. Puede apuntar a documentación.
titleNombre corto y estable del problema.
statusCódigo HTTP.
detailExplicación específica de esta ocurrencia.
instanceURI que identifica la petición o la ocurrencia concreta.
 
ProblemDetail problem = ProblemDetail.forStatusAndDetail(
    HttpStatus.NOT_FOUND,
    "Order 7c... does not exist"
);
problem.setTitle("Order not found");
problem.setType(URI.create("https://example.com/problems/order-not-found"));
problem.setProperty("errorCode", "ORDER_NOT_FOUND");
HTTP/1.1 404 Not Found · application/problem+json
{
  "type": "https://example.com/problems/order-not-found",
  "title": "Order not found",
  "status": 404,
  "detail": "Order 7c... does not exist",
  "instance": "/api/orders/7c...",
  "errorCode": "ORDER_NOT_FOUND"
}

Las propiedades adicionales son útiles para valores que necesita una aplicación cliente, por ejemplo un errorCode estable, pero conviene evitar convertir el error en un contenedor arbitrario de detalles internos.

Spring utiliza application/problem+json para representar ProblemDetail cuando corresponde. Además, las excepciones web del framework implementan el contrato ErrorResponse, lo que permite un tratamiento coherente de errores HTTP del propio Spring.

06

Diseña códigos de error estables para el cliente

El texto de detail está pensado para personas y puede cambiar o traducirse. Una aplicación frontend no debería contener lógica como if (message.equals("Order already cancelled")).

public enum ApiErrorCode {
    ORDER_NOT_FOUND,
    ORDER_STATE_CONFLICT,
    VALIDATION_FAILED
}
problem.setProperty("errorCode", ApiErrorCode.ORDER_STATE_CONFLICT.name());

Ahora el consumidor puede programar contra ORDER_STATE_CONFLICT, mientras el texto visible evoluciona de forma independiente.

El código debe representar una condición útil para el consumidor. Evita publicar nombres de clases Java como OrderStateConflictException: acoplarías el contrato externo a una decisión de implementación.

07

Validación: cuando @Valid falla

Supongamos este request:

public record CreateOrderRequest(
    @NotBlank String customerId,
    @NotEmpty List<@Valid OrderLineRequest> lines
) {}
@PostMapping
@ResponseStatus(HttpStatus.CREATED)
public OrderResponse create(
    @Valid @RequestBody CreateOrderRequest request
) {
    return mapper.toResponse(service.create(request));
}

Cuando falla la validación de un objeto enlazado con @RequestBody, una de las excepciones relevantes de Spring MVC es MethodArgumentNotValidException. Podemos convertir los errores de campo a una estructura explícita:

@RestControllerAdvice
public class ApiExceptionHandler extends ResponseEntityExceptionHandler {

    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex,
            HttpHeaders headers,
            HttpStatusCode status,
            WebRequest request) {

        ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
        problem.setTitle("Validation failed");
        problem.setDetail("One or more request fields are invalid");
        problem.setProperty("errorCode", "VALIDATION_FAILED");

        List<Map<String, String>> errors = ex.getBindingResult()
            .getFieldErrors()
            .stream()
            .map(error -> Map.of(
                "field", error.getField(),
                "message", Objects.requireNonNullElse(
                    error.getDefaultMessage(), "Invalid value")
            ))
            .toList();

        problem.setProperty("errors", errors);
        return handleExceptionInternal(ex, problem, headers, status, request);
    }
}
HTTP/1.1 400 Bad Request
{
  "title": "Validation failed",
  "status": 400,
  "detail": "One or more request fields are invalid",
  "errorCode": "VALIDATION_FAILED",
  "errors": [
    { "field": "customerId", "message": "must not be blank" },
    { "field": "lines", "message": "must not be empty" }
  ]
}

Matiz importante: la validación de parámetros de método puede producir HandlerMethodValidationException. No asumas que toda validación MVC termina siempre en MethodArgumentNotValidException.

08

ResponseEntityExceptionHandler: no reinventes los errores de Spring MVC

ResponseEntityExceptionHandler es una base conveniente para un @ControllerAdvice que centraliza excepciones producidas por Spring MVC. Podemos extenderla y personalizar puntos concretos sin crear desde cero handlers para cada fallo de binding, conversión o validación.

@RestControllerAdvice
public class ApiExceptionHandler extends ResponseEntityExceptionHandler {

    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail handleOrderNotFound(OrderNotFoundException ex) {
        return problem(
            HttpStatus.NOT_FOUND,
            "Order not found",
            ex.getMessage(),
            "ORDER_NOT_FOUND"
        );
    }

    private ProblemDetail problem(
            HttpStatus status,
            String title,
            String detail,
            String errorCode) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(status, detail);
        problem.setTitle(title);
        problem.setProperty("errorCode", errorCode);
        return problem;
    }
}

Esta combinación suele funcionar bien: handlers específicos para fallos de dominio y la infraestructura de Spring para fallos propios del framework.

09

El handler de Exception no debe filtrar la causa real

Es razonable tener una última red para errores no clasificados, pero su responsabilidad es doble: devolver una respuesta segura al cliente y conservar suficiente información en el servidor para investigar.

private static final Logger log = LoggerFactory.getLogger(ApiExceptionHandler.class);

@ExceptionHandler(Exception.class)
ProblemDetail handleUnexpected(Exception ex, HttpServletRequest request) {
    String errorId = UUID.randomUUID().toString();

    log.error("Unhandled API error id={} method={} path={}",
        errorId, request.getMethod(), request.getRequestURI(), ex);

    ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.INTERNAL_SERVER_ERROR);
    problem.setTitle("Internal server error");
    problem.setDetail("An unexpected error occurred");
    problem.setProperty("errorCode", "INTERNAL_ERROR");
    problem.setProperty("errorId", errorId);
    return problem;
}

El cliente recibe un identificador que puede incluir en un ticket. Los logs conservan stack trace y contexto técnico. Eso es mucho mejor que devolver directamente ex.getMessage().

Nunca devuelvas al cliente stack traces, SQL, nombres de tablas, rutas del filesystem, secretos, tokens, hostnames internos o mensajes de excepciones de infraestructura sin revisar. Los errores también son una superficie de seguridad.
10

No todos los errores merecen ERROR en logs

Una API con buen manejo de errores puede seguir siendo inoperable si llena los logs de ruido. La severidad debería reflejar la situación operativa.

SituaciónNivel típicoRazón
404 esperado por id inexistenteDEBUG o ningún logEs comportamiento normal del contrato.
Validación 400Ninguno o DEBUGEl cliente puede corregir la petición.
409 por carrera o versión obsoletaINFO/WARN según contextoPuede ser esperado, pero interesa medir frecuencia.
Timeout de dependenciaWARN o ERRORExiste degradación operacional.
Excepción inesperadaERRORNecesita investigación.

Evita loguear la misma excepción en controller, service, repository y advice. Un único fallo convertido en cuatro stack traces hace más difícil investigar, no más fácil.

11

Ejemplo completo: dominio limpio, API consistente

Excepciones de dominio

public class OrderNotFoundException extends RuntimeException {
    public OrderNotFoundException(UUID id) {
        super("Order " + id + " does not exist");
    }
}

public class OrderStateConflictException extends RuntimeException {
    public OrderStateConflictException(UUID id, OrderStatus status) {
        super("Order " + id + " cannot be confirmed from " + status);
    }
}

Servicio

@Service
public class OrderService {
    private final OrderRepository repository;

    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }

    public Order findById(UUID id) {
        return repository.findById(id)
            .orElseThrow(() -> new OrderNotFoundException(id));
    }

    @Transactional
    public Order confirm(UUID id) {
        Order order = findById(id);
        if (order.getStatus() != OrderStatus.PENDING) {
            throw new OrderStateConflictException(id, order.getStatus());
        }
        order.confirm();
        return order;
    }
}

Controlador

@RestController
@RequestMapping("/api/orders")
public class OrderController {
    private final OrderService service;
    private final OrderMapper mapper;

    public OrderController(OrderService service, OrderMapper mapper) {
        this.service = service;
        this.mapper = mapper;
    }

    @GetMapping("/{id}")
    public OrderResponse find(@PathVariable UUID id) {
        return mapper.toResponse(service.findById(id));
    }

    @PostMapping("/{id}/confirmation")
    public OrderResponse confirm(@PathVariable UUID id) {
        return mapper.toResponse(service.confirm(id));
    }
}

Advice

@RestControllerAdvice
public class ApiExceptionHandler extends ResponseEntityExceptionHandler {

    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail handleNotFound(OrderNotFoundException ex) {
        return problem(HttpStatus.NOT_FOUND,
            "Order not found", ex.getMessage(), "ORDER_NOT_FOUND");
    }

    @ExceptionHandler(OrderStateConflictException.class)
    ProblemDetail handleConflict(OrderStateConflictException ex) {
        return problem(HttpStatus.CONFLICT,
            "Order state conflict", ex.getMessage(), "ORDER_STATE_CONFLICT");
    }

    private ProblemDetail problem(
            HttpStatus status, String title, String detail, String code) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(status, detail);
        problem.setTitle(title);
        problem.setProperty("errorCode", code);
        return problem;
    }
}

La ventaja importante no es tener menos líneas. Es que cada capa responde una pregunta distinta: el dominio explica qué condición falló, el servicio controla el caso de uso y el advice define el contrato HTTP.

12

¿Y @ResponseStatus?

Podemos anotar una excepción con @ResponseStatus:

@ResponseStatus(HttpStatus.NOT_FOUND)
public class OrderNotFoundException extends RuntimeException {
    // ...
}

Es cómodo para casos pequeños, pero acopla directamente la excepción al protocolo HTTP. Si la misma excepción se utiliza desde un consumidor Kafka, un job batch o una interfaz CLI, esa decisión deja de ser tan natural.

Regla práctica: para APIs pequeñas puede ser suficiente. Cuando existe una capa de dominio reutilizable o necesitas un contrato de error rico y consistente, prefiero traducir las excepciones en un advice.

13

Errores frecuentes

try/catch en cada endpoint

Duplica política HTTP y llena el camino feliz de infraestructura.

200 con {"success": false}

Rompe la semántica HTTP y dificulta clientes, métricas, proxies y observabilidad.

500 para cualquier fallo

Hace indistinguibles errores del cliente, conflictos de negocio y bugs del servidor.

Mensajes como contrato

Los textos cambian; usa códigos de error estables si el cliente necesita reaccionar.

Filtrar ex.getMessage()

Las excepciones técnicas pueden contener información interna o sensible.

Un DTO diferente por controlador

Obliga al consumidor a aprender múltiples formatos para la misma API.

Loguear 404 como ERROR

Convierte comportamiento esperado en ruido operacional.

Capturar Exception demasiado pronto

Un catch genérico en el servicio puede destruir el significado real del fallo.

14

Cómo lo explicaría en una entrevista

“En una API Spring Boot separo las excepciones de dominio de su representación HTTP. Los controladores se concentran en el camino feliz y uso un @RestControllerAdvice con @ExceptionHandler para traducir errores a códigos HTTP coherentes. Para el body prefiero ProblemDetail, que implementa el modelo RFC 9457, y añado un código de error estable cuando el cliente necesita reaccionar. Trato validaciones, conflictos y recursos inexistentes de forma explícita, y dejo un handler de último recurso para 500 que registra el stack trace pero nunca expone detalles internos al consumidor.”

15

Checklist para producción

  • El mismo problema produce el mismo status y formato en todos los endpoints.
  • El body usa una estructura estándar y documentada.
  • Los clientes pueden depender de un errorCode estable, no de un mensaje humano.
  • Los errores de validación identifican campos concretos cuando resulta útil.
  • Los 500 no exponen stack traces ni detalles de infraestructura.
  • Existe un identificador correlacionable para investigar fallos inesperados.
  • Los logs distinguen comportamiento esperado de incidentes reales.
  • Los errores están incluidos en tests de contrato/integración, no solo el camino feliz.
