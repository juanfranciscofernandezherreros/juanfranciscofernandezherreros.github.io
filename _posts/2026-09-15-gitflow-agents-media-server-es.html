Gitflow gobernado por AGENTS.md

Un modelo de promoción explícito para que cada cambio nazca en el lugar correcto, pase controles verificables y termine en una release trazable sin convertir las ramas temporales en infraestructura permanente.

01

La idea esencial

Gitflow no es solo una colección de nombres de rama. Es una política de movimiento: define desde qué estado nace un cambio, qué rama puede recibirlo, cuándo se considera publicable y qué evidencia queda después. En media-server, esa política se documenta en AGENTS.md, se valida parcialmente con GitHub Actions y se ejecuta mediante pull requests.

El modelo conserva dos ramas permanentes. main representa las versiones publicadas y develop reúne el siguiente estado integrado. Las ramas feature/*, release/* y hotfix/* son herramientas temporales: existen para aislar una decisión, obtener revisión y producir un historial comprensible; desaparecen cuando han cumplido su función. El escenario no es teórico: se aplica al repositorio que construye la plataforma multimedia self-hosted descrita en este blog.

02

Responsabilidad de cada rama

main

Contiene el estado publicado. Recibe únicamente releases preparadas o hotfixes urgentes. Los tags de versión se crean sobre sus commits.

PERMANENTE

develop

Es la línea de integración. De ella nacen las features y las releases, y a ella regresan ambos tipos de cambio.

PERMANENTE

feature/X.Y.Z-descripción

Aísla un cambio funcional o documental. Nace siempre desde develop sincronizada y solo puede promoverse hacia develop.

TEMPORAL

release/X.Y.Z

Congela el conjunto que se publicará, prepara el changelog y se fusiona tanto en main como en develop.

TEMPORAL

hotfix/X.Y.Z-descripción

Nace desde main para corregir producción. Debe regresar a main y develop para evitar líneas divergentes.

TEMPORAL

Tag vX.Y.Z

Identifica de forma inmutable el commit publicado en main. La GitHub Release explica el contenido de esa versión.

HITO INMUTABLE
03

Qué hace AGENTS.md

AGENTS.md es un contrato operativo para los agentes que trabajan en el repositorio. No sustituye a Git ni concede permisos especiales: convierte decisiones del equipo en instrucciones previas a cualquier edición. Su objetivo es impedir que la automatización improvise una versión, trabaje sobre una rama obsoleta o publique desde un origen incorrecto.

  1. Solicita una versión exacta y su tipo.

    Antes de editar exige X.Y.Z y una decisión explícita entre major, minor o patch. El agente no puede calcular ni corregir esa versión por su cuenta.

  2. Comprueba producción.

    Cambia a main, ejecuta git fetch origin y git pull --ff-only origin main, y detiene el trabajo si hay suciedad local o divergencia.

  3. Prepara la base de desarrollo.

    Para una feature, cambia a develop, la sincroniza con --ff-only y verifica que el árbol esté limpio.

  4. Fija el origen.

    La feature debe crearse desde el HEAD sincronizado de develop, nunca desde main, otra feature o una copia desactualizada.

  5. Normaliza nombres y rutas.

    Exige nombres como feature/2.1.1-create-features-from-develop, en minúsculas y kebab-case, y define qué destinos acepta cada rama.

  6. Controla el final de vida.

    Prohíbe borrar una rama antes de que GitHub confirme el merge y evita crear una rama permanente llamada releases.

  7. Vincula versión y publicación.

    La release, el tag vX.Y.Z y la GitHub Release deben usar exactamente la versión confirmada y originarse en main.

Límite importante: un documento puede orientar a un agente obediente, pero no bloquea por sí solo un push manual. Por eso las reglas críticas se complementan con workflows y protección de ramas.

04

Flujo completo de una feature

El proyecto comprueba primero main porque es la referencia publicada. Después cambia deliberadamente a develop, que es la base canónica de cualquier trabajo ordinario:

git switch main
git fetch origin
git pull --ff-only origin main
git status --short

git switch develop
git pull --ff-only origin develop
git status --short

git switch -c feature/2.1.1-create-features-from-develop

--ff-only es una barrera pequeña pero útil: actualiza la rama únicamente si Git puede avanzar el puntero sin inventar un merge local. Si falla, hay una divergencia que debe entenderse antes de continuar. Del mismo modo, una salida vacía de git status --short confirma que el cambio nuevo no se mezclará con modificaciones anteriores.

Tras editar y validar, se crea un commit cohesivo, se publica la feature y se abre un pull request hacia develop. La rama no se elimina al enviar el PR; se elimina localmente y en origin solo después de que GitHub informe de estado MERGED.

git add AGENTS.md
git commit -m "docs: create feature branches from develop"
git push -u origin feature/2.1.1-create-features-from-develop

gh pr create --base develop \
  --head feature/2.1.1-create-features-from-develop

gh pr checks 26 --watch
gh pr merge 26 --merge
05

De develop a una release

Una feature integrada todavía no es una versión publicada. La rama release/X.Y.Z nace desde develop y representa el conjunto exacto que se quiere promocionar. En ella pueden hacerse ajustes propios de publicación, como transformar la sección Unreleased del changelog en 2.1.1, sin introducir funcionalidad nueva.

MovimientoPropósitoResultado
develop → release/2.1.1Congelar y preparar la versión.Rama temporal revisable.
release/2.1.1 → mainPublicar el estado aprobado.Commit de producción.
release/2.1.1 → developDevolver el changelog y cualquier ajuste de release.Ramas permanentes coherentes.
main → v2.1.1Marcar el commit publicado.Referencia inmutable y GitHub Release.
git switch develop
git pull --ff-only origin develop
git switch -c release/2.1.1

# Preparar CHANGELOG.md, validar, commit y push
gh pr create --base main --head release/2.1.1
gh pr create --base develop --head release/2.1.1

git switch main
git pull --ff-only origin main
git tag -a v2.1.1 -m "Release v2.1.1"
git push origin v2.1.1
gh release create v2.1.1 --verify-tag

Los dos PR deben estar fusionados antes de borrar la rama release. El tag se crea después sobre main, no sobre la rama release ni sobre develop. Así, preguntar qué código representa v2.1.1 tiene una respuesta única.

06

El camino diferente de un hotfix

Un hotfix responde a un defecto urgente de una versión ya publicada. Por eso su base correcta es main, no develop: debe partir exactamente del estado que está en producción. El patrón es hotfix/X.Y.Z-descripción.

Una vez validado, se fusiona en main para publicar la corrección y en develop para que el próximo release no reintroduzca el problema. Después se crea el tag confirmado y se elimina la rama temporal. Usar únicamente el merge a main resolvería la incidencia inmediata, pero dejaría dos historias funcionalmente distintas.

07

Qué aplica GitHub Actions

El workflow source-branch.yml se ejecuta en pull requests dirigidos a main o develop. Su job Source branch policy aplica una matriz sencilla:

DestinoOrígenes permitidosEjemplo rechazado
mainrelease/*, hotfix/*feature/* → main
developfeature/*, release/*, hotfix/*random-branch → develop

El workflow validate.yml comprueba los dos ficheros Docker Compose, valida el JSON del dashboard de Grafana y busca marcadores de conflicto sin resolver. Estas pruebas contestan dos preguntas distintas: «¿ha seguido el cambio una ruta autorizada?» y «¿la configuración continúa siendo estructuralmente válida?».

Defensa por capas: AGENTS.md previene errores antes de editar; los PR hacen visible la decisión; GitHub Actions valida ruta y configuración; la protección de ramas debe exigir esos checks para impedir que un merge incorrecto los ignore.

Hay una limitación deliberada: el workflow reconoce el prefijo de la rama, pero no demuestra que una feature naciera realmente desde el HEAD de develop. Esa precondición se mantiene mediante AGENTS.md, la sincronización previa y la revisión del historial. Si fuera un requisito de cumplimiento fuerte, podría añadirse un control específico del ancestro común.

08

El caso real de media-server 2.1.1

La versión 2.1.1 corrigió precisamente el origen de las features. La rama feature/2.1.1-create-features-from-develop nació desde el commit sincronizado de develop. Su cambio convirtió esa práctica en una norma explícita de AGENTS.md y corrigió el diagrama que describe el modelo.

  1. PR #26: feature hacia develop.

    Los checks Source branch policy y validate pasaron; GitHub confirmó el merge antes de eliminar la feature.

  2. Rama release/2.1.1.

    Nació desde el nuevo develop y añadió la entrada correspondiente al changelog.

  3. PR #27: release hacia main.

    Promocionó la corrección al historial publicable.

  4. PR #28: release hacia develop.

    Devolvió la preparación del changelog a la línea de integración.

  5. Tag y GitHub Release.

    v2.1.1 quedó asociado al merge de main; después se borró la rama release.

El resultado final conserva únicamente main y develop como ramas permanentes. El historial permite reconstruir qué PR integró el cambio, qué controles pasaron, qué commit se publicó y qué versión lo identifica.

09

SemVer como decisión explícita

Semantic Versioning usa MAJOR.MINOR.PATCH. Un cambio incompatible incrementa MAJOR; una capacidad compatible incrementa MINOR; una corrección compatible incrementa PATCH. En este repositorio la clasificación no se delega al agente, porque el número comunica intención del mantenedor, no solo una propiedad mecánica del diff.

Así, activar el modo kernel TUN de Tailscale se publicó como 2.1.0 al introducir un cambio operativo relevante. Corregir después las reglas documentales de creación de features se publicó como 2.1.1. Lo importante no es memorizar esos dos ejemplos, sino conservar la decisión explícita y usar el mismo valor en rama, changelog, tag y release.

10

Errores que este modelo evita

Feature desde main

Omite cambios ya integrados en develop y obliga después a reconciliar historiales. La regla nueva lo prohíbe expresamente.

Push directo a main

Evita revisión, controles y trazabilidad. main solo recibe releases y hotfixes mediante las rutas previstas.

Release permanente

Una rama releases acumula estados ambiguos. Cada versión usa una rama temporal y numerada que se elimina al terminar.

Borrado prematuro

Eliminar antes de confirmar el merge puede retirar la referencia necesaria para revisar o recuperar el cambio.

Tag sobre develop

Mezcla integración con publicación. Los tags se colocan exclusivamente sobre el commit correspondiente de main.

Versión inventada

Automatizar el incremento sin confirmación puede comunicar una compatibilidad equivocada. El usuario decide número y tipo.

11

Cuándo termina realmente el flujo

El trabajo no termina al escribir código ni al pulsar merge una vez. Para una versión ordinaria, la definición de terminado incluye: feature integrada en develop; checks en verde; release integrada en ambas ramas permanentes; tag apuntando al commit de main; GitHub Release publicada; ramas temporales eliminadas; copias locales sincronizadas y árbol de trabajo limpio.

Este cierre disciplinado reduce decisiones implícitas. La próxima persona —o el próximo agente— no necesita adivinar si una rama sigue activa, si un tag procede de producción o si un ajuste de release regresó a desarrollo. Git deja de ser solo almacenamiento de commits y pasa a ser el registro verificable de cómo se tomó y publicó cada decisión.
