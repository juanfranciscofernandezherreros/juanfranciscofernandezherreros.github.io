Gitflow governed by AGENTS.md

01

The essential idea

Gitflow is not merely a collection of branch names. It is a movement policy: it defines where a change starts, which branch may receive it, when it is publishable, and what evidence remains afterwards. In media-server, that policy is documented in AGENTS.md, partially enforced by GitHub Actions, and executed through pull requests.

The model keeps two permanent branches. main represents published versions, while develop collects the next integrated state. The feature/*, release/*, and hotfix/* branches are temporary tools. They isolate a decision, make review possible, and produce understandable history; they disappear after fulfilling that purpose. This is not a theoretical scenario: it governs the repository that builds the self-hosted media platform described on this blog.

03

What AGENTS.md does

AGENTS.md is an operational contract for agents working in the repository. It neither replaces Git nor grants special permissions. Instead, it turns team decisions into instructions that apply before any edit. Its purpose is to prevent automation from inventing a version, working on an obsolete branch, or publishing from an incorrect origin.

  1. Request an exact version and type.

    Before editing, it requires X.Y.Z and an explicit choice of major, minor, or patch. The agent cannot calculate or correct the version independently.

  2. Check production.

    Switch to main, run git fetch origin and git pull --ff-only origin main, and stop if local changes or divergence exist.

  3. Prepare the development base.

    For a feature, switch to develop, synchronize it with --ff-only, and verify a clean worktree.

  4. Fix the origin.

    The feature must be created from synchronized develop HEAD, never from main, another feature, or a stale copy.

  5. Normalize names and routes.

    Require names such as feature/2.1.1-create-features-from-develop, lowercase kebab-case descriptions, and explicit destinations for each branch type.

  6. Control end of life.

    Do not delete a branch until GitHub confirms its merge, and never create a permanent releases branch.

  7. Bind version to publication.

    The release branch, vX.Y.Z tag, and GitHub Release use exactly the confirmed version and originate from main.

Important boundary: a document guides a compliant agent but cannot block a manual push by itself. Critical rules therefore need workflows and branch protection as complementary controls.

04

The complete feature flow

The project checks main first because it is the published reference. It then deliberately switches to develop, the canonical base for ordinary work:

git switch main
git fetch origin
git pull --ff-only origin main
git status --short

git switch develop
git pull --ff-only origin develop
git status --short

git switch -c feature/2.1.1-create-features-from-develop

--ff-only is a small but useful barrier. It updates the branch only when Git can advance the pointer without inventing a local merge. A failure exposes divergence that must be understood before proceeding. Likewise, empty output from git status --short confirms that the new change will not be mixed with previous modifications.

After editing and validation, a cohesive commit is created, the feature is pushed, and a pull request targets develop. The branch is not removed when the PR is submitted. It is deleted locally and from origin only after GitHub reports the MERGED state.

git add AGENTS.md
git commit -m "docs: create feature branches from develop"
git push -u origin feature/2.1.1-create-features-from-develop

gh pr create --base develop \
  --head feature/2.1.1-create-features-from-develop

gh pr checks 26 --watch
gh pr merge 26 --merge
05

From develop to a release

An integrated feature is not yet a published version. The release/X.Y.Z branch starts from develop and represents the exact set to promote. Release-only preparation, such as turning the changelog's Unreleased section into 2.1.1, belongs there; new functionality does not.

develop → release/2.1.1Freeze and prepare the version.Reviewable temporary branch.
release/2.1.1 → mainPublish the approved state.Production commit.
release/2.1.1 → developReturn changelog and release adjustments.Consistent permanent branches.
main → v2.1.1Mark the published commit.Immutable reference and GitHub Release.
git switch develop
git pull --ff-only origin develop
git switch -c release/2.1.1

# Prepare CHANGELOG.md, validate, commit, and push
gh pr create --base main --head release/2.1.1
gh pr create --base develop --head release/2.1.1

git switch main
git pull --ff-only origin main
git tag -a v2.1.1 -m "Release v2.1.1"
git push origin v2.1.1
gh release create v2.1.1 --verify-tag

Both PRs must be merged before the release branch is deleted. The tag is then created on main, not on the release branch or develop. The question “which code does v2.1.1 represent?” therefore has one answer.

06

The different hotfix path

A hotfix addresses an urgent defect in an already published version. Its correct base is therefore main, not develop: it must start from the precise production state. Its pattern is hotfix/X.Y.Z-description.

Once validated, it merges into main to publish the correction and into develop so that the next release cannot reintroduce the defect. The confirmed tag follows, and the temporary branch is removed. Merging only to main would solve the immediate incident while leaving two functionally different histories.

07

What GitHub Actions enforces

The source-branch.yml workflow runs for pull requests targeting main or develop. Its Source branch policy job applies a small matrix:

DestinationAllowed originsRejected example
mainrelease/*, hotfix/*feature/* → main
developfeature/*, release/*, hotfix/*random-branch → develop

The validate.yml workflow checks both Docker Compose files, validates the Grafana dashboard JSON, and searches for unresolved conflict markers. These jobs answer different questions: “Did the change follow an authorized route?” and “Is the configuration still structurally valid?”

Layered defense: AGENTS.md prevents errors before editing; PRs expose the decision; GitHub Actions validates route and configuration; branch protection should require those checks so that an incorrect merge cannot ignore them.

There is a deliberate limitation. The workflow recognizes branch prefixes, but it does not prove that a feature originally started at develop HEAD. That precondition is maintained by AGENTS.md, prior synchronization, and history review. A stricter compliance environment could add a dedicated common-ancestor check.

08

The real media-server 2.1.1 case

Version 2.1.1 corrected the origin of feature branches. feature/2.1.1-create-features-from-develop started from synchronized develop. Its change turned that practice into an explicit AGENTS.md rule and corrected the diagram describing the model.

  1. PR #26: feature into develop.

    The Source branch policy and validate checks passed; GitHub confirmed the merge before the feature was deleted.

  2. release/2.1.1 branch.

    It started from the new develop state and added the corresponding changelog entry.

  3. PR #27: release into main.

    It promoted the correction into publishable history.

  4. PR #28: release into develop.

    It returned the changelog preparation to the integration line.

  5. Tag and GitHub Release.

    v2.1.1 was associated with the main merge, after which the release branch was removed.

The final state keeps only main and develop as permanent branches. The history shows which PR integrated the change, which controls passed, which commit was published, and which version identifies it.

09

SemVer as an explicit decision

Semantic Versioning uses MAJOR.MINOR.PATCH. An incompatible change increments MAJOR; compatible functionality increments MINOR; a compatible correction increments PATCH. This repository does not delegate classification to the agent because the number communicates maintainer intent, not merely a mechanical property of a diff.

Enabling Tailscale kernel TUN mode was published as 2.1.0 because it introduced a relevant operational change. Correcting the feature-creation rules was then published as 2.1.1. The lesson is not to memorize those examples, but to preserve the explicit decision and use the same value in branch, changelog, tag, and release.

10

Failures this model prevents

Feature from main

It omits work already integrated in develop and forces history reconciliation later. The new rule explicitly prohibits it.

Direct push to main

It bypasses review, controls, and traceability. main receives only releases and hotfixes through approved routes.

Permanent release branch

A releases branch accumulates ambiguous states. Every version gets a numbered temporary branch that is deleted afterwards.

Premature deletion

Removing a branch before merge confirmation can discard the reference needed for review or recovery.

Tag on develop

It confuses integration with publication. Tags belong exclusively to the corresponding main commit.

Invented version

Automatic increments without confirmation may communicate incorrect compatibility. The user decides number and type.

11

When the flow is actually complete

Work does not end when code is written or when one merge button is pressed. For a regular version, done means: the feature is integrated into develop; checks are green; the release is integrated into both permanent branches; the tag points to the main commit; the GitHub Release is published; temporary branches are removed; local copies are synchronized; and the worktree is clean.

This disciplined closure removes implicit decisions. The next person—or the next agent—does not need to guess whether a branch is still active, whether a tag came from production, or whether a release adjustment returned to development. Git becomes more than commit storage: it becomes the verifiable record of how every decision was made and published.
