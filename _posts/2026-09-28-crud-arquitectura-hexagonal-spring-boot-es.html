CRUD con Arquitectura Hexagonal

Un CRUD parece sencillo hasta que el controlador conoce JPA, el servicio conoce Hibernate y el modelo de negocio acaba lleno de anotaciones de infraestructura. En esta guía construiremos un CRUD de usuarios separando dominio, aplicación e infraestructura para entender de verdad qué significan Ports & Adapters.

Nivel
Intermedio
Stack
Java + Spring Boot + JPA
Objetivo
CRUD desacoplado
01

El problema que queremos evitar

La estructura Controller → Service → Repository funciona bien para aplicaciones pequeñas. El problema aparece cuando esas capas empiezan a mezclar responsabilidades. Un servicio que debería expresar reglas de aplicación termina importando JpaRepository, una entidad de negocio acaba anotada con @Entity y una decisión de persistencia condiciona todo el código.

La Arquitectura Hexagonal propone que el núcleo de la aplicación no dependa de los detalles externos. Spring, REST, JPA, Hibernate o MySQL son mecanismos de entrada y salida. Son importantes, pero no deberían definir el modelo de negocio.

Modelo mental: el negocio define qué necesita. La infraestructura decide cómo satisfacerlo.
02

Las tres zonas del proyecto

Domain

Modelos y conceptos del negocio. No conoce Spring, JPA ni HTTP.

Application

Casos de uso y orquestación. Decide qué debe ocurrir en cada operación.

Infrastructure

REST, JPA, base de datos, configuración y adaptadores tecnológicos.

La regla útil no es memorizar carpetas, sino controlar la dirección de las dependencias. El código interior debe poder compilarse conceptualmente sin saber si mañana persistiremos en MySQL, MongoDB o una API remota.

04

El dominio: User sin JPA

Empezamos por el modelo que representa al usuario dentro de nuestro negocio. No es una tabla y no es una respuesta HTTP.

public class User {
    private final Long id;
    private final String name;
    private final String email;

    public User(Long id, String name, String email) {
        this.id = id;
        this.name = name;
        this.email = email;
    }

    public Long getId() { return id; }
    public String getName() { return name; }
    public String getEmail() { return email; }
}

La ausencia de @Entity, @Table, @Id o @Column es deliberada. El dominio no necesita saber cómo se almacenará el objeto.

05

Puertos de entrada: qué puede hacer la aplicación

Los puertos de entrada describen las capacidades del sistema. Para un CRUD podemos modelar cada operación como un caso de uso.

public interface CreateUserUseCase {
    User create(User user);
}

public interface GetUserUseCase {
    User getById(Long id);
}

public interface GetAllUsersUseCase {
    List<User> getAll();
}

public interface UpdateUserUseCase {
    User update(Long id, User user);
}

public interface DeleteUserUseCase {
    void delete(Long id);
}

Estas interfaces no dicen nada de REST. La misma aplicación podría invocar los casos de uso desde un controlador HTTP, un consumidor Kafka, una tarea batch o una CLI.

06

Puerto de salida: qué necesita la aplicación

Para completar los casos de uso necesitamos persistencia, pero el núcleo no debería imponer JPA. Por eso definimos una abstracción propia.

public interface UserRepositoryPort {
    User save(User user);
    Optional<User> findById(Long id);
    List<User> findAll();
    User update(User user);
    void deleteById(Long id);
    boolean existsById(Long id);
}

Este contrato expresa necesidades del caso de uso. La implementación puede cambiar sin obligar a modificar el servicio de aplicación.

07

Application Service: implementar el CRUD

UserService implementa los puertos de entrada y depende únicamente del puerto de salida.

public class UserService implements
        CreateUserUseCase,
        GetUserUseCase,
        GetAllUsersUseCase,
        UpdateUserUseCase,
        DeleteUserUseCase {

    private final UserRepositoryPort repository;

    public UserService(UserRepositoryPort repository) {
        this.repository = repository;
    }

    @Override
    public User create(User user) {
        return repository.save(user);
    }

    @Override
    public User getById(Long id) {
        return repository.findById(id)
                .orElseThrow(() -> new RuntimeException("User not found"));
    }

    @Override
    public List<User> getAll() {
        return repository.findAll();
    }

    @Override
    public User update(Long id, User user) {
        User existing = repository.findById(id)
                .orElseThrow(() -> new RuntimeException("User not found"));

        User updated = new User(
                existing.getId(),
                user.getName(),
                user.getEmail()
        );

        return repository.update(updated);
    }

    @Override
    public void delete(Long id) {
        if (!repository.existsById(id)) {
            throw new RuntimeException("User not found");
        }
        repository.deleteById(id);
    }
}

Los RuntimeException son intencionadamente provisionales en esta primera versión. El siguiente paso natural es introducir excepciones de dominio y traducirlas a respuestas HTTP coherentes con @ControllerAdvice.

08

Infraestructura de persistencia

UserEntity

Ahora sí entramos en el mundo JPA. La entidad de persistencia puede conocer anotaciones y decisiones de base de datos.

@Entity
@Table(name = "users")
public class UserEntity {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private String email;

    public UserEntity() {}
    // getters y setters
}

JpaUserRepository

public interface JpaUserRepository
        extends JpaRepository<UserEntity, Long> {
}

Mapper de persistencia

@Component
public class UserPersistenceMapper {
    public UserEntity toEntity(User user) {
        UserEntity entity = new UserEntity();
        entity.setId(user.getId());
        entity.setName(user.getName());
        entity.setEmail(user.getEmail());
        return entity;
    }

    public User toDomain(UserEntity entity) {
        return new User(
                entity.getId(),
                entity.getName(),
                entity.getEmail()
        );
    }
}

Adaptador de salida

@Component
public class UserPersistenceAdapter implements UserRepositoryPort {
    private final JpaUserRepository repository;
    private final UserPersistenceMapper mapper;

    public UserPersistenceAdapter(
            JpaUserRepository repository,
            UserPersistenceMapper mapper) {
        this.repository = repository;
        this.mapper = mapper;
    }

    @Override
    public User save(User user) {
        UserEntity saved = repository.save(mapper.toEntity(user));
        return mapper.toDomain(saved);
    }

    @Override
    public Optional<User> findById(Long id) {
        return repository.findById(id).map(mapper::toDomain);
    }

    @Override
    public List<User> findAll() {
        return repository.findAll()
                .stream()
                .map(mapper::toDomain)
                .toList();
    }

    @Override
    public User update(User user) {
        return mapper.toDomain(repository.save(mapper.toEntity(user)));
    }

    @Override
    public void deleteById(Long id) {
        repository.deleteById(id);
    }

    @Override
    public boolean existsById(Long id) {
        return repository.existsById(id);
    }
}
UserService→UserRepositoryPort→UserPersistenceAdapter→JpaUserRepository→Database
09

Adaptador de entrada REST

HTTP también es infraestructura. En lugar de exponer UserEntity, definimos contratos específicos para la API.

public record CreateUserRequest(
        String name,
        String email
) {}

public record UpdateUserRequest(
        String name,
        String email
) {}

public record UserResponse(
        Long id,
        String name,
        String email
) {}

El controlador depende de los puertos de entrada. No necesita conocer JPA ni el adaptador de persistencia.

@RestController
@RequestMapping("/users")
public class UserController {
    private final CreateUserUseCase createUser;
    private final GetUserUseCase getUser;
    private final GetAllUsersUseCase getAllUsers;
    private final UpdateUserUseCase updateUser;
    private final DeleteUserUseCase deleteUser;

    public UserController(
            CreateUserUseCase createUser,
            GetUserUseCase getUser,
            GetAllUsersUseCase getAllUsers,
            UpdateUserUseCase updateUser,
            DeleteUserUseCase deleteUser) {
        this.createUser = createUser;
        this.getUser = getUser;
        this.getAllUsers = getAllUsers;
        this.updateUser = updateUser;
        this.deleteUser = deleteUser;
    }

    @PostMapping
    public User create(@RequestBody CreateUserRequest request) {
        return createUser.create(
                new User(null, request.name(), request.email())
        );
    }

    @GetMapping("/{id}")
    public User getById(@PathVariable Long id) {
        return getUser.getById(id);
    }

    @GetMapping
    public List<User> getAll() {
        return getAllUsers.getAll();
    }

    @PutMapping("/{id}")
    public User update(
            @PathVariable Long id,
            @RequestBody UpdateUserRequest request) {
        return updateUser.update(
                id,
                new User(id, request.name(), request.email())
        );
    }

    @DeleteMapping("/{id}")
    public void delete(@PathVariable Long id) {
        deleteUser.delete(id);
    }
}

Para producción, el paso siguiente sería usar UserRestMapper y devolver siempre UserResponse, evitando que el contrato HTTP quede acoplado al modelo de dominio.

10

Configurar UserService sin acoplarlo a Spring

Podemos mantener UserService sin @Service y registrarlo desde infraestructura.

@Configuration
public class BeanConfiguration {
    @Bean
    public UserService userService(UserRepositoryPort repository) {
        return new UserService(repository);
    }
}

Spring encuentra UserPersistenceAdapter, que implementa UserRepositoryPort, y lo inyecta en el servicio. El núcleo sigue sin depender de anotaciones de Spring.

Ese recorrido resume la arquitectura. El controller adapta HTTP a la aplicación; el servicio ejecuta el caso de uso; el puerto de salida expresa la necesidad de persistencia; y el adaptador JPA traduce esa necesidad a una tecnología concreta.

13

Qué ganamos y qué pagamos

Arquitectura Hexagonal no es gratis. Introduce más tipos, mappers y contratos. En un CRUD descartable puede ser una complejidad innecesaria. En una aplicación con reglas de negocio, varias entradas, persistencias cambiantes o una vida útil larga, esas fronteras empiezan a devolver valor.

BeneficioCoste
Dominio independiente de JPA y HTTP.Más clases y conversiones.
Casos de uso fáciles de probar de forma aislada.Hay que decidir bien dónde vive cada responsabilidad.
Persistencia sustituible mediante adaptadores.Puede ser excesivo para CRUDs triviales.
Contratos explícitos entre capas.Un diseño pobre puede producir abstracciones sin valor.
La arquitectura no consiste en tener muchas carpetas. Consiste en proteger las reglas y casos de uso frente a detalles que deberían poder cambiar.
14

Por qué los tests se vuelven más sencillos

UserService solo depende de UserRepositoryPort. Eso permite probar la lógica con un fake o un mock sin arrancar una base de datos ni un contexto completo de Spring.

@Test
void shouldCreateUser() {
    UserRepositoryPort repository = mock(UserRepositoryPort.class);
    UserService service = new UserService(repository);

    User input = new User(null, "Ana", "ana@email.com");
    User saved = new User(1L, "Ana", "ana@email.com");

    when(repository.save(input)).thenReturn(saved);

    User result = service.create(input);

    assertEquals(1L, result.getId());
    verify(repository).save(input);
}

El test comprueba el caso de uso. JPA se prueba en otro nivel, mediante tests de integración del adaptador de persistencia.

15

Qué falta para llevarlo a un proyecto real

Este diseño deja visible el siguiente conjunto de mejoras: excepciones específicas, validación de entrada, respuestas HTTP consistentes, email único, mappers REST completos, paginación y tests de integración.

  • UserNotFoundException en lugar de RuntimeException.
  • EmailAlreadyExistsException para una regla de unicidad.
  • @ControllerAdvice para traducir errores a códigos HTTP.
  • @Valid, @NotBlank y @Email en los DTOs.
  • UserRestMapper para no devolver directamente el dominio.
  • Tests unitarios de casos de uso y tests de integración de adaptadores.

El manejo de excepciones merece una pieza propia porque ahí aparece otra frontera importante: el dominio expresa el error y el adaptador HTTP decide cómo representarlo al cliente.

16

La idea que conviene recordar

Los puertos describen lo que la aplicación ofrece o necesita; los adaptadores conectan esos puertos con tecnologías concretas.

El flujo final queda así:

REST
  ↓
Controller
  ↓
Input Port
  ↓
Application Service
  ↓
Domain
  ↓
Output Port
  ↓
Persistence Adapter
  ↓
JPA / Hibernate
  ↓
Database

Si mañana cambia la base de datos, el objetivo es modificar el adaptador, no reescribir el negocio. Si mañana REST deja de ser la única entrada, el caso de uso debería seguir siendo válido. Esa es la utilidad práctica de Ports & Adapters.
