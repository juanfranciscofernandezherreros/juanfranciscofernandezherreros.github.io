What this part covers

Building hello-world-argocd by hand in Part 1 was the point — it's how you learn what each file actually does. But a real team doesn't hand-write every microservice from scratch. This part uses crud-automation, a Python generator, to produce a brand new service with the exact same shape, then runs it through the same onboarding as Part 2 — copy the manifests pattern, register the Application, done.

01

The generator: --architecture minimal

crud-automation normally generates full CRUD microservices — Postgres, Flyway, MapStruct, security, observability. Its minimal architecture is the odd one out: it ignores the entity's fields entirely and produces the same bare skeleton as hello-world-argocd instead — one endpoint, no database, no security, no observability. Meant for exactly this: a new service that's going to be wired into GitOps, not a CRUD API.

Entity name
Becomes the project folder (crud-<name>-minimal), the Java class names, and the single endpoint's path. Here: GodbyeMicroservices.
Fields
Still required by the command's syntax, but completely ignored by this architecture — there's no CRUD to build them into.
02

Terminal walkthrough — generate, verify, publish, onboard

Every screenshot below is real output from generating this exact service, right before writing this page — same order you'd run it in.

1 — generate it

generate_crud.py GodbyeMicroservices "id:int" --architecture minimal

One command. The fields (id:int) are only there to satisfy the CLI's syntax — this architecture never reads them.

2 — what came out

8 files, all under app/

Same shape as hello-world-argocd: pom.xml, one Application class, one Controller, one test, a Dockerfile. Nothing else.

3 — it actually compiles and passes

mvn test

Generated code is worth nothing if it doesn't build. Spring context starts, the one controller test passes, exit code 0.

4 — build the image

docker build -t godbyemicroservices:local app

Identical step to Part 1, section 05 — just a different image name.

5 — get it into the cluster

kind load docker-image godbyemicroservices:local --name hello-world

Same cluster as hello-world — one kind cluster is happily running two independent services.

6 — publish the code repo

crud_generator.github_repo.push_to_github(...)

The same function --github calls on the CLI, run directly since the project already existed: git init + commit + gh repo create --push, plus fixing the new repo's Actions permissions.

7 — register with Argo

kubectl apply -f applications/godbyemicroservices.yaml

Exactly the pattern from Part 2, section 04: a copy of manifests/hello-world/ and applications/hello-world.yaml, three fields changed. Synced and Healthy within seconds.

8 — final proof

kubectl get pods + curl

The pod is Running, and the generated endpoint answers with the entity's own name baked in — proof this isn't a copy of hello-world, it's a distinct generated service.

04

The onboarding, as a sequence

1 You Copy manifests/hello-world/ to manifests/godbyemicroservices/ in gitops-config, rename every field.
2 You Copy applications/hello-world.yaml the same way — metadata.name, source.path, destination.namespace.
3 You git push, then kubectl apply -f applications/godbyemicroservices.yaml.
4 ArgoCD Picks it up as a second, fully independent Application — same reconciliation loop, same namespace isolation.

Nothing here is specific to a generated service — it's the exact same four steps Part 2 describes for any new service, hand-written or generated.

05

Reference commands

Generate

python generate_crud.py GodbyeMicroservices "id:int" --architecture minimal

Build + load

mvn -f app/pom.xml clean package
docker build -t godbyemicroservices:local app
kind load docker-image godbyemicroservices:local --name hello-world

Publish

python -c "from crud_generator.github_repo import push_to_github; print(push_to_github('crud-godbyemicroservices-minimal'))"

Onboard + verify

kubectl apply -f applications/godbyemicroservices.yaml
kubectl -n godbyemicroservices get pods
kubectl -n godbyemicroservices port-forward svc/godbyemicroservices 8082:8080
curl http://localhost:8082/godbyemicroservices
