Load 100,000 PostgreSQL rows

Provision durable storage, create the schema, generate a deterministic dataset inside PostgreSQL, and prove it is complete before the memory-constrained service starts.

00

Why the database comes first

The test is meaningful only if the dataset exists independently of the Java process. Generating a million Java objects at application startup would mix fixture creation with the failure under test and could exhaust the heap before the HTTP endpoint is available. Here PostgreSQL owns the data; Spring Boot merely queries it.

1 · Provision

Create PostgreSQL, its Service, and persistent volume.

2 · Seed

Create the table and generate 100,000 rows server-side.

3 · Verify

Check count and boundaries before deploying the API.

This ordering also makes failures legible. If the validation query returns 100,000 rows but the HTTP request later exhausts the heap, the fault is in materializing the query result, not in fixture creation.

01

Persistent PostgreSQL resources

A StatefulSet gives the database a stable workload identity. A ClusterIP Service provides the DNS name postgresql to clients in the namespace, and a PersistentVolumeClaim preserves PGDATA if the PostgreSQL pod is recreated.

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgresql-data
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 2Gi
---
apiVersion: v1
kind: Service
metadata:
  name: postgresql
spec:
  selector:
    app: postgresql
  ports:
    - port: 5432
      targetPort: 5432

The StatefulSet uses postgres:16-alpine and defines POSTGRES_DB=goodbye, POSTGRES_USER=goodbye, and the lab password through an environment value. In a production repository, store credentials in a Secret or external secret manager, not in a ConfigMap or article.

kubectl get statefulset,pod,svc,pvc -n godbyemicroservices-postgres-oom
kubectl wait --for=condition=Ready pod/postgresql-0 \
  -n godbyemicroservices-postgres-oom --timeout=180s
02

Create the table

The schema deliberately stays small. The numeric primary key makes boundaries easy to verify, while the payload gives each row an actual value that the JDBC driver and Java heap must retain.

CREATE TABLE IF NOT EXISTS goodbye_record (
    id      BIGINT PRIMARY KEY,
    payload VARCHAR(64) NOT NULL
);

IF NOT EXISTS lets the statement run again without destroying existing data. It is not a migration strategy for evolving schemas; use Flyway or Liquibase once the example grows beyond a controlled lab.

03

Generate 100,000 rows server-side

PostgreSQL's set-returning generate_series creates all identifiers inside the database engine. One set-based INSERT ... SELECT avoids 100,000 network round trips and avoids building a client-side list.

INSERT INTO goodbye_record (id, payload)
SELECT value, 'goodbye-' || value
FROM generate_series(1, 100000) AS value
ON CONFLICT (id) DO NOTHING;

The dataset is deterministic: ID 1 always has goodbye-1, and ID 100000 has goodbye-100000. ON CONFLICT DO NOTHING makes rerunning this seed safe when those primary keys already exist.

Execute the complete operation directly in the PostgreSQL pod:

kubectl exec -i -n godbyemicroservices-postgres-oom postgresql-0 -- \
  psql -U goodbye -d goodbye -v ON_ERROR_STOP=1 -c \
  "CREATE TABLE IF NOT EXISTS goodbye_record (id BIGINT PRIMARY KEY, payload VARCHAR(64) NOT NULL); INSERT INTO goodbye_record (id, payload) SELECT value, 'goodbye-' || value FROM generate_series(1, 100000) AS value ON CONFLICT (id) DO NOTHING;"

-v ON_ERROR_STOP=1 makes psql return failure immediately if either statement fails. That behavior is important in scripts and deployment checks.

04

Verify without downloading the table

Aggregate in PostgreSQL and return one compact row. Counting the result in Java, DBeaver, or a shell would first transfer the dataset and could reproduce the very memory problem we want to isolate.

kubectl exec -n godbyemicroservices-postgres-oom postgresql-0 -- \
  psql -U goodbye -d goodbye -c \
  "SELECT COUNT(*) AS total, MIN(id) AS first_id, MAX(id) AS last_id FROM goodbye_record;"

 total  | first_id | last_id
--------+----------+---------
 100000 |        1 |  100000
Acceptance condition: total=100000, first_id=1, and last_id=100000. Only after that result should the Spring Boot pod be started.

Sample a bounded page when inspecting content:

SELECT id, payload
FROM goodbye_record
ORDER BY id
LIMIT 20;
05

Initialization and persistence traps

Init scripts run once

Files in /docker-entrypoint-initdb.d run only when PostgreSQL initializes an empty data directory.

The PVC survives pods

Deleting the pod does not empty the database. A changed init ConfigMap will not automatically reseed an existing volume.

Schema before service

Use readiness and explicit validation so the application never silently starts against an empty table.

Bound inspection queries

Use aggregates or LIMIT. Do not render the full failure dataset in an administration client.

For an existing PVC, apply migrations or run the idempotent seed explicitly. Delete the PVC only when intentionally resetting this disposable lab, because that operation destroys the stored dataset.

06

From 100,000 to the OOM dataset

The exercise requested here stops at 100,000 rows. The deployed OOM variant later uses the exact same SQL with an upper bound of 1000000. That larger fixture makes exhaustion deterministic under the service's very small -Xmx18m heap.

-- OOM lab scale; same method, ten times as many rows
SELECT value, 'goodbye-' || value
FROM generate_series(1, 1000000) AS value;

Row count alone is not a portable memory threshold. Object layout, selected columns, JDBC driver, Java version, heap ceiling, and fetch strategy all affect the result. Treat the count as a reproducible fixture for this service, not as a universal OOM formula.
