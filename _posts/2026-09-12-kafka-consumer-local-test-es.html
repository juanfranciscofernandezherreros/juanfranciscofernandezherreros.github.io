Kafka · Spring Boot · Prueba end-to-end

Un consumer que funcionaba y guardaba datos vacíos

El mensaje llegaba, la transacción terminaba, los tests estaban verdes y PostgreSQL recibía una fila. Solo había un problema: las 23 columnas del jugador quedaban a NULL. Esta es la prueba local que lo hizo visible y la carga de 5.000 filas que demostró la corrección.

01

Arrancar no significa funcionar

El proyecto csv-stats-player-consumer recibe por Kafka un evento Avro que anuncia un CSV disponible. Si el tipo es STATS_PLAYER, abre el fichero, valida sus 23 columnas, transforma cada fila en una entidad JPA y la persiste en PostgreSQL.

La pregunta inicial parecía operativa: «¿puedo ejecutar este microservicio en mi Windows y consumir un evento real?». Sin embargo, una prueba útil debía responder algo más exigente: ¿puedo demostrar que el contenido correcto recorrió todo el sistema y llegó intacto a la base de datos?

02

Una plataforma local aislada

El consumer no es autónomo. Necesita PostgreSQL, un broker Kafka y Schema Registry para resolver los esquemas Avro. La prueba utilizó contenedores con nombres y puertos propios para no interferir con otros entornos Docker del equipo.

Desde el proceso Java del host, la configuración efectiva fue:

$env:DB_URL='jdbc:postgresql://localhost:15432/csvstats'
$env:DB_USER='csvstats'
$env:DB_PASS='csvstats'
$env:KAFKA_BOOTSTRAP_SERVERS='localhost:19092'
$env:KAFKA_CONSUMER_GROUP_ID='csvstats-local-load-5000-logs'
$env:KAFKA_AUTO_OFFSET_RESET='latest'
$env:KAFKA_SCHEMA_REGISTRY_URL='http://localhost:18081'
$env:KAFKA_SPECIFIC_AVRO_READER='true'

mvn -B spring-boot:run

Por qué latest: el grupo era nuevo y solo debía observar el evento de esta prueba. Usar earliest habría reproducido eventos anteriores cuyos ficheros temporales ya no existían, mezclando ruido histórico con el experimento actual.

03

El contrato que cruza Kafka

La key no es decorativa. uniqueId termina como clave primaria de processed_file_event, de modo que reenviar el mismo evento no duplica el CSV. El value contiene el tipo y una ruta que debe ser accesible desde el proceso consumidor.

{
  "uniqueId": "local-load-5000-logs-20260912"
}
|
{
  "fileType": "STATS_PLAYER",
  "filePath": "C:\\Develop\\csv-stats-player-consumer\\local-test-output\\stats-player-5000.csv"
}

La publicación se realizó con KafkaAvroSerializer y los tipos Java generados desde FileEventKey.avsc y FileEventValue.avsc. Esto importa: enviar JSON plano a un listener configurado con KafkaAvroDeserializer no prueba el mismo contrato.

04

La primera fila reveló el fallo

Antes de generar 5.000 registros, ejecuté una prueba mínima con un solo jugador. Kafka entregó el mensaje y el servicio informó de una inserción correcta. La tabla de idempotencia también contenía el evento. Una comprobación SQL de contenido contó otra historia:

 id | name | team | pts | reb | ast
----+------+------+-----+-----+-----
  1 |      |      |     |     |
(1 row)
El sistema no había perdido el mensaje; había perdido el estado durante el mapeo. Esa diferencia dirige el diagnóstico. Kafka, Avro, el parser, la transacción y PostgreSQL estaban activos. El punto sospechoso era la conversión StatsPlayerDTO → StatsPlayer.

El fichero generado por MapStruct confirmó la causa. El método construía la entidad, pero no copiaba una sola propiedad:

public StatsPlayer toEntity(StatsPlayerDTO dto) {
    if (dto == null) {
        return null;
    }

    StatsPlayer statsPlayer = new StatsPlayer();
    return statsPlayer;
}

Los getters y setters procedían de Lombok. MapStruct ejecutaba su procesador sin la integración que le permite esperar a que Lombok complete el modelo del tipo. Para MapStruct, DTO y entidad parecían objetos sin propiedades.

05

Cómo podían pasar 19 tests

La suite comprobaba el parser, el listener, la transacción, el manejo de errores, la configuración Kafka y la entidad. El servicio de importación utilizaba un mapper simulado, por lo que verificaba la coordinación entre colaboradores, no la implementación generada.

Esto no convierte esos tests en inútiles. Cada uno protegía una responsabilidad válida. El hueco era específico: nadie ejercitaba el código que MapStruct generaba durante la compilación. Un mock no puede descubrir que ese código está vacío.

Regla reutilizable: si una herramienta genera código, incluye al menos una prueba sobre el artefacto generado real. Probar únicamente las interfaces que lo rodean protege el diseño, pero no la generación.
06

Corregir el procesado de anotaciones

La corrección añadió lombok-mapstruct-binding al annotationProcessorPaths del compilador Maven. No es una dependencia de runtime: solo coordina los procesadores durante la compilación.

<path>
  <groupId>org.projectlombok</groupId>
  <artifactId>lombok-mapstruct-binding</artifactId>
  <version>0.2.0</version>
</path>

Después de mvn -B clean test, StatsPlayerMapperImpl ya contenía las asignaciones de las 23 propiedades:

statsPlayer.setName(dto.getName());
statsPlayer.setTeam(dto.getTeam());
statsPlayer.setPts(dto.getPts());
statsPlayer.setReb(dto.getReb());
statsPlayer.setAst(dto.getAst());
// ... hasta tfs

También se añadió StatsPlayerMapperTest. El test usa el mapper real, convierte DTO a entidad y vuelve a DTO. Así detecta tanto una generación vacía como una pérdida de datos en cualquiera de las dos direcciones.

07

La prueba con 5.000 filas

Con el defecto corregido, generé un CSV determinista de 5.000 jugadores. Cada fila tenía nombre, equipo y estadísticas numéricas reproducibles. El tamaño fue de 335.476 bytes y el fichero contenía 5.001 líneas: una cabecera y 5.000 registros.

El parser trabaja en bloques de 500. La carga ejercitó diez bloques completos, saveAllAndFlush, limpieza del contexto JPA entre bloques, secuencia de identificadores, batching JDBC e idempotencia del fichero entero.

2026-09-12T15:17:33.194+02:00  INFO ... Mensaje recibido - Key: local-load-5000-logs-20260912, fileType: STATS_PLAYER, filePath: ...stats-player-5000.csv
2026-09-12T15:17:33.194+02:00  INFO ... Procesando archivo STATS_PLAYER...
2026-09-12T15:17:36.716+02:00  INFO ... Guardados 5000 jugadores del evento local-load-5000-logs-20260912

Es salida real abreviada: entre esas líneas, el log completo conserva el SQL generado por Hibernate. El tiempo observado desde la recepción hasta el mensaje final fue de unos 3,5 segundos en este equipo local. No debe interpretarse como benchmark universal; depende del hardware, Docker Desktop, configuración de logging y almacenamiento.

08

La evidencia debe estar en la base de datos

El mensaje «Guardados 5000» demuestra que el método llegó al final, pero no basta para validar contenido. La condición de aceptación combinó recuento, nulos, límites y muestras.

          5000 |               0 |   5102 |  10101

Resultado: el evento Avro fue consumido una vez, los diez chunks se persistieron dentro de la transacción y las 5.000 filas conservaron sus valores. El fallo de mapeo ya no estaba presente.
09

Qué logs conservar en una prueba reproducible

La ejecución exportó por separado el log completo del consumer y los logs de Kafka, Schema Registry, PostgreSQL y ZooKeeper. Separarlos permite investigar una capa sin confundir su reloj, nivel o formato con los de otra.

  • Consumer: arranque, configuración efectiva, asignación de partición, recepción, SQL y confirmación final.
  • Kafka: creación y actividad del topic, coordinación del grupo y estado del broker.
  • Schema Registry: acceso a los sujetos Avro y comunicación con Kafka.
  • PostgreSQL: arranque, conexiones, checkpoints y posibles errores del motor.
  • Informe SQL: evidencia compacta del resultado que no depende de interpretar miles de inserts.

Activar org.hibernate.SQL=DEBUG hizo que el log del consumer superase los 7 MB. Es útil para una investigación puntual, pero demasiado ruido para operación normal. En producción conviene registrar identificador de evento, fichero, filas, duración y resultado, y reservar el SQL detallado para diagnósticos acotados.

10

Lecciones que sobreviven a este proyecto

  1. Valida estado, no actividad. Que haya logs, commits de offset e inserts no demuestra que los datos sean correctos.
  2. Empieza por una fila legible. La carga grande prueba volumen; la fila pequeña hace visible la semántica.
  3. Prueba el código generado. MapStruct, Lombok, Avro y otros generadores introducen comportamiento que los mocks no cubren.
  4. Usa identificadores de evento nuevos. La idempotencia correcta puede convertir una repetición en un no-op y ocultar que realmente no ejecutaste la ruta esperada.
  5. Consulta agregados y muestras. COUNT, nulos, límites y tres filas representativas ofrecen mejor evidencia que abrir 5.000 registros.
  6. Distingue validación de benchmark. Una duración local prueba que el flujo termina; no caracteriza el rendimiento del sistema bajo concurrencia.

La mejor consecuencia de esta prueba no fue confirmar que Kafka funcionaba. Fue descubrir una frontera sin verificar entre dos objetos Java. El entorno end-to-end no sustituyó a los tests unitarios: señaló exactamente qué test unitario faltaba.

Código y corrección reproducible en csv-stats-player-consumer. La versión corregida es la 1.0.23.
