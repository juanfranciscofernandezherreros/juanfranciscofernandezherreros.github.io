Anotaciones estereotipo en Spring

Por qué @Component, @Service, @Repository y @Controller son más que etiquetas, cómo las descubre Spring y cómo explicar la diferencia entre un estereotipo y un bean.

Nivel
Fundamentos
Tema
Spring Core
Objetivo
Entrevista técnica
01

La respuesta de 30 segundos

Los estereotipos de Spring son anotaciones que clasifican componentes de la aplicación y permiten que Spring los descubra durante el component scanning. @Component es el estereotipo genérico. @Service, @Repository y @Controller son estereotipos especializados que comunican la responsabilidad de la clase. Cuando Spring descubre una de estas clases, puede crear una instancia y registrar esa instancia como bean dentro del ApplicationContext.

La distinción clave en entrevista es sencilla: la anotación no es el bean. La anotación marca la clase para su descubrimiento; el objeto que Spring crea y gestiona es el bean.

02

Por qué Spring los llama estereotipos

Un estereotipo describe el papel que desempeña una clase dentro de la aplicación. Dos clases pueden convertirse en beans de Spring y tener responsabilidades completamente distintas. El estereotipo hace visible esa responsabilidad para las personas, las herramientas y, en algunos casos, para el propio framework.

@Component

El estereotipo genérico. Se usa cuando ningún rol más específico describe bien el componente.

@Service

Suele identificar lógica de aplicación o de dominio. Su principal valor es comunicar intención.

@Repository

Identifica componentes de persistencia y participa en el mecanismo de traducción de excepciones de persistencia de Spring.

@Controller

Identifica controladores de Spring MVC que manejan peticiones web y normalmente resuelven vistas o respuestas.

@RestController merece un matiz: está compuesta a partir de @Controller y @ResponseBody. Se usa para controladores cuyos valores de retorno se escriben directamente en el cuerpo de la respuesta HTTP, normalmente como JSON.

03

De la anotación al bean: component scanning

Un estereotipo no ejecuta mágicamente la lógica de negocio. Su primer efecto práctico es convertir la clase en candidata para el component scanning.

@Service
public class PaymentService {
    public void confirmPayment(Long paymentId) {
        // lógica de negocio
    }
}
Clase anotada→Component scan→BeanDefinition→Objeto creado→Bean gestionado

Spring registra metadatos del componente descubierto como un BeanDefinition. A partir de ahí, el contenedor puede instanciarlo, resolver sus dependencias, aplicar postprocesadores y proxies y gestionar su ciclo de vida.

Relación con Spring Boot: @SpringBootApplication incluye component scanning mediante @ComponentScan. Por defecto, el escaneo parte del paquete donde está la clase de aplicación y continúa por sus subpaquetes, por eso la estructura de paquetes importa.

04

La relación entre las anotaciones

Los estereotipos especializados están meta-anotados para que Spring pueda tratarlos como componentes. Un modelo mental útil es:

@Component
├── @Service
├── @Repository
└── @Controller
    └── @RestController  // conceptualmente: @Controller + @ResponseBody

Este diagrama es conceptual, no representa herencia de Java. Las anotaciones se componen mediante meta-anotaciones. Ese matiz es importante en una entrevista porque decir que @Service "extiende" @Component no es técnicamente preciso.

05

@Component vs @Service: ¿cambia el comportamiento?

Para un component scanning normal, ambas pueden terminar registrando un bean gestionado por Spring. Esto funciona:

@Component
public class PaymentService {
    // ...
}

Pero esto comunica mejor la intención:

@Service
public class PaymentService {
    // ...
}

La elección importa porque la arquitectura también es comunicación. Un lector debería poder mirar la anotación y entender si la clase pertenece a infraestructura, lógica de negocio, persistencia o al límite HTTP.

No exageres la diferencia: @Service no hace automáticamente que un método sea transaccional, thread-safe o asíncrono. Esos comportamientos requieren mecanismos separados como @Transactional, proxies o un diseño explícito de concurrencia.

06

Por qué @Repository es más que documentación

@Repository comunica que la clase pertenece a la capa de persistencia, pero también puede participar en la traducción de excepciones. Spring puede transformar excepciones de persistencia soportadas en su jerarquía consistente de DataAccessException.

@Repository
public class JdbcOrderRepository {
    // operaciones de persistencia
}

La consecuencia arquitectónica útil es que las capas superiores pueden depender de una abstracción de excepciones de persistencia de Spring en lugar de quedar acopladas directamente a los tipos de excepción de una tecnología concreta.

La traducción exacta depende de la infraestructura de persistencia y del postprocesado configurados. En un stack típico de datos con Spring Boot gran parte de este wiring se configura automáticamente, pero no conviene describir el estereotipo como un try/catch universal.

07

Estereotipo no es lo mismo que Bean

Esta es una de las mejores preguntas de seguimiento en una entrevista.

@Service
public class InvoiceService {
}

InvoiceService es una clase marcada con un estereotipo. Si component scanning la descubre, Spring registra su definición y normalmente crea una instancia gestionada. Esa instancia es el bean.

También podemos crear un bean sin utilizar ningún estereotipo:

@Configuration
public class AppConfig {
    @Bean
    public ObjectMapper objectMapper() {
        return new ObjectMapper();
    }
}

ObjectMapper se convierte en bean aunque la clase ObjectMapper no esté anotada con @Component ni @Service en nuestra aplicación. Esta es una de las razones por las que @Bean es útil para tipos de terceros o cuando la construcción necesita configuración explícita.

Para entender qué ocurre después del registro, continúa con Spring Beans en profundidad.

08

Preguntas de seguimiento habituales

¿Es obligatorio @Service?

No. Una clase de servicio podría registrarse con @Component o explícitamente con @Bean. @Service comunica mejor su responsabilidad.

¿Qué añade @RestController?

Combina la semántica de controlador con @ResponseBody, de modo que los valores de retorno se escriben en el cuerpo de la respuesta por defecto.

¿Puede el scanning ignorar un estereotipo?

Sí. Si la clase está fuera de los paquetes configurados para escaneo, no será descubierta solo por tener @Service u otro estereotipo.

¿Puedo crear mi propio estereotipo?

Sí. Spring soporta anotaciones compuestas, por lo que una anotación propia puede estar meta-anotada con @Component y otras anotaciones.

09

Una respuesta sólida de entrevista

“Los estereotipos de Spring son anotaciones que se usan para clasificar componentes de la aplicación y hacerlos candidatos para component scanning. @Component es el estereotipo genérico, mientras que @Service, @Repository y @Controller expresan responsabilidades más concretas. Cuando Spring descubre una de estas clases, registra sus metadatos y puede crear un bean gestionado dentro del ApplicationContext. El estereotipo no es el bean: marca la clase para su descubrimiento. También diferencio @Repository porque puede participar en la traducción de excepciones de persistencia, y @RestController porque combina comportamiento de controlador con @ResponseBody. Además, los beans no tienen que venir de estereotipos; también pueden declararse explícitamente con @Bean.”

Esta respuesta funciona porque cubre definición, mecanismo, diferencias semánticas, un matiz específico del framework y la relación con los beans sin afirmar que todos los estereotipos cambian el comportamiento en runtime.

10

Qué debes recordar

  • Un estereotipo clasifica un componente; un bean es el objeto gestionado.
  • @Component es genérico; los estereotipos especializados comunican intención arquitectónica.
  • Component scanning conecta los estereotipos con el registro automático de beans.
  • @Repository tiene semántica específica de persistencia además del nombre.
  • @RestController es un estereotipo web compuesto con semántica de response body.
  • @Bean es un mecanismo alternativo de registro y no requiere anotar la clase objetivo.
