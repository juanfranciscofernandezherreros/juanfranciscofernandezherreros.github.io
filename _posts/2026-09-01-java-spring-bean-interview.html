01

What exactly is a Spring Bean?

A Spring Bean is an object registered with and managed by the Spring IoC container. The container stores its definition, decides when to create it, resolves its dependencies, applies post-processors and proxies, controls its scope, and invokes lifecycle callbacks.

The container is normally exposed through an ApplicationContext. Internally, Spring works with metadata called BeanDefinition, which describes the bean type, name, scope, lazy-initialization policy, and dependencies.

BeanDefinition→Creation→Injection→Post-processing→Bean ready

Do not confuse a Spring Bean with a JavaBean. JavaBean is a class convention. A Spring Bean is defined by container management, not by getters, setters, or a no-argument constructor.

02

How a Spring Bean is registered

Spring can discover application classes through component scanning. @Component is the general stereotype; @Service, @Repository, and @Controller communicate more specific responsibilities.

@Service
public class EmailService {
    public void send(String message) {
        System.out.println(message);
    }
}

You can also declare a bean explicitly with @Bean inside a @Configuration class. This is especially useful for third-party classes you cannot annotate.

@Configuration
public class AppConfig {
    @Bean
    public ObjectMapper objectMapper() {
        return new ObjectMapper();
    }
}

The default bean name is objectMapper, matching the configuration method. You can override it with @Bean("apiObjectMapper"). With component scanning, the default name is derived from the component type.

Spring Boot auto-configuration

Starters may also register beans according to available classes, configuration properties, and beans already present in the context. Auto-configuration commonly combines conditions such as @ConditionalOnClass, @ConditionalOnProperty, and @ConditionalOnMissingBean.

@Bean
@ConditionalOnMissingBean
public PaymentClient paymentClient(PaymentProperties properties) {
    return new HttpPaymentClient(properties.baseUrl());
}

If the application provides its own PaymentClient, the condition prevents the default one from being registered. That is how many Spring Boot integrations remain customizable without modifying the library.

03

Dependency resolution and injection

Constructor injection makes dependencies explicit, allows fields to remain final, and keeps unit tests simple. With a single constructor, Spring does not require @Autowired.

@RestController
public class UserController {
    private final EmailService emailService;

    public UserController(EmailService emailService) {
        this.emailService = emailService;
    }
}
Spring scans configuration→Creates beans→Resolves dependencies→Injects ready objects

Resolution is primarily type-based. If no candidate exists, Spring commonly reports NoSuchBeanDefinitionException. If several candidates match and Spring cannot choose, it reports NoUniqueBeanDefinitionException.

Several beans with the same type

public interface NotificationSender {
    void send(String message);
}

@Component("emailSender")
class EmailSender implements NotificationSender { /* ... */ }

@Component("smsSender")
class SmsSender implements NotificationSender { /* ... */ }

@Service
class AlertService {
    private final NotificationSender sender;

    AlertService(@Qualifier("smsSender") NotificationSender sender) {
        this.sender = sender;
    }
}

@Qualifier selects a specific candidate. @Primary identifies the preferred candidate when there is no qualifier. You can also inject all implementations as a List<NotificationSender> or Map<String, NotificationSender>.

04

The bean lifecycle

  1. Spring reads configuration and registers bean definitions.
  2. BeanFactoryPostProcessor implementations may modify those definitions.
  3. Spring instantiates the bean and resolves its dependencies.
  4. It invokes Aware callbacks when the bean implements them.
  5. BeanPostProcessor implementations run before initialization.
  6. @PostConstruct, afterPropertiesSet(), or a configured initMethod runs.
  7. Post-processors run after initialization and may return a proxy instead of the original instance.
  8. When the context closes, @PreDestroy, destroy(), or a configured destroyMethod may run.
@Component
public class ExchangeRateCache {
    @PostConstruct
    void loadRates() {
        // Dependencies are already injected here.
    }

    @PreDestroy
    void clearResources() {
        // Release owned resources here.
    }
}

Operational trade-off: avoid fragile or expensive remote work in @PostConstruct. A failure prevents the bean from being created and may stop the entire application from starting.

05

Scopes and instance lifetime

singleton

One instance per bean definition and ApplicationContext. It is the default scope, but it does not mean one instance in the entire JVM.

prototype

A new instance for each request to the container. Spring initializes it, but does not automatically manage its destruction.

request

One instance per HTTP request. It is available only in a web-aware context.

session

One instance per HTTP session. This requires extra care in distributed applications.

@Component
@Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
public class ReportJob { /* ... */ }

The prototype-inside-singleton trap

If you inject a prototype directly into a singleton, dependency resolution happens once when the singleton is created. If you need a new instance for every operation, request it lazily through ObjectProvider.

@Service
public class ReportService {
    private final ObjectProvider<ReportJob> jobs;

    public ReportService(ObjectProvider<ReportJob> jobs) {
        this.jobs = jobs;
    }

    public void generate() {
        ReportJob job = jobs.getObject();
        // A new instance for this operation.
    }
}
06

Proxies and behavior added by Spring

Spring may return a proxy instead of the original instance so it can apply cross-cutting behavior. This powers features such as @Transactional, @Async, caching, security, and custom aspects.

@Service
public class PaymentService {
    @Transactional
    public void confirmPayment(Long paymentId) {
        // The proxy opens a transaction before entering
        // and commits or rolls it back afterwards.
    }
}

A call from another bean goes through the proxy. An internal call such as this.confirmPayment() does not, which is why self-invocation can make @Transactional or @Async appear to do nothing.

A common design fix is to move the intercepted operation into another bean with a clear responsibility instead of relying on self-invocation.

07

Singleton does not mean thread-safe

A singleton bean can receive concurrent calls from many requests. Spring does not synchronize its methods or protect mutable fields. The safest default for service beans is to keep them stateless.

@Service
public class UnsafeCounterService {
    private int counter = 0;

    public int next() {
        return ++counter; // Race condition.
    }
}

Business state normally belongs in a database, a concurrency-safe cache, or another system that provides the guarantees your workload requires.

08

Testing a bean

Constructor injection lets you test bean logic without starting Spring. Mockito can provide collaborators and keep the test fast.

@ExtendWith(MockitoExtension.class)
class TransferServiceTest {
    @Mock AccountRepository repository;
    @Mock AuditPublisher publisher;
    @InjectMocks TransferService service;

    @Test
    void publishesAuditAfterTransfer() {
        service.transfer(/* data */);
        verify(publisher).publish(any());
    }
}

Use @SpringBootTest when the thing you need to verify is the wiring, auto-configuration, proxying, or collaboration between multiple beans. For narrower concerns, slices such as @WebMvcTest and @DataJpaTest are usually cheaper.

09

Common failures and what they tell you

NoSuchBeanDefinitionException

No candidate exists. Check component scanning, profiles, conditions, configuration imports, and whether the expected bean was actually registered.

NoUniqueBeanDefinitionException

Several candidates match. Use @Qualifier, @Primary, or inject the full collection intentionally.

BeanCurrentlyInCreationException

This often points to a circular dependency. The durable fix is usually to separate responsibilities rather than hiding the cycle with @Lazy.

BeanCreationException

Construction or initialization failed. The actionable cause is often near the bottom of the exception chain, not in the first line.

10

Technical summary and interview answer

A Spring Bean is an object whose definition is registered in the IoC container. Spring controls its creation, resolves and injects dependencies, applies post-processors and proxies, determines its scope, and runs lifecycle callbacks. Beans may come from component scanning, explicit @Bean methods, or auto-configuration. The default scope is singleton within an ApplicationContext, which does not imply thread safety.

In real applications, prefer constructor injection, keep singleton services free of unprotected mutable state, resolve ambiguity explicitly, understand when a proxy is involved, and start the full Spring context in tests only when the context itself is part of what you need to verify.
