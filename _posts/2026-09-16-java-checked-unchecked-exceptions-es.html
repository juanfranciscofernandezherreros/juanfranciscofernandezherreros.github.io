Checked vs Unchecked Exceptions

La diferencia se memoriza rápido. Lo importante es saber qué significa una excepción para quien llama al método, en qué capa debe vivir y si obligar a manejarla en compilación mejora el contrato o simplemente añade ruido.

00

La respuesta de entrevista

Una checked exception debe capturarse o declararse con throws; una unchecked exception no tiene esa obligación en tiempo de compilación. Las checked son subclases de Exception excepto RuntimeException. RuntimeException, Error y sus subclases son unchecked.

La respuesta es correcta, pero una conversación de nivel senior empieza con la siguiente pregunta: ¿por qué elegirías una u otra?

01

La jerarquía

Throwable
├── Error                         // unchecked
│   └── OutOfMemoryError
└── Exception
    ├── IOException               // checked
    │   └── FileNotFoundException
    ├── SQLException              // checked
    └── RuntimeException          // unchecked
        ├── NullPointerException
        ├── IllegalArgumentException
        └── IllegalStateException

La clave está en la herencia, no en que escribamos o no una cláusula throws. Declarar una RuntimeException con throws no la convierte en checked.

02

Checked exceptions

El compilador de Java aplica la regla catch or specify a las checked exceptions. Si un método puede producir una, el código que lo llama debe manejarla o propagarla.

public String readConfig(Path path) throws IOException {
    return Files.readString(path);
}

try {
    String config = readConfig(Path.of("app.conf"));
} catch (IOException ex) {
    // recuperar, traducir, reintentar o informar del fallo
}

Una checked exception hace visible el fallo en el contrato del método. Esto puede ser valioso cuando quien llama puede reaccionar razonablemente ante esa situación.

Buen encaje

Una condición recuperable que el caller debería considerar conscientemente: no se puede leer un fichero, falta un recurso externo necesario o existe un camino alternativo.

Coste

Cada capa intermedia debe capturarla o declararla, lo que puede llenar las firmas de ruido cuando esas capas no pueden hacer nada útil.

03

Unchecked exceptions

Las unchecked exceptions no están obligadas por el compilador. Un método puede lanzar una RuntimeException sin declararla.

public Order findOrder(UUID id) {
    return repository.findById(id)
        .orElseThrow(() -> new OrderNotFoundException(id));
}

public final class OrderNotFoundException extends RuntimeException {
    public OrderNotFoundException(UUID id) {
        super("Order " + id + " was not found");
    }
}

Esto no significa que las unchecked deban ser invisibles o no documentarse. Significa que Java no obliga a cada caller a introducir código de manejo.

Uso habitual: errores de programación, precondiciones incumplidas, estados inválidos y fallos de aplicación o dominio para los que las capas intermedias no tienen una estrategia útil de recuperación.

05

¿Capturar, propagar o traducir?

La decisión importante muchas veces no es checked frente a unchecked, sino qué capa tiene suficiente contexto para actuar.

public Invoice loadInvoice(UUID id) {
    try {
        return externalClient.fetch(id);
    } catch (IOException ex) {
        throw new InvoiceProviderException(
            "Could not load invoice " + id,
            ex
        );
    }
}

Aquí la aplicación traduce un fallo específico de infraestructura a una excepción que tiene sentido dentro de su propia abstracción y conserva la causa original.

No captures una excepción únicamente para escribir un log y volver a lanzarla en cada capa. Captura cuando puedas recuperar, añadir contexto útil, traducir abstracciones o realizar limpieza necesaria.

06

Excepciones propias

Extender Exception crea una checked exception:

public class PaymentRejectedException extends Exception {
    public PaymentRejectedException(String message) {
        super(message);
    }
}

Extender RuntimeException crea una unchecked exception:

public class InvalidOrderStateException extends RuntimeException {
    public InvalidOrderStateException(String message) {
        super(message);
    }
}

La elección debe depender del contrato que quieres ofrecer, no de qué versión te obliga a escribir menos líneas.

07

¿Y en Spring?

En aplicaciones Spring modernas es habitual utilizar excepciones unchecked de aplicación o dominio y traducirlas en los límites, por ejemplo con @RestControllerAdvice. Así controladores y servicios no arrastran checked exceptions por todas las firmas cuando esas capas no pueden recuperarse.

@ExceptionHandler(OrderNotFoundException.class)
ProblemDetail handleNotFound(OrderNotFoundException ex) {
    return ProblemDetail.forStatusAndDetail(
        HttpStatus.NOT_FOUND,
        ex.getMessage()
    );
}

También conviene recordar la semántica transaccional de Spring: por defecto, las runtime exceptions y los errors provocan rollback, mientras que las checked exceptions no lo hacen salvo que se configuren reglas de rollback. Ese comportamiento del framework es distinto de la clasificación de Java, pero importa al diseñar excepciones de la capa de servicio.

08

Errores frecuentes

Catch Exception

Los catches demasiado amplios ocultan el modelo de fallos y pueden tragarse problemas que realmente no sabes manejar.

Catch vacío

Ignorar un fallo dificulta el diagnóstico y puede dejar la aplicación en un estado inválido.

throws Exception

Destruye información útil del contrato. Prefiere el tipo significativo más específico.

RuntimeException para todo

Unchecked no es un atajo para evitar diseñar. Las excepciones deben seguir expresando una semántica de fallo útil.

// Mal
try {
    process();
} catch (Exception ex) {
    // ignorado
}
09

Una regla de decisión que escala

Pregúntate si se puede esperar razonablemente que quien llama se recupere de esa condición. Si recuperarse forma parte de su responsabilidad normal, una checked exception puede hacer explícito el contrato. Si el fallo representa un error de programación, una invariante rota, un estado inválido o algo que los callers intermedios no pueden arreglar, una unchecked suele encajar mejor.

Después añade la arquitectura a la decisión: no filtres SQLException, excepciones de clientes HTTP o errores específicos de un proveedor hacia tu dominio simplemente porque la infraestructura los lance.

10

Preguntas de entrevista

¿Se puede capturar una unchecked exception?

Sí. "Unchecked" solo significa que el compilador no obliga a capturarla o declararla.

¿Puede una unchecked aparecer en una cláusula throws?

Sí, pero no es obligatorio y no cambia su clasificación.

¿Todas las subclases de Exception son checked?

No. RuntimeException y todas sus subclases son unchecked.

¿Error es una checked exception?

No. Error y sus subclases son unchecked y normalmente representan condiciones graves de la JVM o del entorno que el código de aplicación no debería capturar de forma rutinaria.

¿Todo error de negocio recuperable debería ser checked?

No existe una regla universal para todas las arquitecturas. La cuestión es si obligar a todos los callers a reconocer esa condición mejora realmente la API. En muchas aplicaciones Spring, los fallos de dominio son unchecked y se manejan en un límite de la aplicación.

Idea clave: checked frente a unchecked es una distinción de compilación, pero elegir entre ellas es una decisión de diseño de API y arquitectura. Diseña las excepciones pensando en quién puede recuperarse, conserva los límites entre abstracciones y no uses RuntimeException únicamente para silenciar al compilador.
