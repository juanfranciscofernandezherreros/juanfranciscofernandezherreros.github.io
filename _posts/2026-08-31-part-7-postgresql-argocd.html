00

Two repositories, two responsibilities

The source repository builds and tests the Spring Boot image. The gitops-config repository declares what Kubernetes must run: namespace, PostgreSQL, storage, seed SQL, Service, pod, image reference, resources, and JVM flags. Argo CD watches the second repository and reconciles that desired state.

Application source

Controller, JDBC repository, startup validation, Dockerfile, tests, and image build. The OOM variant lives on feature/h2-million-row-oom.

GitOps configuration

Manifests consumed by Argo CD. The deployed experiment is represented by commit 802a284.

This boundary prevents a local kubectl edit from becoming the undocumented truth. Durable changes go to Git; Argo applies and audits them.

01

The Argo CD Application

The Application points to the directory that owns the complete experiment and creates its destination namespace. Automated pruning removes resources deleted from Git, while self-heal corrects drift.

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: godbyemicroservices-postgres-oom
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/juanfranciscofernandezherreros/gitops-config.git
    targetRevision: main
    path: godbyemicroservices-postgres-oom
  destination:
    server: https://kubernetes.default.svc
    namespace: godbyemicroservices-postgres-oom
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true

Argo CD does not build the Java artifact and does not execute application business tests by itself. It applies the declared resources and evaluates their Kubernetes health.

02

Database resource graph

ConfigMap

Contains the idempotent schema and generate_series(1, 1000000) seed used by the final OOM drill.

StatefulSet and PVC

Run postgres:16-alpine and persist PGDATA in a 2Gi volume. The database has a 512Mi container limit, separate from Java's 100Mi limit.

PostgreSQL Service

Provides postgresql:5432 inside the namespace. The application never uses the workstation's forwarded port.

Spring Service and Pod

Expose HTTP port 8080 internally and run exactly one intentionally non-restarting Java pod.

Docker's PostgreSQL entrypoint executes the mounted SQL only when the volume is empty. On every later reconciliation, the PVC remains authoritative. The application's production initializer is disabled and startup validation refuses to proceed when the expected database content is absent.

kubectl get configmap,statefulset,pvc,svc,pod \
  -n godbyemicroservices-postgres-oom

kubectl exec -n godbyemicroservices-postgres-oom postgresql-0 -- \
  psql -U goodbye -d goodbye -c \
  "SELECT COUNT(*), MIN(id), MAX(id) FROM goodbye_record;"
03

Wire Spring Boot to PostgreSQL

Kubernetes injects the datasource settings into the Java container. The hostname is the PostgreSQL Service name, not localhost: inside the application pod, localhost means the application pod itself.

env:
  - name: SPRING_DATASOURCE_URL
    value: jdbc:postgresql://postgresql:5432/goodbye
  - name: SPRING_DATASOURCE_USERNAME
    value: goodbye
  - name: SPRING_DATASOURCE_PASSWORD
    value: goodbye
  - name: APP_DATABASE_INITIALIZE
    value: "false"
  - name: APP_DATABASE_EXPECTED_RECORDS
    value: "1000000"

The repository reads rows with a JDBC fetch size of 1,000, but it still appends every mapped record to one ArrayList. Fetch size bounds batches transferred by the driver; it does not bound the final Java collection. That distinction is what makes the endpoint a realistic materialization failure.

04

Constrain the JVM and exit on OOM

Kubernetes limits total container memory to 100Mi. Inside that boundary, the demo uses an 18Mi heap and explicit ceilings for other JVM areas. ExitOnOutOfMemoryError converts an OOM thrown by the HTTP worker into process termination instead of allowing Tomcat to return 500 while the JVM remains alive.

resources:
  requests:
    memory: 64Mi
  limits:
    memory: 100Mi
env:
  - name: JAVA_TOOL_OPTIONS
    value: >-
      -Xmx18m
      -XX:+ExitOnOutOfMemoryError
      -XX:MaxMetaspaceSize=40m
      -XX:ReservedCodeCacheSize=6m
      -XX:MaxDirectMemorySize=1m
      -Xss256k
      -XX:+UseSerialGC
      -XX:TieredStopAtLevel=1

These extreme values are for a disposable failure drill. Production sizing must be based on measured RSS, concurrency, allocation rate, GC pauses, native memory, and startup headroom.

05

Why this workload is a Pod, not a Deployment

The stated requirement is precise: after the OOM, mark an error and do not restart the pod. A Deployment always creates pods with restartPolicy: Always; changing it to Never is invalid. A Job can also avoid retries with backoffLimit: 0, but an HTTP service is not naturally a batch job.

For this demonstration, Git therefore declares one standalone Pod with restartPolicy: Never. When Java exits, kubelet records the terminal failure and does not restart its container. Because no controller replaces the Pod, Argo can observe the failed resource.

Sync: Synced

The failed Pod still matches the object declared in Git.

Health: Degraded

The desired Pod exists but its process ended in Error.

Restarts: 0

restartPolicy: Never preserves the evidence.

This is excellent for the experiment and unsuitable as a production availability model. A real service normally uses a Deployment and accepts restarts, alerting on OOM events and restart rate instead of deliberately remaining down.

06

Deploy and test the complete path

After the image has been built and made available to the kind cluster, apply the Application. Wait for PostgreSQL, validate its data, wait for the Java pod to become Ready, and only then trigger the request.

kubectl apply -f application-postgres-oom.yaml
kubectl wait --for=condition=Ready pod/postgresql-0 \
  -n godbyemicroservices-postgres-oom --timeout=180s
kubectl wait --for=condition=Ready pod/godbyemicroservices-postgres-oom \
  -n godbyemicroservices-postgres-oom --timeout=180s

# Keep this command running in terminal 1
kubectl port-forward -n godbyemicroservices-postgres-oom \
  svc/godbyemicroservices-postgres-oom 8082:8080

# Trigger the materialization failure from terminal 2
curl.exe http://localhost:8082/godbyemicroservices

The query streams batches from PostgreSQL, maps records, and retains them in ArrayList. When capacity growth requires more than the 18Mi heap, the trace ends around ArrayList.grow in GoodbyeRecordRepository.findAll. PostgreSQL and its PVC remain healthy.

kubectl get pod -n godbyemicroservices-postgres-oom
# godbyemicroservices-postgres-oom   0/1   Error   0
# postgresql-0                       1/1   Running 0

kubectl get application godbyemicroservices-postgres-oom -n argocd
# SYNC STATUS: Synced   HEALTH STATUS: Degraded

kubectl logs -n godbyemicroservices-postgres-oom \
  godbyemicroservices-postgres-oom
07

Read the result correctly

Synced does not mean that the program is running. It means the live manifests equal Git. Degraded carries the operational failure. The earlier attempt returned HTTP 500 but left the JVM alive; adding ExitOnOutOfMemoryError made the process exit, and using a standalone Pod made the terminal error remain visible with zero restarts.

To repeat the disposable drill, delete the failed Pod and let automated self-heal recreate the object from Git. Then wait for Ready and invoke the endpoint again.

kubectl delete pod godbyemicroservices-postgres-oom \
  -n godbyemicroservices-postgres-oom
kubectl wait --for=condition=Ready pod/godbyemicroservices-postgres-oom \
  -n godbyemicroservices-postgres-oom --timeout=180s

The database is not reloaded during this reset. The StatefulSet and PVC remain running, so the one million rows are reused and the next request exercises the same fixture.

08

What to carry into production

Keep data ownership separate

Use migrations and persistent storage; do not generate a large fixture in the application heap.

Alert on health, not sync alone

Monitor pod termination reasons, restarts, readiness, Argo health, and application metrics.

Page large results

Expose bounded pages, streams, or exports instead of returning an unbounded table as one JSON response.

Size from evidence

Load-test representative queries and leave explicit native-memory headroom below the cgroup limit.
