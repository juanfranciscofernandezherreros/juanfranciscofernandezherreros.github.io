Configuración en Spring Boot

La configuración parece sencilla hasta que una propiedad tiene cuatro valores distintos: uno en application.yml, otro en un profile, otro como variable de entorno y otro en la línea de comandos. En una entrevista, entender quién gana y por qué vale más que memorizar dónde escribir una clave.

00

La respuesta corta de entrevista

Spring Boot externaliza la configuración para ejecutar el mismo artefacto en entornos diferentes. Puede leer propiedades desde archivos, variables de entorno, system properties, argumentos de línea de comandos y otras fuentes. Esas fuentes tienen una precedencia definida: las de mayor prioridad pueden sobrescribir valores anteriores. Los profiles activan variantes de configuración, y @ConfigurationProperties permite agrupar y validar configuración tipada.

La idea importante es separar código de configuración de despliegue. Una imagen Docker o un JAR no debería recompilarse porque producción use otro hostname, timeout o tamaño de pool.

01

Externalized Configuration: un artefacto, varios entornos

# application.yml
orders:
  client:
    base-url: https://orders.example
    connect-timeout: 2s
    read-timeout: 5s

El mismo código puede arrancar en local, CI, staging o producción cambiando valores desde fuera. Esto permite promover el mismo binario y reducir diferencias accidentales entre entornos.

Código

Define comportamiento estable y tipos. Se versiona, compila y prueba.

Configuración

Define valores que cambian por despliegue: endpoints, límites, flags, credenciales referenciadas o parámetros operativos.

02

Fuentes de propiedades y precedencia

Spring Boot construye un Environment a partir de múltiples PropertySource. No todas tienen la misma prioridad. Una forma útil de recordarlo es que la configuración externa y explícita suele poder sobrescribir defaults empaquetados.

EjemploUso habitualPrioridad relativa
application.yml dentro del JARDefaultsBase
application-prod.ymlValores de profileSobrescribe base dentro de config data
Archivo externoConfiguración del despliegueMayor que el empaquetado
Variable de entornoContenedores / plataformaMayor que config data
Java system propertyArranque JVMMayor que variables de entorno
--key=valueOverride explícitoMuy alta
# application.yml
server:
  port: 8080

# variable de entorno
SERVER_PORT=9090

# línea de comandos
java -jar app.jar --server.port=7070

Con esas entradas, el argumento de línea de comandos gana y el servidor arranca con 7070.

No memorices una lista sin entender la regla. En producción importa poder diagnosticar de dónde salió un valor. Un override olvidado explica muchas diferencias entre entornos aparentemente iguales.

03

Profiles: activar grupos coherentes de configuración o beans

Un profile representa un contexto lógico como local, test o prod. Spring Boot puede cargar application-prod.yml además del archivo base.

# application.yml
orders:
  client:
    base-url: http://localhost:8081

# application-prod.yml
orders:
  client:
    base-url: https://orders.internal.example
SPRING_PROFILES_ACTIVE=prod
java -jar app.jar

# o
java -jar app.jar --spring.profiles.active=prod

También existe @Profile para registrar beans solo bajo determinados profiles:

@Bean
@Profile("local")
PaymentGateway fakePaymentGateway() {
    return new InMemoryPaymentGateway();
}

Buen uso: diferencias reales de infraestructura o entorno. Mal uso: una explosión de profiles que actúan como feature flags, clientes o combinaciones difíciles de probar.

04

@Value vs @ConfigurationProperties

@Value es cómodo para uno o dos valores aislados:

@Value("${orders.client.base-url}")
private String baseUrl;

Cuando la configuración forma una unidad, @ConfigurationProperties ofrece tipado, agrupación, relaxed binding y validación.

@ConfigurationProperties(prefix = "orders.client")
@Validated
public record OrdersClientProperties(
    @NotNull URI baseUrl,
    @NotNull Duration connectTimeout,
    @NotNull Duration readTimeout,
    @Min(1) int maxRetries
) {}
orders:
  client:
    base-url: https://orders.example
    connect-timeout: 2s
    read-timeout: 5s
    max-retries: 3

Ahora la configuración tiene contrato. Si falta un valor obligatorio o max-retries es inválido, es mejor fallar durante el arranque que descubrirlo bajo tráfico real.

05

Cómo registrar @ConfigurationProperties

Una opción es escanear clases de properties:

@SpringBootApplication
@ConfigurationPropertiesScan
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}

Otra es registrar clases concretas:

@Configuration
@EnableConfigurationProperties(OrdersClientProperties.class)
class OrdersClientConfiguration { }

La clase de properties debería representar datos del entorno. No la conviertas en un service lleno de dependencias y lógica de negocio.

06

Variables de entorno y relaxed binding

En Kubernetes, OpenShift y contenedores es habitual suministrar configuración mediante variables de entorno:

ORDERS_CLIENT_BASE_URL=https://orders.internal
ORDERS_CLIENT_MAX_RETRIES=5

Spring Boot puede enlazarlas con orders.client.base-url y orders.client.max-retries. Esta flexibilidad forma parte de sus convenciones de relaxed binding.

La imagen contiene código; un Deployment, Helm chart, ConfigMap, Secret o la plataforma suministra valores del entorno.

07

Configuración no significa meter secretos en Git

Contraseñas, tokens, claves privadas y credenciales de base de datos no deberían almacenarse en un application-prod.yml versionado. El repositorio puede definir el contrato o placeholders; el secreto debe llegar desde un mecanismo adecuado.

spring:
  datasource:
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}

Un placeholder no protege el secreto si después haces commit del valor real en otro fichero. Gestionar secretos implica almacenamiento, acceso, rotación, auditoría y revocación.

08

spring.config.import y configuración modular

Spring Boot permite importar configuración adicional mediante spring.config.import.

spring:
  config:
    import: "optional:file:./config/orders.yml"

optional: indica que el arranque puede continuar si el recurso no existe. Sin él, una ubicación requerida que falta se considera un error.

También conviene distinguir spring.config.location y spring.config.additional-location: el primero puede reemplazar ubicaciones por defecto; el segundo añade ubicaciones. Se procesan pronto, por lo que deben proporcionarse desde fuentes disponibles antes de cargar el resto de config data.

09

Configuración en tests

Los tests no deberían depender accidentalmente del portátil del desarrollador.

@SpringBootTest(properties = {
    "orders.client.base-url=http://localhost:9999",
    "orders.client.max-retries=1"
})
class OrdersApplicationTest { }

Con Testcontainers, @DynamicPropertySource es útil cuando una propiedad se conoce después de arrancar el contenedor:

@DynamicPropertySource
static void databaseProperties(DynamicPropertyRegistry registry) {
    registry.add("spring.datasource.url", postgres::getJdbcUrl);
    registry.add("spring.datasource.username", postgres::getUsername);
    registry.add("spring.datasource.password", postgres::getPassword);
}

La idea es que el test declare explícitamente el entorno que necesita y no dependa de valores globales invisibles.

10

Errores frecuentes

@Value por todas partes

Dispersa claves como strings y oculta el contrato de configuración de un componente.

Un profile por feature

Produce combinaciones difíciles de probar. Los profiles funcionan mejor para contextos coherentes.

Defaults peligrosos

Una credencial o endpoint crítico no debería caer silenciosamente a un valor de otro entorno.

Secretos en YAML

Versionar secretos los extiende a clones, historial, forks, caches y logs.

No validar configuración

Permite que un error de despliegue sobreviva al arranque y falle más tarde.

No saber quién sobrescribió el valor

Sin precedencia, dos despliegues aparentemente iguales pueden comportarse distinto.

11

Preguntas de entrevista

¿Qué diferencia hay entre application.yml y application-prod.yml?

El primero contiene configuración general; el segundo es una variante considerada cuando prod está activo y puede sobrescribir valores del documento base.

¿Qué gana: YAML o variable de entorno?

En el orden habitual, una variable de entorno tiene mayor precedencia que config data empaquetada.

¿Cuándo usarías @Value?

Para valores aislados. Para grupos estructurados con tipos y validación prefiero @ConfigurationProperties.

¿Qué es relaxed binding?

La capacidad de enlazar variantes de nombres —kebab-case, camelCase o mayúsculas con guiones bajos según la fuente— al mismo modelo.

¿Dónde guardarías secretos?

En el mecanismo de secretos de la plataforma o un secret manager, inyectándolos en runtime; no en Git.

¿Por qué validar configuration properties?

Para convertir un error de despliegue en un fallo temprano y explícito durante el arranque.

12

Cómo lo respondería en una entrevista senior

“Intento que el mismo artefacto sea promovible entre entornos y que las diferencias entren como configuración externa. Uso application.yml para defaults seguros, profiles para variantes coherentes y variables o fuentes externas para valores del despliegue. Para configuración estructurada prefiero @ConfigurationProperties con tipos y validación. Conozco la precedencia porque un override puede explicar diferencias entre entornos. Los secretos no viven en Git y los tests declaran sus propiedades explícitamente. Mi objetivo es fallar pronto ante configuración inválida y poder rastrear de dónde salió cada valor.”

Idea clave: Spring Boot configuration no es solo YAML. Es un sistema de fuentes, precedencia, binding, validación y activación para ejecutar el mismo código de forma predecible en distintos entornos.
