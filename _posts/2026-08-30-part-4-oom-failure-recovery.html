The drill

This is a controlled failure exercise, not a memory-leak pattern to keep in production. The service starts with a component that appends 1MiB byte arrays to a retained list. Kubernetes limits the container to 100Mi, so the pod eventually dies and the controller restarts it.

MemoryOomProbe.java — experimental code
List<byte[]> retainedMemory = new ArrayList<>();
while (true) {
    retainedMemory.add(new byte[1024 * 1024]);
}

Run this only in a disposable local cluster. The list intentionally retains every allocation. Never expose this switch in a production workload.

01

Heap is not container memory

The first surprise was that -Xmx did not fully predict the result. A Java process also consumes metaspace, code cache, thread stacks, direct buffers, GC structures, shared libraries, and JVM native memory. Kubernetes enforces the cgroup total, not just the Java heap.

OOMKilled / 137

The kernel killed the container after total memory crossed 100Mi. Java may have no chance to print a heap exception.

Java OOM / 1

The JVM detected exhaustion inside a managed area and exited with an exception.

Running / 0

Heap and native ceilings leave enough room below the container limit.

That distinction matters during diagnosis. kubectl logs alone may end abruptly for an OOM kill; the authoritative evidence is lastState.terminated.reason and the exit code.

kubectl get pod -n godbyemicroservices -l app=godbyemicroservices \
  -o jsonpath="{.items[0].status.containerStatuses[0].lastState.terminated.reason} {.items[0].status.containerStatuses[0].lastState.terminated.exitCode}{'\n'}"

02

Why Argo can be Synced while the pod is broken

Argo CD answers two separate questions. Sync asks whether the live Kubernetes objects match Git. Health asks whether those objects are operational. A perfectly applied Deployment whose pod keeps crashing can therefore be Synced and Degraded at the same time.

Synced

The Deployment in the cluster matches the YAML stored in Git.

Degraded

The Deployment cannot make its requested replica available.

Operation: Succeeded

Applying valid YAML succeeded, even though the resulting workload later failed.

Adding progressDeadlineSeconds: 30 made Kubernetes report ProgressDeadlineExceeded sooner. That improved health reporting, but it did not retroactively turn a successful manifest apply into a failed sync operation.

03

Making the operation fail on purpose

When the requirement is specifically “show the synchronization operation as Failed,” Argo needs a sync task that can return failure. For the drill, a PreSync Job ran the same image with the same 100Mi limit and backoffLimit: 0.

startup-check.yaml — temporary failure gate
apiVersion: batch/v1
kind: Job
metadata:
  name: godbyemicroservices-startup-check
  annotations:
    argocd.argoproj.io/hook: PreSync
spec:
  backoffLimit: 0
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: startup-check
          image: godbyemicroservices:local
          resources:
            limits:
              memory: 100Mi

The hook pod ended as OOMKilled with exit code 137. The Job reached BackoffLimitExceeded, and Argo recorded operation=Failed with “one or more synchronization tasks completed unsuccessfully.” This proves the distinction: workload health affects Health; a failed sync task affects the operation phase.

04

Recovery: remove the fault, not the limit

Remove the deliberate leak

The local MemoryOomProbe experiment, its test, and the OOM_ON_STARTUP property were deleted before publishing the service. The application starts only Spring and its single GodbyeMicroservicesController.

Remove the experimental gate

The PreSync Job and the short progress deadline were removed from gitops-config. The Deployment remains at replicas: 1.

Keep the 100Mi boundary

The container limit stayed unchanged. The JVM received conservative heap, metaspace, code-cache, direct-memory, stack, GC, and tiered-compilation settings so Spring fits inside the cgroup.

Rebuild and reconcile

The image was rebuilt, loaded into kind, and the pod recreated. Argo reconciled Git commit 4fc7726.

Dockerfile — final JVM command
ENTRYPOINT ["java", "-Xmx36m", "-XX:MaxMetaspaceSize=44m",
  "-XX:ReservedCodeCacheSize=8m", "-XX:MaxDirectMemorySize=4m",
  "-Xss256k", "-XX:+UseSerialGC", "-XX:TieredStopAtLevel=1",
  "-jar", "app.jar"]

These values are specific to this small demonstration service. For a real workload, measure peak RSS, request rate, thread count, GC behavior, and startup headroom before choosing production limits.
