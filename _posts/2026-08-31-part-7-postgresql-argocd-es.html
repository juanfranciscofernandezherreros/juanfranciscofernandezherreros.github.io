PostgreSQL en Argo CD

Reconcilia desde Git la base de datos y Spring Boot, conserva un millón de registros y convierte un OOM de Java durante la petición en un pod fallido visible que no reinicia.

Dos repositorios, dos responsabilidades

El repositorio de código construye y prueba la imagen Spring Boot. El repositorio gitops-config declara lo que Kubernetes debe ejecutar: namespace, PostgreSQL, almacenamiento, SQL inicial, Service, pod, referencia de imagen, recursos y opciones de la JVM. Argo CD observa el segundo repositorio y reconcilia ese estado deseado.

Código de aplicación

Controller, repositorio JDBC, validación inicial, Dockerfile, pruebas y construcción. La variante OOM está en feature/h2-million-row-oom.

Configuración GitOps

Manifiestos consumidos por Argo CD. El experimento desplegado queda representado por el commit 802a284.

Esta frontera impide que un kubectl edit local se convierta en una verdad sin documentar. Los cambios duraderos entran en Git; Argo los aplica y audita.

01

La Application de Argo CD

La Application apunta al directorio dueño del experimento completo y crea su namespace de destino. El borrado automático elimina recursos retirados de Git, mientras que self-heal corrige desviaciones.

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: godbyemicroservices-postgres-oom
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/juanfranciscofernandezherreros/gitops-config.git
    targetRevision: main
    path: godbyemicroservices-postgres-oom
  destination:
    server: https://kubernetes.default.svc
    namespace: godbyemicroservices-postgres-oom
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true

Argo CD no construye el artefacto Java ni ejecuta por sí solo las pruebas funcionales. Aplica recursos declarados y evalúa su salud en Kubernetes.

02

Grafo de recursos de la base de datos

ConfigMap

Contiene el esquema idempotente y la carga generate_series(1, 1000000) de la prueba OOM final.

StatefulSet y PVC

Ejecutan postgres:16-alpine y guardan PGDATA en un volumen de 2Gi. PostgreSQL tiene un límite de 512Mi, separado de los 100Mi de Java.

Service PostgreSQL

Proporciona postgresql:5432 dentro del namespace. La aplicación nunca utiliza el puerto redirigido del equipo.

Service y Pod Spring

Exponen internamente HTTP 8080 y ejecutan exactamente un pod Java que deliberadamente no reinicia.

El entrypoint de PostgreSQL ejecuta el SQL montado únicamente con el volumen vacío. En reconciliaciones posteriores manda el PVC. El inicializador de producción de la aplicación está desactivado y la validación de arranque impide continuar si falta el contenido esperado.

kubectl get configmap,statefulset,pvc,svc,pod \
  -n godbyemicroservices-postgres-oom

kubectl exec -n godbyemicroservices-postgres-oom postgresql-0 -- \
  psql -U goodbye -d goodbye -c \
  "SELECT COUNT(*), MIN(id), MAX(id) FROM goodbye_record;"
03

Conecta Spring Boot con PostgreSQL

Kubernetes inyecta la configuración del datasource en el contenedor Java. El hostname es el nombre del Service PostgreSQL, no localhost: dentro del pod de la aplicación, localhost significa ese mismo pod.

env:
  - name: SPRING_DATASOURCE_URL
    value: jdbc:postgresql://postgresql:5432/goodbye
  - name: SPRING_DATASOURCE_USERNAME
    value: goodbye
  - name: SPRING_DATASOURCE_PASSWORD
    value: goodbye
  - name: APP_DATABASE_INITIALIZE
    value: "false"
  - name: APP_DATABASE_EXPECTED_RECORDS
    value: "1000000"

El repositorio usa un fetch size JDBC de 1.000, pero sigue añadiendo cada registro transformado a un único ArrayList. El fetch size limita los lotes transferidos por el driver; no limita la colección Java final. Esa diferencia convierte el endpoint en un fallo realista de materialización.

04

Limita la JVM y termina ante OOM

Kubernetes limita la memoria total del contenedor a 100Mi. Dentro de esa frontera, la demostración usa 18Mi de heap y límites explícitos para otras áreas. ExitOnOutOfMemoryError convierte el OOM del hilo HTTP en la terminación del proceso, en vez de permitir que Tomcat responda 500 mientras la JVM continúa viva.

resources:
  requests:
    memory: 64Mi
  limits:
    memory: 100Mi
env:
  - name: JAVA_TOOL_OPTIONS
    value: >-
      -Xmx18m
      -XX:+ExitOnOutOfMemoryError
      -XX:MaxMetaspaceSize=40m
      -XX:ReservedCodeCacheSize=6m
      -XX:MaxDirectMemorySize=1m
      -Xss256k
      -XX:+UseSerialGC
      -XX:TieredStopAtLevel=1

Estos valores extremos pertenecen a una prueba desechable. El dimensionamiento de producción debe apoyarse en RSS, concurrencia, ritmo de asignación, pausas GC, memoria nativa y margen de arranque medidos.

05

Por qué es un Pod y no un Deployment

El requisito es exacto: tras el OOM, marcar error y no reiniciar el pod. Un Deployment siempre crea pods con restartPolicy: Always; cambiarlo a Never es inválido. Un Job permite evitar reintentos con backoffLimit: 0, pero un servicio HTTP no es naturalmente un proceso batch.

Para esta demostración, Git declara un Pod independiente con restartPolicy: Never. Cuando Java termina, kubelet registra el fallo y no reinicia el contenedor. Como ningún controlador sustituye el Pod, Argo observa el recurso fallido.

Sync: Synced

El Pod fallido sigue coincidiendo con el objeto declarado en Git.

Health: Degraded

El Pod deseado existe, pero su proceso terminó en Error.

Reinicios: 0

restartPolicy: Never conserva la evidencia.

Es excelente para el experimento y no es un modelo de disponibilidad para producción. Un servicio real suele utilizar Deployment y aceptar reinicios, alertando por eventos OOM y tasa de reinicios en lugar de permanecer caído.

06

Despliega y prueba el recorrido completo

Después de construir la imagen y dejarla disponible en kind, aplica la Application. Espera a PostgreSQL, valida sus datos, espera que Java esté Ready y solo entonces dispara la petición.

kubectl apply -f application-postgres-oom.yaml
kubectl wait --for=condition=Ready pod/postgresql-0 \
  -n godbyemicroservices-postgres-oom --timeout=180s
kubectl wait --for=condition=Ready pod/godbyemicroservices-postgres-oom \
  -n godbyemicroservices-postgres-oom --timeout=180s

# Mantén este comando ejecutándose en la terminal 1
kubectl port-forward -n godbyemicroservices-postgres-oom \
  svc/godbyemicroservices-postgres-oom 8082:8080

# Provoca el fallo de materialización desde la terminal 2
curl.exe http://localhost:8082/godbyemicroservices

La consulta recibe lotes desde PostgreSQL, transforma registros y los retiene en ArrayList. Cuando ampliar su capacidad requiere más de 18Mi, la traza acaba alrededor de ArrayList.grow dentro de GoodbyeRecordRepository.findAll. PostgreSQL y su PVC permanecen sanos.

kubectl get pod -n godbyemicroservices-postgres-oom
# godbyemicroservices-postgres-oom   0/1   Error   0
# postgresql-0                       1/1   Running 0

kubectl get application godbyemicroservices-postgres-oom -n argocd
# SYNC STATUS: Synced   HEALTH STATUS: Degraded

kubectl logs -n godbyemicroservices-postgres-oom \
  godbyemicroservices-postgres-oom
07

Interpreta bien el resultado

Synced no significa que el programa esté ejecutándose. Significa que los manifiestos vivos coinciden con Git. Degraded expresa el fallo operativo. El intento anterior devolvía HTTP 500 pero dejaba viva la JVM; añadir ExitOnOutOfMemoryError hizo terminar el proceso, y el Pod independiente mantuvo visible el error terminal con cero reinicios.

Para repetir el laboratorio, elimina el Pod fallido y deja que self-heal lo recree desde Git. Después espera a Ready y vuelve a invocar el endpoint.

kubectl delete pod godbyemicroservices-postgres-oom \
  -n godbyemicroservices-postgres-oom
kubectl wait --for=condition=Ready pod/godbyemicroservices-postgres-oom \
  -n godbyemicroservices-postgres-oom --timeout=180s

La base de datos no se recarga durante este reinicio. El StatefulSet y el PVC siguen activos, por lo que el millón de filas se reutiliza en la siguiente petición.

08

Qué trasladar a producción

Separa la propiedad de los datos

Usa migraciones y almacenamiento persistente; no generes un fixture grande en el heap.

Alerta por salud, no solo por sync

Monitoriza terminaciones, reinicios, readiness, salud de Argo y métricas de aplicación.

Pagina resultados grandes

Ofrece páginas, streams o exportaciones acotadas, no una tabla ilimitada en una respuesta JSON.

Dimensiona con evidencia

Prueba consultas representativas y deja margen explícito para memoria nativa bajo el límite del cgroup.
