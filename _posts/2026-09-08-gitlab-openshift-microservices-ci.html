Microservices Delivery Notes

Continuous integration with GitLab and OpenShift

How a source-code change becomes a tested, traceable container image that OpenShift can run safely.

Level
Intermediate
Topic
CI/CD
Context
Microservices
01

The essential idea

Continuous integration validates every change to a microservice automatically. A push or merge request starts a GitLab pipeline that compiles the application, runs tests and quality checks, builds a container image, and publishes an immutable version to a registry. OpenShift runs that version and provides deployment, networking, health checks, scaling, and recovery.

GitLab CI and OpenShift solve different parts of the delivery process. GitLab decides whether a change is fit to become a release artifact. OpenShift operates that artifact. Keeping this boundary clear makes failures easier to locate and releases easier to audit.

02

End-to-end architecture

Git push→GitLab pipeline→Tests and analysis→Container image→Registry→OpenShift

GitLab

Stores code, reviews merge requests, runs pipelines, keeps evidence, and controls which changes can be merged.

GitLab Runner

Executes each job in an isolated environment with the permissions and tools required by that stage.

Image registry

Stores immutable images identified by a commit SHA or release version instead of a mutable label such as latest.

OpenShift

Pulls the approved image and manages pods, services, routes, configuration, secrets, probes, and rollout status.

03

A pipeline for one microservice

Each microservice should produce and validate its own artifact. For a Java service, a simplified .gitlab-ci.yml can describe three stages:

stages:
  - test
  - image
  - deploy

variables:
  IMAGE_TAG: "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA"

test:
  stage: test
  script:
    - ./mvnw verify

build-image:
  stage: image
  script:
    - printf '%s' "$CI_REGISTRY_PASSWORD" | podman login -u "$CI_REGISTRY_USER" --password-stdin "$CI_REGISTRY"
    - podman build -t "$IMAGE_TAG" .
    - podman push "$IMAGE_TAG"

deploy-development:
  stage: deploy
  script:
    - oc set image deployment/orders-service orders-service="$IMAGE_TAG"
    - oc rollout status deployment/orders-service --timeout=180s
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'

The example shows the responsibility chain, not a universal production template. Runner type, image builder, credentials, approval rules, and deployment strategy depend on the platform and security model.

Traceability: tagging an image with CI_COMMIT_SHA connects the running container to the exact source revision and pipeline that produced it.

04

What should be validated?

  • Compilation and unit tests: verify local behavior quickly.
  • Integration tests: exercise databases, brokers, or other real dependencies in controlled environments.
  • Contract tests: detect incompatible API or event changes before consumers fail.
  • Static and dependency analysis: identify quality issues and known vulnerable libraries.
  • Image scanning: inspect the operating-system and runtime packages included in the image.
  • Deployment verification: wait for readiness and run a small smoke test against the deployed service.

A green build is not enough: if the pipeline publishes an image without testing its contracts or checking whether the rollout becomes ready, important failures move from integration time to runtime.

05

What OpenShift contributes

The pipeline delivers an image; OpenShift turns it into a running workload. A Deployment declares the image and replicas, a Service provides stable internal discovery, and a Route can expose the service externally. ConfigMaps and Secrets separate environment configuration from the image.

Readiness probes prevent traffic from reaching a pod before it can serve requests. Liveness probes can restart a stuck container, while startup probes protect applications that legitimately need more initialization time. Resource requests and limits help the scheduler place pods and contain failures.

During a rolling update, OpenShift starts new pods and removes old ones progressively. The pipeline should inspect rollout status and fail visibly if the new version never becomes ready.

06

Why microservices change the pipeline

Independent deployment is one of the main benefits of microservices. A change to orders-service should not require rebuilding unrelated services. Each service therefore needs a clear ownership boundary, its own versioned image, and checks appropriate to its dependencies.

Independent artifact

Build once and promote the same immutable image through environments; do not rebuild it differently for production.

Compatible contracts

Evolve APIs and events without breaking consumers that may be deployed at a different time.

Observable release

Correlate logs, metrics, traces, image version, commit, and pipeline so a regression can be diagnosed quickly.

Controlled configuration

Keep environment-specific URLs and credentials outside the image, with secrets never written into the repository.

07

CI, delivery, and deployment

  • Continuous integration: every change is compiled, tested, and integrated frequently.
  • Continuous delivery: every accepted change leaves a releasable artifact ready for an authorized deployment.
  • Continuous deployment: every accepted change is deployed automatically without a manual release decision.

For development, GitLab may update OpenShift directly with oc. For controlled environments, a GitOps model is often clearer: the pipeline publishes the image and updates a deployment repository; a controller such as Argo CD reconciles that declared state with OpenShift. Git then records who requested the version change and makes rollback a versioned operation.

08

Security and operating rules

Use a dedicated service account with the minimum permissions required by the job. Store credentials as protected CI variables or retrieve them from a secret manager. Protect production environments, require appropriate approvals, scan dependencies and images, and avoid printing tokens in job logs.

Promotion should reference an existing image digest or immutable tag. Rebuilding the same commit for each environment weakens confidence because production would receive different bytes from those tested earlier.

09

The interview answer

“A change to a microservice starts a GitLab CI pipeline. The pipeline compiles the code, runs unit, integration, contract, quality, and security checks, then creates one immutable container image and publishes it with a traceable version. OpenShift runs that image and manages configuration, networking, probes, replicas, and rolling updates. Each microservice has an independent pipeline and artifact, while compatible contracts protect communication between services. Deployment can be performed directly from GitLab or, preferably for controlled environments, through a GitOps repository reconciled by a controller.”

A good explanation follows one commit from source to a verified workload and clearly separates artifact creation from runtime operation.
