Spring stereotype annotations

Why @Component, @Service, @Repository, and @Controller are more than labels, how Spring discovers them, and how to explain the difference between a stereotype and a bean.

Level
Foundations
Topic
Spring Core
Goal
Technical interview
01

The 30-second answer

Spring stereotypes are annotations that classify application components and allow Spring to discover them during component scanning. @Component is the generic stereotype. @Service, @Repository, and @Controller are specialized stereotypes that communicate the responsibility of the class. When Spring discovers one of these classes, it can create an instance and register that instance as a bean in the ApplicationContext.

The key interview distinction is simple: the annotation is not the bean. The annotation marks the class for discovery; the object that Spring creates and manages is the bean.

02

Why Spring calls them stereotypes

A stereotype describes the role a class plays in the application. Two classes can both become Spring beans while having very different responsibilities. The stereotype makes that responsibility visible to humans, tooling, and in some cases the framework itself.

@Component

The generic stereotype. Use it when no more specific role describes the component.

@Service

Usually identifies application or domain-service logic. Its main value is semantic clarity.

@Repository

Identifies persistence components and participates in Spring's persistence-exception translation mechanism.

@Controller

Identifies Spring MVC controllers that handle web requests and normally resolve views or responses.

@RestController deserves a nuance: it is composed from @Controller and @ResponseBody. It is used for controllers whose handler return values are written to the HTTP response body, commonly as JSON.

03

From annotation to bean: component scanning

A stereotype does not magically execute business logic. Its first practical effect is to make a class a candidate for component scanning.

@Service
public class PaymentService {
    public void confirmPayment(Long paymentId) {
        // business logic
    }
}
Annotated class→Component scan→BeanDefinition→Object created→Managed bean

Spring registers metadata for the discovered component as a BeanDefinition. The container can then instantiate it, resolve its dependencies, apply post-processors and proxies, and manage its lifecycle.

Spring Boot connection: @SpringBootApplication includes component scanning through @ComponentScan. By default, scanning starts from the package containing the application class and its subpackages, which is why package structure matters.

04

The annotation relationship

The specialized stereotypes are themselves meta-annotated so Spring can treat them as components. A useful mental model is:

@Component
├── @Service
├── @Repository
└── @Controller
    └── @RestController  // conceptually: @Controller + @ResponseBody

This diagram is a conceptual view, not Java inheritance. Annotations are composed through meta-annotations. That distinction is worth making in an interview because saying that @Service "extends" @Component is technically inaccurate.

05

@Component vs @Service: does it change runtime behavior?

For ordinary component scanning, both can result in a managed Spring bean. This works:

@Component
public class PaymentService {
    // ...
}

But this communicates intent better:

@Service
public class PaymentService {
    // ...
}

The choice matters because architecture is also communication. A reader should be able to look at the annotation and understand whether the class is infrastructure, business logic, persistence, or an HTTP boundary.

Do not overstate the difference: @Service does not automatically make a method transactional, thread-safe, or asynchronous. Those behaviors require separate mechanisms such as @Transactional, proxies, or explicit concurrency design.

06

Why @Repository is more than documentation

@Repository communicates that the class belongs to the persistence boundary, but it can also participate in exception translation. Spring can translate supported persistence exceptions into its consistent DataAccessException hierarchy.

@Repository
public class JdbcOrderRepository {
    // persistence operations
}

The useful architectural consequence is that higher layers can depend on Spring's persistence exception abstraction instead of being tightly coupled to a particular database technology's exception types.

The exact translation depends on the configured persistence infrastructure and post-processing. In a typical Spring Boot data stack much of this wiring is configured automatically, but the stereotype itself should not be described as a universal try/catch mechanism.

07

Stereotype is not the same as Bean

This is one of the strongest follow-up questions in an interview.

@Service
public class InvoiceService {
}

InvoiceService is a class marked with a stereotype. If component scanning discovers it, Spring registers its definition and normally creates a managed instance. That instance is the bean.

You can also create a bean without any stereotype annotation:

@Configuration
public class AppConfig {
    @Bean
    public ObjectMapper objectMapper() {
        return new ObjectMapper();
    }
}

ObjectMapper becomes a bean even though the ObjectMapper class is not annotated with your application's @Component or @Service. This is one reason @Bean is useful for third-party types or when construction requires explicit configuration.

For a deeper explanation of what happens after registration, continue with Spring Beans in depth.

08

Common interview follow-ups

Is @Service required?

No. A service class could be registered with @Component or explicitly with @Bean. @Service communicates the role more clearly.

What does @RestController add?

It combines controller semantics with @ResponseBody, so handler return values are written to the response body by default.

Can scanning miss a stereotype?

Yes. If the class is outside the configured scan packages, it will not be discovered just because it has @Service or another stereotype.

Can I create my own stereotype?

Yes. Spring supports composed annotations, so a custom annotation can itself be meta-annotated with @Component and other annotations.

09

A strong interview answer

“Spring stereotypes are annotations used to classify application components and make them candidates for component scanning. @Component is the generic stereotype, while @Service, @Repository, and @Controller express more specific responsibilities. When Spring discovers one of these classes, it registers metadata for it and can create a managed bean in the ApplicationContext. The stereotype itself is not the bean: it marks the class for discovery. I also distinguish @Repository because it can participate in persistence exception translation, and @RestController because it combines controller behavior with @ResponseBody. Beans do not have to come from stereotypes; they can also be declared explicitly with @Bean.”

That answer works because it covers the definition, the mechanism, the semantic differences, one framework-specific nuance, and the relationship with beans without claiming that every stereotype changes runtime behavior.

10

What to remember

  • A stereotype classifies a component; a bean is the managed object.
  • @Component is generic; specialized stereotypes communicate architectural intent.
  • Component scanning is what connects stereotypes to automatic bean registration.
  • @Repository has persistence-specific semantics beyond naming.
  • @RestController is a composed web stereotype with response-body semantics.
  • @Bean is an alternative registration mechanism and does not require annotating the target class.
