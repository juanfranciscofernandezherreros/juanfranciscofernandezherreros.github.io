Spring Security en entrevistas

En una entrevista no basta con saber escribir una SecurityFilterChain. Lo que diferencia una respuesta sólida es poder explicar qué ocurre desde que llega una petición hasta que Spring decide quién eres, qué permisos tienes y si puede continuar hacia el controlador.

00

La respuesta corta de entrevista

Spring Security protege aplicaciones principalmente mediante una cadena de filtros Servlet. Esos filtros extraen credenciales, autentican al usuario, guardan el resultado en un SecurityContext y posteriormente autorizan la petición según rutas, roles, authorities o reglas de método. Autenticación responde “¿quién eres?” y autorización responde “¿puedes hacer esto?”.

Esta explicación abre casi todas las preguntas posteriores: dónde vive el usuario autenticado, quién valida una contraseña o un JWT, por qué un endpoint devuelve 401 o 403 y por qué desactivar CSRF sin entender el tipo de cliente puede introducir una vulnerabilidad.

01

El modelo mental: una cadena de filtros antes del controller

En una aplicación Servlet, la petición no entra directamente en el DispatcherServlet. Spring Security integra un FilterChainProxy que selecciona una SecurityFilterChain y ejecuta los filtros aplicables.

Cliente
  │
  ▼
Servlet FilterChain
  │
  ▼
DelegatingFilterProxy
  │
  ▼
FilterChainProxy
  │
  ▼
SecurityFilterChain
  ├─ CSRF / headers
  ├─ autenticación
  ├─ SecurityContext
  └─ autorización
  │
  ▼
DispatcherServlet → Controller

El orden importa: la autenticación debe producir una identidad antes de que la autorización decida si tiene permiso. No hace falta memorizar todos los filtros internos, pero sí comprender la secuencia.

@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    return http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/public/**").permitAll()
            .requestMatchers("/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated())
        .httpBasic(Customizer.withDefaults())
        .build();
}

Pregunta típica: “¿Qué sustituye hoy a WebSecurityConfigurerAdapter?” Una configuración basada en beans, normalmente declarando un SecurityFilterChain.

02

Autenticación: convertir credenciales en una identidad

Spring Security representa la autenticación con Authentication. Antes de validar credenciales puede representar una solicitud; después representa al principal autenticado.

PiezaResponsabilidad
AuthenticationPrincipal, credenciales y authorities.
AuthenticationManagerContrato que intenta autenticar.
ProviderManagerImplementación habitual que delega en providers.
AuthenticationProviderConoce un mecanismo concreto: usuario/contraseña, JWT, etc.
SecurityContextContiene la autenticación actual.
SecurityContextHolderDa acceso al contexto asociado a la ejecución actual.

Con usuario y contraseña, un flujo habitual consulta un UserDetailsService y compara la contraseña mediante un PasswordEncoder.

@Bean
PasswordEncoder passwordEncoder() {
    return PasswordEncoderFactories.createDelegatingPasswordEncoder();
}

No confundas hashing con cifrado. Una contraseña normalmente se almacena con un hash adaptativo; no necesitas poder descifrarla para autenticar.

03

Autorización: identidad no significa permiso

Estar autenticado solo demuestra que Spring reconoce una identidad. La autorización decide si esa identidad puede acceder al recurso.

.authorizeHttpRequests(auth -> auth
    .requestMatchers(HttpMethod.GET, "/catalog/**").permitAll()
    .requestMatchers("/admin/**").hasRole("ADMIN")
    .requestMatchers("/orders/**").hasAuthority("orders:write")
    .anyRequest().authenticated()
)

hasRole("ADMIN") usa la convención ROLE_ADMIN; hasAuthority compara la authority expresada. La autorización también puede vivir en métodos:

@EnableMethodSecurity
@Configuration
class SecurityConfig { }

@PreAuthorize("hasAuthority('orders:write')")
public Order cancel(UUID id) {
    ...
}

La seguridad por URL protege la frontera HTTP; method security puede proteger la operación incluso si se invoca desde otra ruta interna. Son herramientas complementarias.

04

JWT: Spring Security no se vuelve stateless por magia

Un JWT es un formato de token firmado. En una API Resource Server, el cliente suele enviar Authorization: Bearer .... Spring valida firma, fechas y claims según configuración, convierte claims relevantes en authorities y crea la autenticación.

@Bean
SecurityFilterChain apiSecurity(HttpSecurity http) throws Exception {
    return http
        .sessionManagement(session -> session
            .sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/actuator/health").permitAll()
            .anyRequest().authenticated())
        .oauth2ResourceServer(oauth -> oauth.jwt(Customizer.withDefaults()))
        .build();
}

JWT no es cifrado

Un JWT firmado garantiza integridad y autenticidad, pero su payload suele ser legible. No introduzcas secretos pensando que el token los oculta.

Stateless no significa sin estado

La API puede no mantener una HttpSession de login y depender de estado externo para revocación, usuarios, permisos, claves o negocio.

Error frecuente: escribir un filtro JWT manual para todo cuando Spring Security ya ofrece OAuth2 Resource Server. Un filtro propio puede tener sentido, pero necesita una razón concreta.

05

Sesión vs JWT: no existe un ganador universal

AspectoSesiónBearer JWT
Estado de loginNormalmente servidorPrincipalmente en el token
Revocación inmediataSencilla invalidando sesiónPuede exigir expiración corta o estrategia adicional
Navegador tradicionalEncaja muy bien con cookie seguraPosible, con cuidado de almacenamiento y transporte
Servicio a servicioMenos habitualHabitual con OAuth2/OIDC

La respuesta madura no es “JWT siempre escala mejor”. La elección depende de clientes, revocación, infraestructura, proveedor de identidad y modelo de amenazas.

06

CSRF: por qué no se debe desactivar por reflejo

CSRF aprovecha que un navegador puede enviar automáticamente credenciales asociadas a otro sitio, especialmente cookies. Si una aplicación autentica mediante cookie y acepta operaciones con estado, necesita analizar la protección CSRF.

En una API que recibe bearer tokens exclusivamente mediante un header explícito, el riesgo cambia. Por eso muchas APIs stateless desactivan CSRF, pero la explicación correcta es el modelo de credenciales, no “porque es REST”.

http.csrf(csrf -> csrf.disable()); // solo si el modelo de cliente lo justifica

Respuesta fuerte: “Decido CSRF según cómo viajan las credenciales. Si el navegador envía automáticamente una cookie autenticada, desactivarlo exige justificar otra mitigación.”

07

CORS no autentica ni autoriza

CORS es una política del navegador sobre peticiones cross-origin. No evita que un cliente no navegador llame a la API y no sustituye las reglas del servidor.

@Bean
CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration config = new CorsConfiguration();
    config.setAllowedOrigins(List.of("https://app.example.com"));
    config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE"));
    config.setAllowedHeaders(List.of("Authorization", "Content-Type"));
    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/**", config);
    return source;
}
08

401 vs 403

401 Unauthorized

La petición necesita autenticación válida y no la tiene. Conceptualmente es un problema de autenticación.

403 Forbidden

Existe una identidad válida, pero no tiene autorización suficiente.

En Spring Security, AuthenticationEntryPoint participa cuando se requieren credenciales, mientras que AccessDeniedHandler trata accesos denegados.

09

Errores frecuentes en proyectos reales

permitAll demasiado amplio

Un matcher genérico puede abrir más superficie de la prevista.

Roles hardcodeados

Acoplan seguridad y negocio y dificultan evolucionar permisos.

Guardar JWT en cualquier sitio

El almacenamiento en navegador cambia el riesgo de XSS y CSRF.

Logs con tokens

Un bearer token es una credencial y no debería acabar en logs o trazas.

Confiar en CORS

Un cliente no navegador ignora CORS; la autorización sigue siendo obligatoria.

Inventar criptografía

Usa mecanismos estándar; no diseñes algoritmos propios de firma o hashing.

10

Preguntas rápidas de entrevista

¿Dónde guarda Spring al usuario autenticado?

En un Authentication dentro del SecurityContext, normalmente accesible mediante SecurityContextHolder.

¿Authentication y Authorization son lo mismo?

No. Authentication establece identidad; Authorization decide qué puede hacer.

¿Qué es SecurityFilterChain?

Una cadena de filtros de seguridad aplicable a una petición. Puede haber varias y Spring selecciona la que corresponda.

¿Qué hace PasswordEncoder?

Codifica y verifica contraseñas usando algoritmos adecuados, comparando contra un hash y no texto plano.

¿Cuándo 401 y cuándo 403?

401 cuando falta autenticación válida; 403 cuando el usuario autenticado carece del permiso necesario.

¿Desactivarías CSRF en una API?

Solo después de analizar cómo se transportan las credenciales; devolver JSON no es razón suficiente.

11

Cómo lo respondería en una entrevista senior

“Empiezo por el modelo de amenazas y el tipo de cliente. En una aplicación Servlet, Spring Security aplica una cadena de filtros antes del controller. Un mecanismo de autenticación crea un Authentication, el resultado queda en el SecurityContext y después se aplican reglas de autorización por request o por método. Para APIs con OAuth2 prefiero el soporte estándar de Resource Server antes que filtros JWT caseros. Distingo 401 de 403, decido CSRF según el transporte de credenciales y no trato CORS como seguridad del servidor. La configuración técnica es consecuencia del modelo de seguridad, no al revés.”

Idea clave: memorizar anotaciones no demuestra que entiendas Spring Security. La pieza central es seguir una petición: filtros → autenticación → SecurityContext → autorización → aplicación.
