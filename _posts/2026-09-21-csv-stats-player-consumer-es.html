Kafka · Spring Boot · Avro · PostgreSQL

De un evento Kafka a 23 estadísticas persistidas

Este proyecto no envía miles de filas por Kafka. Envía algo mucho más pequeño: un evento que dice «el fichero ya está disponible». A partir de ahí, el consumer decide si debe procesarlo, abre el CSV, valida sus 23 columnas, transforma cada jugador en una entidad JPA y lo guarda en PostgreSQL. Lo interesante está en todo lo que ocurre cuando algo falla, el mismo evento llega dos veces o el fichero contiene miles de filas.

01

El problema que resuelve

csv-stats-player-consumer es un microservicio Spring Boot orientado a eventos. Su responsabilidad empieza cuando otro componente ya ha detectado o generado un fichero de estadísticas de jugadores. En vez de transportar el CSV completo dentro del mensaje Kafka, el productor publica un evento Avro con dos datos de negocio: qué tipo de fichero está listo y dónde puede encontrarlo el consumidor.

El consumer solo acepta eventos cuyo fileType sea STATS_PLAYER. Si recibe otro tipo, lo ignora. Cuando sí coincide, delega la importación a un servicio transaccional.

01 · EVENTO

Avro identifica el fichero y la ejecución.

02 · KAFKA

file.ready entrega la notificación.

03 · CSV

El parser valida 23 columnas y tipos.

04 · JPA

Se persiste por bloques de 500 filas.

05 · POSTGRES

Se guardan jugadores e idempotencia.

Esta arquitectura desacopla la notificación del contenido pesado. Kafka transporta el hecho de que existe trabajo pendiente; el fichero sigue siendo la fuente de las filas que hay que importar.

02

El contrato Avro: una key para la idempotencia

El mensaje utiliza dos esquemas Avro. La key contiene un uniqueId y el value contiene fileType y filePath.

FileEventKey
└── uniqueId: string

FileEventValue
├── fileType: string
└── filePath: string

El uniqueId no es un identificador decorativo. Más adelante se guarda como clave primaria de processed_file_event. Esa decisión conecta el contrato de mensajería con la garantía de idempotencia de la base de datos.

La configuración usa KafkaAvroDeserializer para key y value, specific.avro.reader externalizado y Schema Registry mediante KAFKA_SCHEMA_REGISTRY_URL. Los tipos Java se generan durante la build desde los ficheros .avsc con avro-maven-plugin.

Consecuencia importante: el filePath debe ser accesible desde el proceso consumidor. Si productor y consumidor viven en máquinas o contenedores distintos, una ruta local del productor no sirve por sí sola. El diseño necesita un filesystem compartido, un volumen común o sustituir la ruta por una ubicación remota accesible.
03

El listener hace poco, y eso es una virtud

FileReadyConsumer tiene una responsabilidad deliberadamente pequeña. Recibe un ConsumerRecord<FileEventKey, FileEventValue>, registra el identificador, tipo y ruta, filtra eventos ajenos a STATS_PLAYER y delega el trabajo real.

@KafkaListener(
    topics = "${app.kafka.topics.file-ready}",
    groupId = "${spring.kafka.consumer.group-id}")
public void listen(ConsumerRecord<FileEventKey, FileEventValue> record) {
    if (!"STATS_PLAYER".equalsIgnoreCase(record.value().getFileType())) {
        return;
    }

    importService.importFile(
        record.key().getUniqueId(),
        record.value().getFilePath());
}

Topic y consumer group no están codificados dentro del Java: salen de configuración. El topic tiene file.ready como valor por defecto, mientras que el group id se inyecta desde el entorno.

Separar listener e importación permite probar la decisión «¿este evento me pertenece?» sin mezclarla con parsing, JPA o filesystem.

04

Una transacción para todo el fichero

La pieza central es StatsPlayerImportService.importFile(), anotado con @Transactional. Antes de abrir el CSV pregunta si el eventId ya existe en processed_file_event. Si existe, termina inmediatamente.

if (processedEventRepository.existsById(eventId)) {
    return;
}

Si es un evento nuevo, procesa el fichero. Solo después de terminar correctamente guarda:

new ProcessedFileEvent(eventId, Instant.now())

Eso produce una propiedad útil: jugadores e identificador de evento participan en la misma transacción. Si el parser falla en la fila 800, si una escritura JPA lanza una excepción o si cualquier paso rompe la importación, la excepción se propaga y Spring puede hacer rollback de la operación.

Matiz: procesar en chunks reduce el tamaño del contexto JPA y permite hacer flush periódicamente, pero no convierte cada chunk en una transacción independiente. El método completo sigue siendo una única transacción por fichero. Es una decisión coherente con «todo o nada», aunque una importación muy grande mantiene la transacción abierta durante más tiempo.
05

El CSV se trata como datos, no como texto separado por comas

El parser usa Apache Commons CSV. Eso evita un error clásico: hacer split(",") y romper nombres o campos que contienen comas entrecomilladas.

Cada fila debe contener exactamente 23 columnas. El parser mapea:

GrupoCampos
IdentidadName, Team
ResumenPTS, REB, AST, MIN
TiroFGM, FGA, 2PM, 2PA, 3PM, 3PA, FTM, FTA
Impacto y rebote+/-, OR, DR
Defensa y pérdidasPF, ST, TO, BS, BA, TFS

Excepto name, team y min, las estadísticas cuantitativas se convierten a Integer. Si una fila contiene ten en PTS, no se deja pasar silenciosamente: se lanza una excepción que incluye número de fila, columna y valor problemático.

Ese fallo termina llegando al servicio, que lo envuelve en IllegalStateException. Como el listener no lo absorbe, Spring Kafka puede aplicar la política de reintentos.

06

Chunks de 500 y batching JDBC de 100

El parser no necesita materializar todo el fichero en memoria. parseInChunks() acumula como máximo 500 DTOs y entrega cada bloque al servicio.

Para cada chunk ocurre esta secuencia:

CSVRecord
   ↓
StatsPlayerDTO
   ↓ MapStruct
StatsPlayer
   ↓
saveAllAndFlush(500)
   ↓
EntityManager.clear()

saveAllAndFlush() fuerza la sincronización con la base de datos y EntityManager.clear() evita que miles de entidades ya procesadas sigan gestionadas por el contexto de persistencia.

Además, Hibernate configura hibernate.jdbc.batch_size=100 y order_inserts=true. La entidad usa una secuencia con allocationSize=100, alineada con la estrategia de batching para no depender de un identificador generado por cada insert individual.

100tamaño de batch JDBC
23columnas esperadas por fila
07

MapStruct y Lombok: código generado que también necesita pruebas

El proyecto separa el formato leído del modelo persistente mediante StatsPlayerDTO y StatsPlayer. StatsPlayerMapper usa MapStruct para generar las conversiones en compilación.

Hay un detalle histórico importante: el proyecto necesitó lombok-mapstruct-binding en los annotation processors para que MapStruct vea correctamente las propiedades generadas por Lombok. Sin esa coordinación, el mapper podía compilar y, aun así, construir entidades sin copiar los valores.

Ese fallo ya tiene una prueba específica sobre el mapper real. Lo documenté con una ejecución end-to-end en Probar un Kafka consumer en local: 5.000 filas, Avro y un bug invisible.

Lección general: si una parte esencial de tu aplicación la genera una herramienta durante compilación, no basta con mockear su interfaz. Al menos una prueba debe ejercitar el código generado real.
08

PostgreSQL: Flyway manda, Hibernate valida

La aplicación no deja que Hibernate improvise el esquema en cada arranque. Flyway gestiona la evolución y Hibernate usa ddl-auto: validate para comprobar que las entidades siguen siendo compatibles con la base existente.

La migración crea tres piezas clave:

stats_player_seq
stats_player
processed_file_event

stats_player conserva las 23 propiedades del jugador más su identificador. processed_file_event tiene event_id como primary key y processed_at como timestamp con zona horaria.

La migración también normaliza a INTEGER las estadísticas numéricas y cita explícitamente columnas como "or" y "to", cuyos nombres pueden ser problemáticos en SQL. Al final realinea la secuencia con el mayor identificador existente.

La configuración de conexión no contiene credenciales fijas: DB_URL, DB_USER y DB_PASS llegan por variables de entorno.

09

Cuando el fichero falla: retry y Dead Letter Topic

KafkaConsumerConfig configura un DefaultErrorHandler con FixedBackOff(2000, 2). En términos operativos, después del intento inicial puede haber dos reintentos adicionales, separados por 2 segundos.

Si sigue fallando, DeadLetterPublishingRecoverer publica el registro en un topic con sufijo .DLT y conserva el número de partición:

file.ready partition 3
        │
        ├── intento inicial
        ├── retry +2 s
        ├── retry +2 s
        └──► file.ready.DLT partition 3

El servicio no marca el evento como procesado si la importación termina con error. Esto permite que un retry vuelva a recorrer la lógica en lugar de encontrarse un falso positivo de idempotencia.

10

Qué garantiza realmente la idempotencia

Si Kafka vuelve a entregar un evento ya completado, existsById(eventId) evita volver a abrir el fichero y duplicar jugadores. Es una protección sencilla y explícita.

Hay un matiz de concurrencia interesante. La comprobación existsById y el posterior insert del marcador no forman una única operación atómica de «claim». Dos consumidores concurrentes podrían comprobar a la vez que el identificador aún no existe y empezar a procesar. La primary key de processed_file_event impide que ambos commits terminen correctamente y, al estar todo dentro de la transacción, el perdedor debería revertir también sus jugadores. Aun así, habría hecho trabajo duplicado antes de chocar.

Si el sistema necesitase mucha concurrencia sobre el mismo evento, sería razonable evolucionar hacia una estrategia de claim atómico o bloqueo. Para el contrato actual, la combinación de marcador persistente y transacción proporciona una semántica clara y fácil de auditar.

11

Tests rápidos sin Docker y una frontera de integración real

La suite separa intencionadamente dos niveles. mvn clean test ejecuta tests unitarios y de configuración sin requerir Docker. Allí se comprueba el filtro del listener, el contrato del parser, los chunks, la idempotencia, la transacción, el mapper y la política Kafka de retry/DLT.

La integración con PostgreSQL real vive en PostgreSqlMigrationIT, con naming de Maven Failsafe. Se ejecuta mediante:

mvn clean verify -Pintegration

Ese test arranca postgres:15-alpine con Testcontainers, ejecuta Flyway y consulta information_schema para comprobar tablas, secuencia y tipos de columnas.

Decisión práctica: un desarrollador puede ejecutar la suite normal aunque no tenga Docker. CI, en cambio, ejecuta mvn -B verify -Pintegration y añade la validación del PostgreSQL real.

13

Lo interesante está también en cómo evolucionó

El changelog cuenta una historia técnica bastante clara. El consumer no nació con todas estas garantías: se fueron añadiendo como respuestas a fallos o límites concretos.

Parsing

El split(",") inicial se sustituyó por Apache Commons CSV y validación de 23 columnas.

Tipos

Las estadísticas pasaron de texto a Integer con validación explícita de valores no numéricos.

Resiliencia

Se incorporaron retries, backoff y DLT en vez de limitarse a registrar el error.

Consistencia

La importación se movió a un servicio transaccional y se añadió idempotencia por evento.

Volumen

Llegaron batching JDBC, secuencia optimizada, chunks de 500 y limpieza del persistence context.

Esquema y pruebas

Flyway, ddl-auto: validate, Testcontainers y pruebas del mapper real cerraron fronteras que antes quedaban implícitas.

La versión actual es 1.0.25, sobre Java 21 y Spring Boot 3.1.12.

14

El repositorio también automatiza cómo se cambia

Hay una segunda parte del proyecto que no ejecuta negocio pero sí protege su mantenimiento. AGENTS.md define una política específica para cambios realizados por agentes de IA: rama dedicada, incremento de versión, sincronización de pom.xml/README.md/CHANGELOG.md, tests y Pull Request obligatorio.

GitHub Actions refuerza esa política:

WorkflowQué protege
documentation-policyVersión Maven, README, changelog y formato del mensaje de commit.
testSuite completa con perfil de integración.
master-guardDetecta commits directos no-merge que lleguen a master.
cleanup-merged-branchElimina la rama origen tras un merge correcto.

La protección real frente a pushes directos depende además del Branch Protection/Ruleset configurado en GitHub; el workflow sirve como segunda red y como evidencia visible de la política.

15

El modelo mental que me quedo

Este consumer puede resumirse como una tubería con cuatro fronteras que conviene proteger por separado:

MENSAJE              FICHERO                DOMINIO              BASE DE DATOS
Avro/Kafka    ───►   CSV validado   ───►   DTO / Mapper   ───►  JPA / Flyway
    │                    │                     │                     │
    ├─ filtro            ├─ 23 columnas       ├─ tipos              ├─ transacción
    ├─ retry/DLT         ├─ numericidad       ├─ código generado    ├─ idempotencia
    └─ eventId           └─ chunks            └─ entidad            └─ esquema real

El valor del proyecto no está en una clase aislada. Está en cómo esas fronteras se conectan: un identificador Avro termina protegiendo la persistencia, una excepción del parser activa la política Kafka, el tamaño de chunk condiciona JPA y una migración real se comprueba contra PostgreSQL real.

Ese es el detalle que convierte «leer un CSV y hacer inserts» en un consumer mantenible: cada decisión importante tiene una responsabilidad concreta y, en la mayoría de los casos, una prueba que la protege.
