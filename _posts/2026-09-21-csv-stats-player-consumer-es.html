Kafka · Avro · Spring Boot · PostgreSQL

Del evento Kafka al snapshot consistente

csv-stats-player-consumer no se limita a leer un CSV. Convierte una notificación asíncrona en un snapshot validado, idempotente y transaccional de estadísticas de jugadores. La versión 1.5.3 endurece además la frontera de entrada: antes de importar comprueba que el evento apunte al fichero correcto, dentro del directorio permitido y con la cabecera exacta.

01

El flujo completo en una sola vista

Otro componente genera player_stats.csv y publica en Kafka un evento Avro indicando dónde está. El consumer no recibe las filas por Kafka: recibe una señal para localizar el fichero. A partir de ahí valida el evento, interpreta el CSV, reemplaza el estado de los partidos afectados y marca el evento como procesado solo si todo termina bien.

01 · KAFKA

Llega el evento Avro.

02 · VALIDACIÓN

Tipo, ruta, nombre y cabecera.

03 · CSV

24 columnas y tipos.

04 · POSTGRES

Snapshot transaccional.

05 · EVENTO

Se guarda la idempotencia.

La idea importante es que Kafka coordina trabajo, mientras PostgreSQL representa el estado materializado final.

02

Kafka transporta la señal, Avro define el contrato

La key y el value del evento tienen responsabilidades distintas:

FileEventKey
└── uniqueId: string

FileEventValue
├── fileType: string
└── filePath: string

uniqueId identifica la entrega lógica, fileType permite que varios consumers compartan el mismo canal y filePath apunta al recurso real. Este servicio solo procesa STATS_PLAYER; otros tipos se ignoran.

Consecuencia: el CSV debe ser accesible desde el proceso consumidor. En Docker el repositorio resuelve esta frontera montando el directorio de datos como /data.
03

1.5.3 valida el fichero antes de importarlo

La principal novedad de la versión 1.5.3 es FileEventValidator. Un evento STATS_PLAYER solo avanza si cumple todas estas condiciones:

ComprobaciónRegla
Key y valueDeben existir y contener uniqueId, fileType y filePath no vacíos.
RutaDebe ser absoluta, normalizada y quedar dentro de CSV_ALLOWED_ROOT, por defecto /data.
FicheroDebe existir, ser legible y llamarse exactamente player_stats.csv sin distinguir mayúsculas.
CabeceraDebe coincidir exactamente con las 24 columnas esperadas.

Estos fallos se consideran permanentes: repetirlos dos veces no va a arreglar una ruta relativa ni una cabecera incorrecta. Por eso InvalidFileEventException se clasifica como no reintentable y el mensaje pasa directamente a DLT.

04

eventId y matchId resuelven problemas diferentes

IdentificadorOrigenUso
eventIdFileEventKey.uniqueIdEvitar reprocesar una entrega ya completada.
matchIdPrimera columna del CSVIdentificar el partido cuyo snapshot debe sustituirse.

La diferencia permite que el mismo evento sea idempotente y, al mismo tiempo, que un evento nuevo pueda actualizar un partido ya existente.

05

La importación reemplaza snapshots, no acumula filas

Desde 1.5.0 el CSV incluye match_id. En 1.5.2 la persistencia se endureció para evitar duplicados: al procesar un fichero nuevo, el servicio elimina las filas existentes de cada matchId afectado y guarda el snapshot recibido dentro de la misma transacción.

1. comprobar eventId
2. leer CSV en chunks
3. por cada matchId nuevo:
   eliminar snapshot anterior
4. insertar filas nuevas
5. guardar processed_file_event
6. commit

El conjunto de partidos ya reemplazados vive durante toda la importación, así que un partido se borra una sola vez aunque sus jugadores estén repartidos entre varios chunks.

Mismo eventId

La importación no se repite.

Nuevo eventId, mismo matchId

Se sustituye el snapshot anterior.

06

El CSV es un contrato de 24 columnas

Apache Commons CSV evita tratar el fichero como texto separado ingenuamente con split(","). La cabecera esperada es:

match_id,Player,Team,PTS,REB,AST,MIN,FGM,FGA,2PM,2PA,3PM,3PA,
FTM,FTA,+/-,OR,DR,PF,ST,TO,BS,BA,TFS

Las estadísticas numéricas se convierten a Integer. Desde 1.5.1, un guion aislado (-) significa “dato no disponible” y se persiste como NULL; un valor como -9 en +/- sigue siendo un entero negativo válido.

El procesamiento se hace en chunks de 500 DTOs. Tras cada saveAllAndFlush(), se limpia el persistence context con EntityManager.clear(). Hibernate mantiene además un batch JDBC de 100 y la secuencia usa allocationSize=100.

07

PostgreSQL y Flyway refuerzan invariantes

La base de datos no es un simple destino. Flyway controla la evolución del esquema y Hibernate usa ddl-auto: validate. La tabla stats_player incluye match_id y una restricción única sobre:

(match_id, name, team)

Esto impide duplicar el mismo jugador del mismo equipo dentro de un partido incluso si la aplicación falla en una validación previa. La tabla processed_file_event guarda la idempotencia por evento.

Unidad de consistencia: importFile() es transaccional. Si falla una fila, un insert o el guardado final del evento, se revierte la importación completa.
08

No todos los errores merecen retry

Los fallos de procesamiento normales usan DefaultErrorHandler con dos reintentos y 2 segundos de espera. Si siguen fallando, el registro se publica en <topic>.DLT.

error temporal
  intento inicial
  → retry +2 s
  → retry +2 s
  → DLT

evento inválido
  → DLT directamente

La distinción evita gastar tiempo repitiendo errores deterministas como rutas fuera de CSV_ALLOWED_ROOT, nombre de fichero incorrecto o cabecera incompatible.

09

MétricaQué mide

10

El directorio configurado con CSV_DATA_DIR se monta como /data en modo solo lectura, coherente con la validación de CSV_ALLOWED_ROOT.

Modelo mental: Kafka dice que existe trabajo; el validador decide si el evento es coherente; el parser convierte el fichero en datos fiables; la transacción reemplaza el snapshot; PostgreSQL impone invariantes; y solo entonces el eventId queda marcado como completado.
