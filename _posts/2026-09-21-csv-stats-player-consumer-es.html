Kafka · Avro · Spring Boot · PostgreSQL

Qué hace realmente csv-stats-player-consumer

csv-stats-player-consumer es un microservicio orientado a eventos cuya función no es “leer un CSV y guardarlo”. Su responsabilidad real es convertir una notificación asíncrona en una actualización consistente, repetible y observable del estado de estadísticas de jugadores almacenado en PostgreSQL. Para hacerlo coordina mensajería, acceso a fichero, validación de datos, transacciones, idempotencia, sustitución de snapshots, persistencia y recuperación ante errores.

01

La responsabilidad del microservicio

El sistema parte de una idea sencilla: otro componente ya ha producido un fichero CSV con estadísticas de jugadores y publica en Kafka un evento indicando que ese fichero está disponible. El mensaje no contiene las miles de filas del CSV. Contiene únicamente la información necesaria para localizar el fichero y clasificarlo.

El consumidor escucha esos eventos, decide si el fichero pertenece a su dominio y, si corresponde a estadísticas de jugadores, inicia una importación. Esa importación debe cumplir varias propiedades al mismo tiempo: no procesar dos veces el mismo evento completado, validar el formato, reemplazar correctamente el estado anterior de cada partido, evitar duplicados lógicos, no dejar datos parciales si algo falla y permitir que Kafka vuelva a intentarlo.

01 · KAFKA

Llega una notificación Avro de fichero disponible.

02 · FILTRO

Solo se acepta el tipo STATS_PLAYER.

03 · CSV

Se abre, valida y transforma el fichero.

04 · TRANSACCIÓN

Se reemplaza el snapshot afectado y se persiste.

05 · CONFIRMACIÓN

El evento queda marcado como procesado.

Por tanto, el microservicio ocupa una frontera entre dos mundos: Kafka representa que ocurrió algo y PostgreSQL representa el estado materializado que debe quedar después de procesarlo.

02

Arquitectura orientada a eventos: Kafka transporta una señal, no el dataset

El diseño usa Kafka como mecanismo de coordinación. El evento significa, conceptualmente, “hay un fichero listo para ser procesado”. Esto desacopla al productor del consumidor: el productor no necesita conocer la lógica JPA, el esquema de la tabla ni cómo se validan las estadísticas; el consumidor no necesita saber cómo se generó el fichero.

El evento utiliza Avro y se divide en una key y un value:

FileEventKey
└── uniqueId: string

FileEventValue
├── fileType: string
└── filePath: string

uniqueId identifica de forma lógica la ejecución o evento. fileType permite que varios consumidores compartan un canal de eventos pero reaccionen solo a los tipos que entienden. filePath indica dónde está el recurso que contiene los datos reales.

Implicación arquitectónica: Kafka no hace accesible el CSV por sí mismo. El proceso consumidor debe poder resolver filePath. En despliegues con contenedores o máquinas distintas esto exige un volumen compartido, un filesystem común o una estrategia equivalente de almacenamiento accesible para ambos lados.

Avro aporta un contrato explícito para la mensajería. La aplicación configura deserialización Avro específica y Schema Registry, de modo que el evento no se trata como un mapa genérico de propiedades, sino como tipos generados que representan un contrato conocido.

03

El listener es deliberadamente fino

FileReadyConsumer es la entrada del microservicio. Su diseño es intencionadamente pequeño: recibe el ConsumerRecord, extrae key y value, registra los datos básicos del mensaje, comprueba el tipo de fichero y delega.

La decisión principal es esta:

si fileType != STATS_PLAYER
    ignorar evento

si fileType == STATS_PLAYER
    importar filePath usando uniqueId

Esta separación es importante porque evita que la capa Kafka se convierta en una clase que también conoce CSV, JPA y reglas de consistencia. El listener decide si el mensaje pertenece al microservicio; el servicio de importación decide cómo convertirlo en estado persistente.

El topic se obtiene de configuración y por defecto es file.ready. El consumer group también llega desde configuración. Esto permite desplegar la misma aplicación en distintos entornos sin recompilarla y mantiene los detalles operativos fuera de la lógica de negocio.

04

Dos identidades distintas: eventId y matchId

Una de las claves para entender el diseño actual es no confundir dos identificadores que resuelven problemas diferentes.

IdentificadorOrigenQué representaPara qué se usa
eventIdFileEventKey.uniqueIdLa entrega lógica del ficheroEvitar reprocesar un evento que ya terminó correctamente
matchIdPrimera columna del CSVEl partido al que pertenece cada filaReemplazar la instantánea de jugadores de ese partido

El eventId protege el procesamiento frente a redeliveries del mismo mensaje. El matchId protege la semántica de negocio cuando llega una nueva versión de los datos del mismo partido.

Esta distinción permite dos comportamientos complementarios. Si Kafka vuelve a entregar exactamente el mismo evento, el servicio puede ignorarlo. Si llega un evento diferente que contiene estadísticas actualizadas para un partido ya existente, el servicio sí debe procesarlo y sustituir el estado anterior del partido.

05

Idempotencia por evento

Antes de abrir el fichero, StatsPlayerImportService consulta processed_file_event. Si ya existe una fila cuya primary key es el eventId, la importación termina inmediatamente.

processed_file_event
├── event_id       PRIMARY KEY
└── processed_at   TIMESTAMP WITH TIME ZONE

El marcador no se escribe al principio, sino al final de la importación correcta. Esta decisión evita un problema serio: si se marcara el evento como procesado antes de leer el CSV y luego fallara la fila 300, un retry encontraría el marcador y descartaría un trabajo que nunca se completó.

El orden conceptual es:

1. ¿eventId ya procesado?
   └─ sí → terminar

2. procesar CSV y persistir snapshot

3. guardar processed_file_event(eventId)

4. confirmar transacción

La idempotencia no significa que Kafka entregue una sola vez. Significa que el efecto observable de repetir una entrega ya completada no cambia el estado.

Límite: la consulta existsById y el insert final no constituyen un “claim” atómico previo al trabajo. Dos ejecuciones verdaderamente concurrentes del mismo eventId podrían empezar a trabajar a la vez. La primary key impide dos confirmaciones finales válidas, pero no evita el trabajo duplicado previo. Para un volumen de concurrencia extrema podría ser necesario un mecanismo de claim o locking más fuerte.
06

El CSV representa una instantánea por partido

El comportamiento actual no es simplemente “insertar nuevas filas”. Cada fichero se interpreta como una instantánea completa de los partidos que contiene. Cuando aparece por primera vez un matchId durante la importación, el servicio elimina todas las filas ya persistidas para ese partido antes de insertar las nuevas.

para cada chunk:
    entidades = mapear DTOs

    matchIds nuevos en este fichero =
        matchIds del chunk todavía no reemplazados

    eliminar filas existentes de esos matchIds
    insertar las filas nuevas del chunk

El conjunto replacedMatchIds vive durante toda la importación y garantiza que cada partido se borre una sola vez, aunque sus jugadores aparezcan repartidos entre varios chunks. Esto es importante porque borrar el partido en cada chunk eliminaría filas insertadas por un chunk anterior del mismo fichero.

La semántica resultante es parecida a una operación de reemplazo: para cada partido presente en el CSV, el estado final en PostgreSQL debe reflejar el contenido del fichero que se está importando, no una acumulación histórica de todas las versiones recibidas.

Evento repetido

Mismo eventId: no se vuelve a procesar.

Snapshot nuevo

Otro eventId con el mismo matchId: se reemplazan los jugadores anteriores de ese partido.

07

La transacción define la unidad real de consistencia

importFile() está anotado con @Transactional. Por tanto, la unidad lógica no es una fila ni un chunk: es el fichero completo.

Dentro de la misma transacción pueden ocurrir eliminaciones del snapshot anterior, inserciones de nuevos jugadores y el guardado del marcador de evento procesado. Si una excepción escapa del método, Spring puede revertir todas esas modificaciones.

BEGIN

  comprobar eventId
  borrar snapshots afectados
  insertar jugadores
  guardar processed_file_event

COMMIT

si algo falla:
ROLLBACK

Este diseño busca una propiedad de “todo o nada”. No interesa dejar 500 jugadores nuevos de un partido y otros 200 antiguos porque la lectura falló a mitad del fichero. Tampoco interesa guardar el marcador idempotente si los datos no llegaron a consolidarse.

El coste de esta garantía es que un fichero grande mantiene una transacción abierta durante más tiempo. Los chunks reducen memoria y tamaño del contexto JPA, pero no fragmentan la transacción. Es una elección entre consistencia fuerte de la importación y duración de la unidad transaccional.

08

El parser trata el CSV como un contrato de datos

StatsPlayerCsvParser usa Apache Commons CSV. Esto permite respetar reglas reales de CSV, como campos entrecomillados, en lugar de asumir que cada coma equivale siempre a una separación válida.

El parser actual exige exactamente 24 columnas por fila. El orden tiene significado:

PosiciónCampoTipo lógico
1match_idTexto
2–3Name, TeamTexto
4–6PTS, REB, ASTEntero nullable
7MINTexto
8–15FGM, FGA, 2PM, 2PA, 3PM, 3PA, FTM, FTAEntero nullable
16–18+/-, OR, DREntero nullable
19–24PF, ST, TO, BS, BA, TFSEntero nullable

La validación no se limita al número de columnas. Las estadísticas numéricas se convierten a Integer. El valor especial - significa “dato no disponible” y se convierte en null. Esto es distinto de un número negativo real: por ejemplo, -9 en +/- sigue siendo un entero válido y conserva su signo.

Si aparece texto no convertible en una columna numérica, el parser lanza una excepción con información de fila, columna y valor. No intenta corregir silenciosamente el dato ni sustituirlo por cero, porque eso alteraría el significado estadístico.

Idea importante: validar pronto desplaza el fallo hacia la frontera de entrada. Es preferible rechazar una fila inválida antes de transformarla en una entidad que descubrir el problema más tarde, cuando el estado ya está parcialmente mezclado con persistencia.
09

Chunks de 500: controlar memoria sin perder atomicidad

El parser no necesita cargar el fichero completo en una lista. parseInChunks() acumula hasta 500 DTOs y entrega cada bloque al servicio. Al terminar el fichero, entrega también el último bloque aunque tenga menos elementos.

Esto cambia el perfil de memoria. En lugar de retener todos los jugadores antes de empezar a persistir, el consumo se mantiene aproximadamente acotado por el tamaño de chunk y por los objetos que JPA tenga gestionados en ese momento.

CSVParser
   │
   ├─ 500 filas → List<StatsPlayerDTO>
   │                 │
   │                 ▼
   │              MapStruct
   │                 │
   │                 ▼
   │              entidades
   │                 │
   │                 ▼
   │           saveAllAndFlush()
   │                 │
   │                 ▼
   │        EntityManager.clear()
   │
   └─ siguiente chunk

Después de saveAllAndFlush(), el servicio ejecuta EntityManager.clear(). El objetivo es evitar que el persistence context mantenga referencias a miles de entidades ya sincronizadas con la base de datos.

El chunk de aplicación es 500, mientras que Hibernate configura hibernate.jdbc.batch_size=100. Son dos niveles distintos: uno regula cuántos objetos procesa la aplicación de una vez y el otro regula cómo Hibernate agrupa operaciones JDBC.

24columnas requeridas por fila
500DTOs por chunk de aplicación
100batch JDBC configurado
100allocationSize de la secuencia
10

DTO, MapStruct y entidad: separar entrada de persistencia

El parser produce StatsPlayerDTO. Ese objeto representa los datos ya interpretados desde CSV. Después, StatsPlayerMapper transforma cada DTO en una entidad StatsPlayer que JPA puede persistir.

La separación evita acoplar directamente el parser al modelo de persistencia. Conceptualmente hay tres etapas:

texto CSV
   ↓ interpretación
StatsPlayerDTO
   ↓ mapeo
StatsPlayer
   ↓ persistencia
tabla stats_player

MapStruct genera el código de mapeo en compilación. Lombok genera parte del boilerplate de los modelos. El proyecto incluye la integración entre ambos annotation processors para que MapStruct pueda reconocer correctamente las propiedades generadas.

La entidad utiliza una secuencia PostgreSQL y un allocationSize de 100. Esto encaja con el procesamiento por lotes: obtener rangos de identificadores evita depender de un round-trip para cada fila individual.

11

PostgreSQL no es solo almacenamiento: también impone invariantes

La tabla stats_player contiene los datos del jugador y su match_id. La base de datos añade una restricción única sobre:

(match_id, name, team)

Esta restricción expresa una regla de identidad lógica: dentro de un mismo partido no debería existir dos veces el mismo jugador del mismo equipo. Es una defensa adicional incluso si la aplicación contiene un error o recibe un fichero con duplicados incompatibles.

El esquema se gestiona con Flyway. Hibernate usa ddl-auto: validate, de modo que no intenta modificar automáticamente el esquema para hacerlo coincidir con las entidades. La responsabilidad de evolucionar la base pertenece a las migraciones; Hibernate comprueba que el modelo esperado y el real son compatibles.

Las migraciones actuales establecen, entre otras cosas, la secuencia, la tabla de estadísticas, la tabla de eventos procesados, la columna match_id y la deduplicación necesaria antes de crear la restricción única.

Flyway

Define cómo cambia el esquema con una secuencia versionada de migraciones.

Hibernate validate

Comprueba el esquema al arrancar, pero no lo reescribe.

12

Los errores vuelven a Kafka: retries y Dead Letter Topic

El listener no absorbe los fallos de importación. Si el servicio lanza una excepción, Spring Kafka la recibe y aplica el DefaultErrorHandler.

La configuración por defecto usa un FixedBackOff de 2 segundos y un máximo de 2 reintentos después del intento inicial:

intento inicial
   │
   ├─ falla
   ▼
espera 2 s
   │
   ├─ retry 1 falla
   ▼
espera 2 s
   │
   ├─ retry 2 falla
   ▼
Dead Letter Topic

Cuando se agotan los intentos, DeadLetterPublishingRecoverer publica el registro en el topic original con un sufijo configurable, por defecto .DLT, conservando la partición.

file.ready[3]
   └─ error definitivo
      └─► file.ready.DLT[3]

La DLT no arregla el fichero. Su función es separar los mensajes que no pudieron completarse del flujo normal para que puedan inspeccionarse, corregirse o reprocesarse mediante una estrategia operativa explícita.

Como el marcador de processed_file_event se escribe solo al final de una transacción correcta, cada retry encuentra el evento todavía pendiente y puede intentar la importación completa otra vez.

13

Semántica práctica: asumir redelivery y diseñar efectos repetibles

En sistemas de mensajería distribuidos es peligroso diseñar como si cada mensaje solo pudiera aparecer una vez. Un error de proceso, un rebalanceo, un timeout o un problema de confirmación pueden provocar una nueva entrega.

Este microservicio afronta esa realidad en dos capas:

Idempotencia técnica

eventId evita aplicar dos veces una entrega ya completada.

Idempotencia de negocio

matchId más el reemplazo del snapshot impide que una nueva versión del partido se limite a duplicar filas anteriores.

No es exactamente lo mismo que una garantía de “exactly once” distribuida entre Kafka, filesystem y PostgreSQL. Es una estrategia de procesamiento robusta construida sobre transacción local, identificadores persistentes y reglas de reemplazo.

14

Observabilidad: saber si procesa, falla o deriva a DLT

El microservicio incorpora Spring Boot Actuator, Micrometer y el registro Prometheus. Además de métricas técnicas de la plataforma, expone métricas funcionales que describen el comportamiento de la importación.

MétricaSignificado
csv_files_processed_totalNúmero de ficheros completados correctamente.
csv_files_failed_totalNúmero de intentos de importación que terminaron con error.
csv_rows_processed_totalFilas contabilizadas en importaciones completadas.
csv_processing_duration_secondsDuración del procesamiento de los ficheros.
kafka_dlt_messages_totalMensajes enviados a DLT tras agotar reintentos.

Estas métricas permiten responder preguntas operativas diferentes. Un aumento de csv_files_failed_total indica fallos de procesamiento. Un aumento de kafka_dlt_messages_total indica que los reintentos tampoco solucionaron el problema. Una degradación de csv_processing_duration_seconds puede señalar ficheros mayores, lentitud de base de datos o presión de I/O.

La aplicación expone también endpoints Actuator como /actuator/health y /actuator/prometheus, lo que permite integrar salud y métricas en la plataforma de observabilidad.

17

Cómo se propaga un fallo de extremo a extremo

Supongamos que una fila contiene abc en la columna PTS. El parser intenta convertirla a Integer y lanza una excepción. El servicio captura el error para registrar métricas y logs, pero vuelve a lanzar una IllegalStateException.

CSV inválido
   ↓
StatsPlayerCsvParser
   ↓ excepción
StatsPlayerImportService
   ├─ incrementa csv_files_failed_total
   ├─ registra el error
   └─ vuelve a lanzar
        ↓
@Transactional
   └─ rollback
        ↓
Spring Kafka
   ├─ retry
   ├─ retry
   └─ DLT si persiste

Este recorrido muestra por qué las capas no son independientes. Una decisión del parser acaba provocando un rollback en PostgreSQL y, después, una política de recuperación en Kafka. La arquitectura funciona porque las excepciones atraviesan las fronteras adecuadas en vez de quedar ocultas.

18

Rendimiento: tres niveles que trabajan juntos

El rendimiento no depende de una única optimización. El proyecto combina tres mecanismos con objetivos distintos.

Streaming del CSV

Evita materializar todo el fichero en memoria antes de empezar.

Chunks de 500

Limitan los objetos manejados por la aplicación y permiten limpiar el contexto JPA.

Batch JDBC de 100

Reduce el número de intercambios necesarios para ejecutar inserts.

Secuencia con allocationSize 100

Reduce la necesidad de obtener un identificador nuevo de la base para cada entidad.

Estas optimizaciones no cambian la semántica transaccional. Mejoran cómo se ejecuta la importación, pero el commit sigue representando el fichero completo.

20

Por qué tiene sentido como microservicio separado

Separar este consumidor puede tener valor cuando la generación del fichero y su materialización en base de datos evolucionan con ritmos distintos. El productor puede centrarse en detectar o producir archivos; el consumidor puede cambiar validaciones, persistencia, batching o estrategias de resiliencia sin convertir al productor en responsable de toda la cadena.

También permite escalar y operar de forma independiente la parte que procesa estadísticas. Kafka actúa como frontera temporal: productor y consumidor no tienen que estar disponibles exactamente al mismo tiempo.

El coste es la complejidad distribuida. Aparecen contratos de eventos, Schema Registry, accesibilidad del fichero, semántica de reintentos, DLT y observabilidad. Por eso el valor del diseño no está simplemente en “usar Kafka”, sino en que esas responsabilidades estén explícitas y tengan límites claros.

21

Resumen conceptual

csv-stats-player-consumer convierte un evento ligero de Kafka en una actualización transaccional de estadísticas de jugadores. Usa Avro para el contrato del evento, un identificador persistente para idempotencia, Apache Commons CSV para validar 24 columnas, MapStruct para separar DTO y entidad, chunks para controlar memoria, JPA/Hibernate para persistencia, PostgreSQL para invariantes, Flyway para evolución del esquema, retries y DLT para recuperación y Micrometer para observabilidad.

La parte más importante no es ninguna tecnología por separado. Es la combinación de reglas: el marcador de evento se guarda solo si el fichero termina; los partidos se sustituyen una única vez por importación; los chunks no rompen la transacción; los errores del parser llegan hasta Kafka; y la base de datos refuerza invariantes que la aplicación por sí sola no debería asumir.

Idea final: el microservicio no está diseñado para acumular filas indefinidamente. Está diseñado para materializar snapshots de estadísticas de forma repetible y consistente a partir de eventos que pueden llegar más de una vez y de ficheros que pueden fallar durante el procesamiento.

Este artículo describe teóricamente el comportamiento actual del repositorio csv-stats-player-consumer, cuya versión declarada actualmente es 1.5.2.
