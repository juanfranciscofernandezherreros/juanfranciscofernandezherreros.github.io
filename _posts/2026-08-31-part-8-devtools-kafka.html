Local Kafka Platform

01

Purpose and components

The platform runs in the devtools-kafka namespace of the local kind-hello-world cluster. It lets microservices produce and consume events, share versioned data contracts, and observe the system through two web interfaces.

ZooKeeper

Coordinates the Kafka generation in use. Service: zookeeper:2181.

Kafka

The broker stores and distributes events. Internal service: kafka:29092.

Schema Registry

Versions and validates contracts. API: schema-registry:8081.

REST Proxy

Translates HTTP into Kafka operations. API: rest-proxy:8082.

Kafka UI

Displays brokers, topics, messages, consumers, schemas, and ZooKeeper.

Redpanda Console

A second interface compatible with the Kafka and Schema Registry APIs.

Important: using Redpanda Console does not turn the broker into Redpanda. The broker remains Kafka from the Confluent distribution; Console is a stateless client.

02

Architecture and flow

Microservices / UIs→Kafka→ZooKeeperUIs / REST Proxy→Schema Registry→_schemas topic

Short Kubernetes DNS names work inside the namespace. From another namespace, a microservice can use kafka.devtools-kafka.svc.cluster.local:29092 and http://schema-registry.devtools-kafka.svc.cluster.local:8081.

Kafka exposes two PLAINTEXT listeners. kafka:29092 is advertised to pods, while localhost:9092 serves local-machine clients through a port forward. The advertised address matters because, after bootstrap, the broker returns the endpoints the client must use for subsequent connections.

03

ZooKeeper, Kafka, and the data

The broker runs confluentinc/cp-kafka:7.4.4 in ZooKeeper mode. KAFKA_ZOOKEEPER_CONNECT=zookeeper:2181 links both components. Kafka UI also receives this endpoint; Redpanda Console does not query ZooKeeper directly because it manages the system through Kafka's standard API.

There is one broker, automatic topic creation, and replication factors of 1 for offsets and transactions. This is a lightweight development setup. A future KRaft migration could remove ZooKeeper, but it requires an operational and metadata migration—not simply deleting the ZooKeeper Deployment.

04

Contracts with Schema Registry

Schema Registry stores its metadata in Kafka's internal _schemas topic. At the end of a synchronization, the register-demo-schemas PostSync hook waits for the API and registers:

  • test-topic-key: a string key.
  • test-topic-value: the DemoValue record, with an integer id and string message.

Schemas give producers and consumers a shared, versioned contract and allow both interfaces to deserialize messages correctly.

05

Visual interfaces

Kafka UI

provectuslabs/kafka-ui:v0.7.2 connects to Kafka, Schema Registry, and ZooKeeper. It displays brokers, topics, partitions, messages, headers, offsets, groups, consumer lag, and subjects. DYNAMIC_CONFIG_ENABLED=false keeps Git as the source of truth.

Redpanda Console

docker.redpanda.com/redpandadata/console:v3.11.0 uses KAFKA_BROKERS=kafka:29092 and SCHEMAREGISTRY_URLS=http://schema-registry:8081. No Redpanda Admin API is configured because the actual broker is Kafka. Both UIs inspect the same cluster; they do not duplicate brokers or data.

07

Local access

The Services use ClusterIP. Run each tunnel in a separate terminal; it remains active until you press Ctrl+C.

kubectl port-forward -n devtools-kafka svc/kafka-ui 18080:8080
kubectl port-forward -n devtools-kafka svc/redpanda-console 18083:8080
kubectl port-forward -n devtools-kafka svc/kafka 9092:9092
kubectl port-forward -n devtools-kafka svc/schema-registry 18081:8081
kubectl port-forward -n devtools-kafka svc/rest-proxy 18082:8082
  • Kafka UI: http://localhost:18080
  • Redpanda Console: http://localhost:18083

Invoke-RestMethod http://localhost:18080/actuator/health
Invoke-RestMethod http://localhost:18083/admin/health
Invoke-RestMethod http://localhost:18081/subjects

Kafka UI should return UP, Redpanda Console should report healthy HTTP, and Schema Registry should list both demo subjects. The registration Job should be Completed; it is not a continuously running service.

09

Security and limitations

Containers run as non-root users with RuntimeDefault seccomp, no privilege escalation, and no Linux capabilities. The UIs pin UID/GID 100:101. Probes govern availability and process health, while requests and limits constrain resource usage.

This is not a production topology: it has one broker, replication factor 1, non-persistent storage, PLAINTEXT without SASL/TLS, unauthenticated UIs, and no NetworkPolicy. Production requires persistence, multiple brokers, replication, encryption, authorization, backups, metrics, and alerting.

10

Manifests

The definition is split between applications/devtools-kafka.yaml and the files under manifests/devtools-kafka/: ZooKeeper, Kafka, Schema Registry, REST Proxy, Kafka UI, Redpanda Console, and the PostSync registrar. Git describes the desired state and Argo CD keeps the cluster aligned with it.

Kafka platform complete

The local event platform is now declarative, observable, and ready for microservices to use through stable in-cluster endpoints.
