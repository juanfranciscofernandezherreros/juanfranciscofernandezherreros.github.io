Anotaciones de una API REST con Spring Boot

Un controlador REST puede acumular una cantidad inquietante de @Algo. La forma útil de aprenderlas no es memorizarlas: es entender qué parte del contrato HTTP controla cada una, qué framework la interpreta y cuándo no deberías usarla.

01

Qué significa “todas” en una API REST

En Java no existe una lista universal de “anotaciones REST”. Una API puede mezclar anotaciones de Spring MVC, Jakarta Validation, Spring Security, Jackson, OpenAPI, JPA, Lombok y librerías propias. Pretender enumerar todo el ecosistema produciría una lista enorme y poco útil.

Esta guía cubre las anotaciones que puedes encontrarte en la frontera HTTP de una API REST con Spring Boot: las que definen endpoints, leen una petición, producen una respuesta, validan datos, convierten errores, controlan CORS y autorización, serializan JSON o documentan el contrato.

Modelo mental: cuando veas una anotación, pregunta primero “¿quién la interpreta?”. @GetMapping pertenece a Spring MVC; @NotBlank a Jakarta Validation; @JsonIgnore a Jackson; @PreAuthorize a Spring Security; @Operation a OpenAPI/Swagger.

02

@Controller, @ResponseBody y @RestController

@Controller

Declara un componente MVC. Está pensado también para aplicaciones que resuelven vistas HTML; devolver un String puede significar “nombre de vista”.

@ResponseBody

Indica que el valor devuelto por un método debe escribirse en el cuerpo HTTP mediante un HttpMessageConverter, por ejemplo como JSON.

@RestController

Es una anotación compuesta: combina @Controller y @ResponseBody para todos los métodos del controlador.

@RequestMapping

Puede ponerse en la clase para definir la ruta base y reglas compartidas por todos los endpoints.

@RestController
@RequestMapping(path = "/api/orders", produces = MediaType.APPLICATION_JSON_VALUE)
public class OrderController {
    // todos los métodos escriben su retorno en la respuesta HTTP
}

@RestController es normalmente la elección correcta para una API JSON. Usar @Controller + @ResponseBody sigue siendo válido cuando quieres mezclar métodos REST y renderizado de vistas.

03

Rutas y verbos HTTP

@RequestMapping es la anotación general. Las variantes @GetMapping, @PostMapping, @PutMapping, @PatchMapping y @DeleteMapping son anotaciones compuestas que expresan el verbo HTTP de forma más legible.

AnotaciónUso habitualEjemplo
@GetMappingLeer uno o varios recursos.GET /api/orders/42
@PostMappingCrear un recurso o disparar una operación no idempotente.POST /api/orders
@PutMappingReemplazar el estado de un recurso de forma idempotente.PUT /api/orders/42
@PatchMappingModificar parcialmente un recurso.PATCH /api/orders/42
@DeleteMappingEliminar un recurso.DELETE /api/orders/42
@RequestMappingMapeo general o reglas más específicas.method = RequestMethod.HEAD
@PostMapping(
    consumes = MediaType.APPLICATION_JSON_VALUE,
    produces = MediaType.APPLICATION_JSON_VALUE
)
public ResponseEntity<OrderResponse> create(...) { ... }

Los atributos importantes de los mappings son path/value, method, params, headers, consumes y produces. Los cuatro últimos permiten que dos métodos compartan ruta pero se seleccionen por condiciones distintas.

@GetMapping(params = "status=PAID")
public List<OrderResponse> paidOrders() { ... }

@GetMapping(headers = "X-API-Version=2")
public List<OrderV2Response> listV2() { ... }

No uses el verbo como decoración. Elegir entre POST, PUT y PATCH forma parte del contrato de la API: afecta a idempotencia, caché, proxies, clientes y expectativas de reintento.

04

Cómo entra información en un endpoint

Una petición HTTP tiene varias zonas: path, query string, headers, cookies, body y partes multipart. Spring ofrece una anotación distinta para cada origen.

AnotaciónLeeEjemplo
@PathVariableVariable embebida en la ruta./orders/{id}
@RequestParamQuery parameter o datos de formulario.?page=0&size=20
@RequestHeaderHeader HTTP.X-Correlation-Id
@CookieValueCookie concreta.SESSION
@RequestBodyCuerpo completo deserializado.JSON → DTO
@RequestPartUna parte de una petición multipart.JSON + fichero
@ModelAttributeBinding desde parámetros/formulario a un objeto.Filtros complejos
@RequestAttributeAtributo añadido previamente al request.Dato de un filtro/interceptor
@SessionAttributeAtributo existente en sesión HTTP.Estado de sesión
@MatrixVariableParámetros matriciales dentro de un segmento./cars;color=red

@PathVariable

@GetMapping("/{id}")
public OrderResponse find(@PathVariable Long id) {
    return service.find(id);
}

Si el nombre del parámetro Java coincide con el placeholder y el proyecto conserva los nombres de parámetros en compilación, puedes omitir el nombre explícito. En código de librería o cuando quieres máxima claridad, @PathVariable("id") evita ambigüedades.

@RequestParam

@GetMapping
public Page<OrderResponse> search(
    @RequestParam(defaultValue = "0") int page,
    @RequestParam(defaultValue = "20") int size,
    @RequestParam(required = false) OrderStatus status
) { ... }

required = false hace el parámetro opcional. defaultValue proporciona un valor y, en la práctica, también elimina la obligación de enviarlo.

@RequestHeader y @CookieValue

public OrderResponse find(
    @RequestHeader("X-Correlation-Id") String correlationId,
    @RequestHeader(value = "Accept-Language", required = false) String language,
    @CookieValue(value = "experiment", required = false) String experiment
) { ... }

@RequestBody

@PostMapping
public ResponseEntity<OrderResponse> create(
    @Valid @RequestBody CreateOrderRequest request
) { ... }

Spring delega la lectura del body a un HttpMessageConverter. Con JSON, Jackson suele convertir el documento en tu DTO. @RequestBody no es “la anotación de JSON”: también puede trabajar con otros media types si existe un converter compatible.

Detalle importante: para formularios tradicionales, usa @RequestParam o @ModelAttribute. La propia documentación de Spring advierte que mezclar acceso a parámetros de formulario y lectura posterior con @RequestBody puede no ser fiable en Servlet.

@RequestPart para multipart

@PostMapping(path = "/{id}/invoice", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
public void uploadInvoice(
    @PathVariable Long id,
    @Valid @RequestPart("metadata") InvoiceMetadata metadata,
    @RequestPart("file") MultipartFile file
) { ... }

@RequestPart es especialmente útil cuando una parte debe deserializarse mediante converters —por ejemplo JSON— y otra es binaria.

05

Binding, fechas, números y reglas de conversión

@ModelAttribute

Construye un objeto y enlaza propiedades desde parámetros de la petición. En APIs REST aparece sobre todo en filtros complejos o endpoints que aceptan formularios.

public record OrderFilter(
    OrderStatus status,
    LocalDate from,
    LocalDate to
) {}

@GetMapping
public List<OrderResponse> search(@ModelAttribute OrderFilter filter) { ... }

@DateTimeFormat y @NumberFormat

public List<OrderResponse> search(
    @RequestParam
    @DateTimeFormat(iso = DateTimeFormat.ISO.DATE)
    LocalDate from
) { ... }

@DateTimeFormat y @NumberFormat pertenecen al sistema de conversión/formateo de Spring. Son útiles para valores que llegan como texto en path, query o formularios. Para fechas dentro de JSON, la configuración de Jackson —por ejemplo @JsonFormat— es otra capa distinta.

@InitBinder

@InitBinder permite personalizar el WebDataBinder de un controlador: conversión, editores y campos permitidos. Es potente, pero hoy suele ser mejor centralizar converters reutilizables que dispersar lógica de binding en controladores.

@InitBinder
void initBinder(WebDataBinder binder) {
    binder.setAllowedFields("status", "from", "to");
}
06

@Valid, @Validated y las constraints de Jakarta

El binding transforma datos. La validación decide si esos datos son aceptables. Son problemas diferentes.

@Valid

jakarta.validation.Valid activa la validación en cascada de un objeto. Es la opción habitual en un @RequestBody.

public record CreateOrderRequest(
    @NotBlank String customerId,
    @NotEmpty @Valid List<OrderLineRequest> lines,
    @Email String contactEmail
) {}

public record OrderLineRequest(
    @NotBlank String sku,
    @Positive int quantity
) {}

@Validated

org.springframework.validation.annotation.Validated integra Bean Validation con Spring y añade soporte para grupos de validación. Es útil cuando el mismo modelo tiene reglas distintas según el caso de uso.

interface OnCreate {}
interface OnUpdate {}

public record CustomerRequest(
    @NotBlank(groups = OnCreate.class) String externalId,
    @NotBlank String name
) {}

Constraints estándar que conviene reconocer

AnotaciónQué comprueba
@NotNull / @NullDebe ser no nulo / nulo.
@NotEmptyNo nulo y no vacío: String, colección, mapa o array.
@NotBlankTexto no nulo con al menos un carácter que no sea whitespace.
@Size(min,max)Tamaño de texto, colección, mapa o array.
@Min / @MaxLímite numérico entero.
@DecimalMin / @DecimalMaxLímite decimal configurable e inclusivo/exclusivo.
@Positive / @PositiveOrZeroValor positivo / positivo o cero.
@Negative / @NegativeOrZeroValor negativo / negativo o cero.
@DigitsNúmero máximo de dígitos enteros y decimales.
@PatternEl texto debe cumplir una expresión regular.
@EmailFormato de email según el provider de validación.
@Past / @PastOrPresentFecha pasada / pasada o presente.
@Future / @FutureOrPresentFecha futura / futura o presente.
@AssertTrue / @AssertFalseBoolean esperado.

@NotNull no implica “texto con contenido”. "" pasa @NotNull. Para cadenas de entrada de una API suele ser más correcto @NotBlank.

@Constraint para validaciones propias

@Target({ ElementType.FIELD, ElementType.PARAMETER })
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = SkuValidator.class)
public @interface ValidSku {
    String message() default "invalid SKU";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

Una constraint propia merece la pena cuando expresa una regla de dominio reutilizable. Si la validación necesita consultar base de datos, permisos o estado externo, normalmente ya no es una constraint de formato: probablemente pertenece a la capa de aplicación.

07

Cómo controlar la respuesta HTTP

@ResponseStatus

Fija un status HTTP en un método o en una excepción.

@PostMapping
@ResponseStatus(HttpStatus.CREATED)
public OrderResponse create(@Valid @RequestBody CreateOrderRequest request) {
    return service.create(request);
}

Para respuestas dinámicas —status, headers o body que cambian según el resultado— ResponseEntity<T> suele ser más explícito.

URI location = URI.create("/api/orders/" + created.id());
return ResponseEntity.created(location).body(created);

ResponseEntity no es una anotación. Es un tipo de respuesta. Conviene separarlo mentalmente de @ResponseStatus: una es metadata declarativa; el otro construye la respuesta en tiempo de ejecución.

08

Errores: @ExceptionHandler y los Advice

@ExceptionHandler

Declara un método capaz de transformar una o varias excepciones en una respuesta HTTP. Dentro de un controlador solo afecta a ese controlador.

@ExceptionHandler(OrderNotFoundException.class)
public ResponseEntity<ProblemDetail> handleNotFound(OrderNotFoundException ex) {
    ProblemDetail problem = ProblemDetail.forStatusAndDetail(
        HttpStatus.NOT_FOUND, ex.getMessage());
    return ResponseEntity.status(HttpStatus.NOT_FOUND).body(problem);
}

@ControllerAdvice y @RestControllerAdvice

@ControllerAdvice aplica métodos como @ExceptionHandler, @InitBinder y @ModelAttribute de forma transversal a varios controladores. @RestControllerAdvice combina ese comportamiento con @ResponseBody, por lo que encaja especialmente bien en APIs REST.

@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(OrderNotFoundException.class)
    ResponseEntity<ProblemDetail> notFound(OrderNotFoundException ex) {
        var problem = ProblemDetail.forStatusAndDetail(
            HttpStatus.NOT_FOUND, ex.getMessage());
        problem.setTitle("Order not found");
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(problem);
    }
}

@ResponseStatus en una excepción

@ResponseStatus(HttpStatus.NOT_FOUND)
public class OrderNotFoundException extends RuntimeException { ... }

Es conciso, pero acopla una excepción a HTTP. En aplicaciones grandes suele ser más flexible mantener excepciones de dominio independientes y traducirlas en un advice.

09

@CrossOrigin y CORS

@CrossOrigin permite configurar CORS sobre una clase o método.

@CrossOrigin(origins = "https://app.example.com")
@RestController
@RequestMapping("/api/orders")
public class OrderController { ... }

Sirve para reglas locales, pero cuando toda la API comparte política CORS suele ser más mantenible configurarla globalmente —y, si hay Spring Security, integrarla con la configuración de seguridad— en vez de repetir @CrossOrigin endpoint por endpoint.

CORS no es autenticación. Es una política aplicada por navegadores sobre peticiones cross-origin. No sustituye JWT, sesiones, OAuth 2.0 ni autorización del servidor.

Anotaciones de Jackson que cambian tu contrato JSON

Estas anotaciones no son de Spring MVC, pero aparecen constantemente en DTOs REST porque Jackson suele encargarse de serializar y deserializar JSON.

AnotaciónEfecto
@JsonPropertyCambia el nombre JSON o controla acceso de una propiedad.
@JsonIgnoreExcluye una propiedad de serialización/deserialización.
@JsonIgnorePropertiesIgnora varias propiedades o, opcionalmente, campos desconocidos.
@JsonIncludeDecide cuándo incluir valores nulos, vacíos, default, etc.
@JsonFormatControla formato de fechas, horas o números durante JSON mapping.
@JsonCreatorMarca constructor o factory usado para deserializar.
@JsonValueDefine la representación JSON de un objeto/enum.
@JsonViewPermite vistas de serialización diferentes.
@JsonTypeInfo / @JsonSubTypesSoporte para payloads polimórficos.
public record OrderResponse(
    @JsonProperty("order_id") Long id,
    @JsonInclude(JsonInclude.Include.NON_NULL) String trackingCode,
    @JsonFormat(pattern = "yyyy-MM-dd'T'HH:mm:ssXXX") OffsetDateTime createdAt
) {}

Decisión de arquitectura: evita exponer entidades JPA directamente como respuesta REST. DTOs separados hacen que anotaciones de persistencia, lazy loading y relaciones bidireccionales no dicten accidentalmente tu contrato JSON.

Anotaciones de seguridad

La autorización HTTP puede configurarse por rutas en SecurityFilterChain o por métodos. Para seguridad a nivel de método, Spring Security ofrece varias familias de anotaciones.

@EnableMethodSecurity

@Configuration
@EnableMethodSecurity
public class SecurityConfig { ... }

Activa la infraestructura de method security. El starter de Spring Security no activa por sí solo la autorización por anotaciones de método.

@PreAuthorize y @PostAuthorize

@PreAuthorize("hasAuthority('orders:write')")
@PostMapping
public OrderResponse create(...) { ... }

@PostAuthorize("returnObject.customerId() == authentication.name")
@GetMapping("/{id}")
public OrderResponse find(@PathVariable Long id) { ... }

@PreAuthorize decide antes de ejecutar. @PostAuthorize decide después y puede inspeccionar el valor devuelto. En APIs de negocio suele ser preferible proteger servicios además de —o en lugar de— solo controladores, para no depender de una única vía de entrada.

@PreFilter y @PostFilter

Filtran colecciones de entrada o salida según expresiones de autorización. Son potentes pero pueden ocultar costes o reglas de filtrado; para grandes colecciones es mejor aplicar seguridad en la consulta que cargar datos para descartarlos después.

@Secured y JSR-250

AnotaciónNota
@SecuredOpción legacy de Spring Security; requiere habilitarla explícitamente.
@RolesAllowedEstándar Jakarta/JSR-250 para roles.
@PermitAllPermite acceso al método en el modelo JSR-250.
@DenyAllDeniega acceso al método.

@AuthenticationPrincipal

@GetMapping("/me/orders")
public List<OrderResponse> mine(
    @AuthenticationPrincipal Jwt jwt
) {
    return service.findByCustomer(jwt.getSubject());
}

Inyecta el principal autenticado en el argumento del controlador. Evita tener que acceder manualmente al SecurityContextHolder en cada endpoint.

12

Anotaciones de OpenAPI / Swagger

Si usas springdoc-openapi, las anotaciones de io.swagger.v3.oas.annotations enriquecen el contrato generado. No cambian cómo Spring ejecuta el endpoint: cambian cómo se documenta.

AnotaciónQué documenta
@TagAgrupa operaciones.
@OperationResumen, descripción, operationId, seguridad, etc.
@ParameterParámetro path/query/header/cookie.
@ApiResponseUna respuesta HTTP posible.
@ApiResponsesConjunto de respuestas.
@ContentMedia type y schema de una request/response.
@SchemaModelo, propiedades, ejemplos, formatos y restricciones.
@ArraySchemaSchema de arrays/colecciones.
@ExampleObjectEjemplos explícitos de payload.
@SecurityRequirementEsquema de seguridad requerido por una operación.
@HiddenOculta una operación o schema de la documentación.
@Operation(summary = "Create an order")
@ApiResponses({
    @ApiResponse(responseCode = "201", description = "Order created"),
    @ApiResponse(responseCode = "400", description = "Invalid request")
})
@PostMapping
public ResponseEntity<OrderResponse> create(...) { ... }

Ojo con el nombre duplicado: Spring tiene org.springframework.web.bind.annotation.RequestBody y OpenAPI tiene io.swagger.v3.oas.annotations.parameters.RequestBody. No son la misma anotación. Cuando necesites ambas, revisa imports y usa el nombre cualificado si evita confusión.

Documenta lo que el código no puede inferir bien: significado de errores, ejemplos, semántica de campos y requisitos de seguridad. Repetir en anotaciones toda la información que ya se deduce del método crea documentación ruidosa y fácil de desincronizar.

13

Anotaciones menos frecuentes en una REST API

@SessionAttributes

Promueve atributos del modelo a sesión durante un flujo MVC. Existe, pero en una REST API stateless suele ser una señal para revisar el diseño.

@ModelAttribute en métodos

Puede precargar atributos antes de ejecutar handlers. Es habitual en MVC con vistas; menos en controladores REST.

@CookieValue

Útil si una cookie forma parte real del contrato. En APIs de máquina a máquina suele aparecer poco.

@MatrixVariable

Spring lo soporta, pero los matrix parameters son poco comunes en APIs públicas modernas.

Que Spring soporte una anotación no significa que debas usarla. La API más mantenible suele utilizar un subconjunto pequeño y consistente.

Ejemplo completo: un controlador de producción razonable

Este ejemplo junta las piezas sin convertir el controlador en un catálogo de anotaciones:

@RestController
@RequestMapping(path = "/api/orders", produces = MediaType.APPLICATION_JSON_VALUE)
@Tag(name = "Orders")
public class OrderController {

    private final OrderService service;

    public OrderController(OrderService service) {
        this.service = service;
    }

    @Operation(summary = "Get an order")
    @GetMapping("/{id}")
    @PreAuthorize("hasAuthority('orders:read')")
    public OrderResponse find(
        @PathVariable @Positive Long id,
        @RequestHeader(value = "X-Correlation-Id", required = false)
        String correlationId
    ) {
        return service.find(id);
    }

    @Operation(summary = "Search orders")
    @GetMapping
    public Page<OrderResponse> search(
        @RequestParam(required = false) OrderStatus status,
        @RequestParam(defaultValue = "0") @PositiveOrZero int page,
        @RequestParam(defaultValue = "20") @Min(1) @Max(100) int size
    ) {
        return service.search(status, page, size);
    }

    @Operation(summary = "Create an order")
    @PostMapping(consumes = MediaType.APPLICATION_JSON_VALUE)
    @PreAuthorize("hasAuthority('orders:write')")
    public ResponseEntity<OrderResponse> create(
        @Valid @RequestBody CreateOrderRequest request
    ) {
        OrderResponse created = service.create(request);
        URI location = URI.create("/api/orders/" + created.id());
        return ResponseEntity.created(location).body(created);
    }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    @PreAuthorize("hasAuthority('orders:write')")
    public void delete(@PathVariable Long id) {
        service.delete(id);
    }
}

Observa lo que no está en el controlador: persistencia, transacciones, entidades JPA y lógica de negocio. Una API REST usa muchas anotaciones, pero la frontera HTTP no debería absorber responsabilidades de todas las capas.

15

Errores que aparecen en proyectos reales

Entidades JPA como DTO

Mezcla @Entity, relaciones y Jackson en el mismo objeto. Termina exponiendo campos internos, ciclos o lazy loading.

@RequestParam para todo

Un comando complejo de creación suele ser más estable como DTO en @RequestBody que como doce query params.

@NotNull mal elegido

Para un texto obligatorio, @NotBlank suele representar mejor la intención.

@CrossOrigin("*") sin pensar

Soluciona rápido un problema del navegador, pero puede esconder una política CORS mal definida.

Seguridad solo en controller

Si el servicio puede invocarse desde jobs, listeners o otra interfaz, la regla de autorización puede quedar fuera.

Swagger como copia del código

Duplicar cada tipo y status manualmente produce documentación que envejece peor que el propio endpoint.

La regla que evita memorizar 50 anotaciones

Piensa en el viaje de la petición: mapping → extracción de datos → conversión → validación → autorización → lógica de aplicación → serialización → status/headers → documentación.

Una anotación REST útil casi siempre interviene en uno de esos pasos. Si sabes en qué paso estás, normalmente puedes deducir qué familia de anotaciones necesitas.

También ayuda separar contrato de infraestructura. @GetMapping, @RequestBody o @ResponseStatus describen claramente la frontera HTTP. @Transactional, @Entity o @Cacheable pueden aparecer en la misma aplicación, pero no son “anotaciones REST”: pertenecen a otras responsabilidades.
