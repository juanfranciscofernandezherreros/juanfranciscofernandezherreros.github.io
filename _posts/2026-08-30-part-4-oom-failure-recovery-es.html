El ejercicio

Este es un ejercicio de fallo controlado, no un patrón de fuga de memoria que deba permanecer en producción. El servicio arranca con un componente que añade arrays de bytes de 1MiB a una lista retenida. Kubernetes limita el contenedor a 100Mi, por lo que el pod termina muriendo y su controlador lo reinicia.

MemoryOomProbe.java — código experimental
List<byte[]> retainedMemory = new ArrayList<>();
while (true) {
    retainedMemory.add(new byte[1024 * 1024]);
}

Ejecuta esto únicamente en un clúster local desechable. La lista retiene intencionadamente cada asignación. No expongas este interruptor en producción.

01

El heap no es toda la memoria del contenedor

La primera sorpresa fue que -Xmx no predecía completamente el resultado. Un proceso Java también consume metaspace, caché de código, stacks de hilos, buffers directos, estructuras del GC, librerías compartidas y memoria nativa de la JVM. Kubernetes aplica el límite al total del cgroup, no solo al heap de Java.

OOMKilled / 137

El kernel mata el contenedor cuando la memoria total supera 100Mi. Java puede no llegar a imprimir una excepción.

Java OOM / 1

La JVM detecta el agotamiento dentro de un área gestionada y sale con una excepción.

Running / 0

Los límites del heap y memoria nativa dejan margen suficiente bajo el límite del contenedor.

La distinción importa al diagnosticar. Un kubectl logs puede terminar abruptamente tras un OOM kill; la evidencia autoritativa está en lastState.terminated.reason y en el código de salida.

kubectl get pod -n godbyemicroservices -l app=godbyemicroservices \
  -o jsonpath="{.items[0].status.containerStatuses[0].lastState.terminated.reason} {.items[0].status.containerStatuses[0].lastState.terminated.exitCode}{'\n'}"

02

Por qué Argo puede estar Synced con el pod roto

Argo CD responde a dos preguntas distintas. Sync comprueba si los objetos vivos de Kubernetes coinciden con Git. Health comprueba si esos objetos funcionan. Un Deployment aplicado perfectamente cuyo pod no deja de fallar puede estar a la vez Synced y Degraded.

Synced

El Deployment del clúster coincide con el YAML almacenado en Git.

Degraded

El Deployment no consigue que su réplica solicitada esté disponible.

Operation: Succeeded

Aplicar YAML válido tuvo éxito aunque el workload resultante fallara después.

Añadir progressDeadlineSeconds: 30 hizo que Kubernetes informara antes de ProgressDeadlineExceeded. Mejoró la señal de salud, pero no convirtió retroactivamente una aplicación correcta de manifiestos en una operación de sincronización fallida.

03

Hacer fallar la operación intencionadamente

Cuando el requisito concreto es “mostrar la operación de sincronización como Failed”, Argo necesita una tarea de sync que pueda devolver un fallo. Para el ejercicio, un Job PreSync ejecutó la misma imagen con el mismo límite de 100Mi y backoffLimit: 0.

startup-check.yaml — puerta temporal de fallo
apiVersion: batch/v1
kind: Job
metadata:
  name: godbyemicroservices-startup-check
  annotations:
    argocd.argoproj.io/hook: PreSync
spec:
  backoffLimit: 0
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: startup-check
          image: godbyemicroservices:local
          resources:
            limits:
              memory: 100Mi

El pod del hook terminó como OOMKilled con código 137. El Job alcanzó BackoffLimitExceeded y Argo registró operation=Failed con “one or more synchronization tasks completed unsuccessfully”. Esto demuestra la diferencia: la salud del workload afecta a Health; una tarea de sincronización fallida afecta a la fase de la operación.

04

Recuperación: retirar el fallo, no el límite

Eliminar la fuga deliberada

El experimento local MemoryOomProbe, su prueba y la propiedad OOM_ON_STARTUP se borraron antes de publicar el servicio. La aplicación arranca únicamente Spring y su único GodbyeMicroservicesController.

Eliminar la puerta experimental

Se retiraron el Job PreSync y el deadline corto de gitops-config. El Deployment conserva replicas: 1.

Mantener la frontera de 100Mi

El límite del contenedor no cambió. Se definieron valores conservadores para heap, metaspace, caché de código, memoria directa, stacks, GC y compilación tiered para que Spring quepa dentro del cgroup.

Reconstruir y reconciliar

Se reconstruyó la imagen, se cargó en kind y se recreó el pod. Argo reconcilió el commit GitOps 4fc7726.

Dockerfile — comando JVM final
ENTRYPOINT ["java", "-Xmx36m", "-XX:MaxMetaspaceSize=44m",
  "-XX:ReservedCodeCacheSize=8m", "-XX:MaxDirectMemorySize=4m",
  "-Xss256k", "-XX:+UseSerialGC", "-XX:TieredStopAtLevel=1",
  "-jar", "app.jar"]

Estos valores son específicos de este pequeño servicio de demostración. En un workload real hay que medir RSS máximo, tráfico, número de hilos, comportamiento del GC y margen de arranque antes de decidir límites de producción.
