Principios SOLID en Java

Cinco principios de diseño que ayudan a mantener el código orientado a objetos comprensible, comprobable y adaptable cuando cambian los requisitos.

01

¿Qué significa SOLID?

SOLID reúne cinco principios de diseño orientado a objetos: responsabilidad única, abierto/cerrado, sustitución de Liskov, segregación de interfaces e inversión de dependencias. Orientan la distribución de responsabilidades y dependencias para que un cambio tenga un impacto pequeño y predecible.

SOLID no es una regla que todas las clases deban cumplir de forma mecánica. Es un vocabulario para reconocer problemas de diseño. Conviene aplicar un principio cuando hace más seguro un cambio o simplifica las pruebas; las abstracciones innecesarias también pueden dificultar la comprensión de un sistema pequeño.

S

Principio de responsabilidad única

Un módulo debe tener una sola razón para cambiar. Se trata de agrupar el código por responsabilidad, no de obligar a que cada clase tenga un único método. Si el cálculo de facturas y el envío de correos cambian por motivos de negocio diferentes, deben pertenecer a componentes distintos.

public class ServicioFacturas {
    private final RepositorioFacturas repositorio;
    private final EnviadorCorreo enviadorCorreo;

    public Factura crear(Pedido pedido) {
        Factura factura = Factura.desde(pedido);
        repositorio.guardar(factura);
        enviadorCorreo.enviar(factura);
        return factura;
    }
}

La coordinación permanece en ServicioFacturas, mientras que la persistencia y el envío tienen responsabilidades propias. Una señal de alerta es una clase que cambia cuando se modifican aspectos no relacionados como la base de datos, los precios, el formato o las notificaciones.

O

Principio abierto/cerrado

Las entidades de software deben estar abiertas a la extensión y cerradas a la modificación. El nuevo comportamiento debería poder añadirse mediante una abstracción estable en lugar de editar repetidamente un condicional cada vez más grande.

public interface PoliticaDescuento {
    BigDecimal aplicar(BigDecimal precio);
}

public final class DescuentoVip implements PoliticaDescuento {
    public BigDecimal aplicar(BigDecimal precio) {
        return precio.multiply(new BigDecimal("0.90"));
    }
}

Un nuevo descuento puede implementar PoliticaDescuento sin cambiar la calculadora que la utiliza. Esto no significa que el código existente nunca pueda modificarse; significa proteger el comportamiento estable frente a cada nueva variante.

L

Principio de sustitución de Liskov

Una implementación debe poder utilizarse donde se espera su abstracción sin romper el comportamiento prometido. Un subtipo debe respetar el contrato: no debería exigir precondiciones más fuertes, entregar resultados más débiles ni introducir fallos inesperados.

public interface MetodoPago {
    Recibo pagar(Dinero importe);
}

public final class PagoTarjeta implements MetodoPago {
    public Recibo pagar(Dinero importe) {
        return pasarela.cobrar(importe);
    }
}

Si una implementación lanza UnsupportedOperationException en llamadas normales permitidas por MetodoPago, probablemente la abstracción sea incorrecta. LSP trata sobre compatibilidad de comportamiento, no solo sobre compartir un tipo padre.

I

Principio de segregación de interfaces

Los clientes no deben depender de métodos que no utilizan. Es preferible definir interfaces pequeñas y centradas en un rol en vez de una gran interfaz que obligue a implementar métodos sin sentido.

public interface Imprimible {
    void imprimir(Documento documento);
}

public interface Escaneable {
    Documento escanear();
}

Una impresora básica implementa solamente Imprimible; un dispositivo multifunción puede implementar ambas interfaces. Los métodos vacíos o que siempre lanzan una excepción porque la clase no puede cumplir parte de la interfaz son señales de alerta.

D

Principio de inversión de dependencias

La política de alto nivel no debe depender directamente de detalles de bajo nivel; ambas deben depender de abstracciones. Normalmente, la necesidad del negocio define la abstracción y la infraestructura proporciona una implementación.

public interface RepositorioPedidos {
    void guardar(Pedido pedido);
}

public class ServicioCompra {
    private final RepositorioPedidos repositorio;

    public ServicioCompra(RepositorioPedidos repositorio) {
        this.repositorio = repositorio;
    }
}

ServicioCompra no sabe si los pedidos se almacenan con JPA, JDBC o en memoria. La inyección por constructor es un mecanismo que facilita DIP, pero utilizar una interfaz no garantiza por sí solo un buen diseño.

07

Cómo trabajan juntos

Cambio

SRP limita por qué cambia un módulo; OCP permite añadir variantes detrás de contratos estables.

Contratos

LSP mantiene fiables las implementaciones; ISP conserva cada contrato centrado en sus clientes.

Dependencias

DIP orienta las dependencias del código hacia abstracciones del negocio y no hacia detalles de infraestructura.

Equilibrio

Utiliza evidencias de cambio y acoplamiento. No añadas una interfaz o un patrón si no resuelve un problema de diseño actual.

Prueba práctica: cuando cambia un requisito, comprueba cuántos archivos no relacionados deben modificarse, si el comportamiento puede probarse de forma aislada y si las implementaciones siguen respetando sus contratos.

08

Respuesta para la entrevista

«SOLID reúne cinco principios de diseño orientado a objetos. SRP separa las razones para cambiar; OCP favorece extender el comportamiento mediante abstracciones estables; LSP exige que las implementaciones respeten sus contratos; ISP mantiene las interfaces pequeñas y específicas para sus clientes; y DIP hace que la política de alto nivel dependa de abstracciones en lugar de detalles de infraestructura. Juntos reducen el acoplamiento y facilitan los cambios y las pruebas. Los aplico de forma pragmática porque las abstracciones adicionales también tienen un coste».

Una respuesta sólida explica el resultado de diseño y aporta un ejemplo concreto. Enumerar los cinco principios sin mostrar cómo afectan a los cambios es menos útil que describir una refactorización real.
