Error handling in Spring Boot

An API is not well designed just because its happy path returns 200 OK. Quality shows up when something fails: which HTTP code is returned, what the client sees, what gets logged, and whether every controller follows the same contract.

The real problem is not throwing exceptions

The real problem is turning failures from different layers into a stable HTTP contract. A Java exception is an internal mechanism. A REST error is part of the public API. Mixing both concepts usually leads to endpoints that return 500 for everything, inconsistent messages, or implementation details that should never leave the process.

We will build a complete strategy around a small order domain: business errors, missing resources, conflicts, request validation, and unexpected failures. The goal is to keep controllers focused on the happy path while every error follows one consistent format.

01

Three error layers you should not mix

Domain

Expresses what went wrong for the business: missing order, invalid transition, insufficient stock, or stale version.

Application

Knows which use case was running and propagates a meaningful failure rather than raw infrastructure details.

HTTP

Translates that failure into a status code, headers, and an external representation.

Infrastructure

Can raise SQL exceptions, timeouts, network failures or availability errors that should rarely be exposed literally.

@Service
public class OrderService {

    public Order findById(UUID id) {
        return repository.findById(id)
            .orElseThrow(() -> new OrderNotFoundException(id));
    }
}

OrderNotFoundException does not need to know HTTP exists. That keeps the service reusable and avoids polluting business logic with HttpStatus or ResponseEntity.

Mental model: the service describes the failure; the web layer decides how to represent it outside the process.

02

Choose the HTTP status before writing the handler

StatusWhen it fitsExample
400 Bad RequestThe request cannot be interpreted or violates input constraints.Malformed JSON or invalid parameter format.
401 UnauthorizedValid authentication is missing.Missing or invalid token.
403 ForbiddenThe caller is authenticated but not allowed to perform the operation.A regular user invokes an admin operation.
404 Not FoundThe requested resource does not exist or must not be revealed.GET /orders/{id} with an unknown id.
409 ConflictThe request is valid but conflicts with current state.Confirming a cancelled order, duplicate email, optimistic locking.
422 Unprocessable ContentThe syntax is valid but the content cannot be processed semantically.A business rule violation when you want to distinguish it from 400.
500 Internal Server ErrorUnexpected server failure.Bug or unclassified exception.
503 Service UnavailableA critical dependency or service is temporarily unavailable.A downstream outage explicitly translated by the API.

Do not automatically map every business exception to 400. A missing resource is 404; a transition incompatible with current state is often better expressed as 409.

03

@ExceptionHandler: handle one exception

@ExceptionHandler declares a method that can handle specific exceptions raised while processing a request. It can live inside one controller or inside global advice.

@RestController
@RequestMapping("/api/orders")
public class OrderController {

    @ExceptionHandler(OrderNotFoundException.class)
    ResponseEntity<ProblemDetail> handleNotFound(OrderNotFoundException ex) {
        ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.NOT_FOUND);
        problem.setTitle("Order not found");
        problem.setDetail(ex.getMessage());
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(problem);
    }
}

This works, but if five controllers can raise the same exception, duplicating the HTTP translation five times is the wrong abstraction.

04

@RestControllerAdvice: one global policy

@RestControllerAdvice combines the global scope of @ControllerAdvice with response-body semantics. Spring discovers the bean and can apply its @ExceptionHandler methods across controllers.

@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail handleOrderNotFound(OrderNotFoundException ex) {
        ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.NOT_FOUND);
        problem.setTitle("Order not found");
        problem.setDetail(ex.getMessage());
        return problem;
    }

    @ExceptionHandler(OrderStateConflictException.class)
    ProblemDetail handleConflict(OrderStateConflictException ex) {
        ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.CONFLICT);
        problem.setTitle("Order state conflict");
        problem.setDetail(ex.getMessage());
        return problem;
    }
}

The controller goes back to describing the happy path, without repeated try/catch blocks.

05

ProblemDetail and RFC 9457

Spring Framework includes ProblemDetail for the standardized Problem Details for HTTP APIs format defined by RFC 9457.

FieldMeaning
typeURI identifying the problem type.
titleShort, stable problem title.
statusHTTP status code.
detailExplanation specific to this occurrence.
instanceURI identifying the request or occurrence.
 
ProblemDetail problem = ProblemDetail.forStatusAndDetail(
    HttpStatus.NOT_FOUND,
    "Order 7c... does not exist"
);
problem.setTitle("Order not found");
problem.setType(URI.create("https://example.com/problems/order-not-found"));
problem.setProperty("errorCode", "ORDER_NOT_FOUND");
HTTP/1.1 404 Not Found · application/problem+json
{
  "type": "https://example.com/problems/order-not-found",
  "title": "Order not found",
  "status": 404,
  "detail": "Order 7c... does not exist",
  "instance": "/api/orders/7c...",
  "errorCode": "ORDER_NOT_FOUND"
}

Spring can render ProblemDetail as application/problem+json. Spring MVC web exceptions also implement the ErrorResponse contract, which helps keep framework-generated errors consistent.

06

Design stable error codes for clients

The human-readable detail text may change or be translated. A frontend should not contain logic such as if (message.equals("Order already cancelled")).

public enum ApiErrorCode {
    ORDER_NOT_FOUND,
    ORDER_STATE_CONFLICT,
    VALIDATION_FAILED
}

Expose a stable external code and keep implementation class names private.

Validation: when @Valid fails

public record CreateOrderRequest(
    @NotBlank String customerId,
    @NotEmpty List<@Valid OrderLineRequest> lines
) {}
@PostMapping
@ResponseStatus(HttpStatus.CREATED)
public OrderResponse create(
    @Valid @RequestBody CreateOrderRequest request
) {
    return mapper.toResponse(service.create(request));
}

For object binding errors, one important Spring MVC exception is MethodArgumentNotValidException. A useful API translates its field errors into an explicit list.

@RestControllerAdvice
public class ApiExceptionHandler extends ResponseEntityExceptionHandler {

    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex,
            HttpHeaders headers,
            HttpStatusCode status,
            WebRequest request) {

        ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
        problem.setTitle("Validation failed");
        problem.setDetail("One or more request fields are invalid");
        problem.setProperty("errorCode", "VALIDATION_FAILED");

        List<Map<String, String>> errors = ex.getBindingResult()
            .getFieldErrors()
            .stream()
            .map(error -> Map.of(
                "field", error.getField(),
                "message", Objects.requireNonNullElse(
                    error.getDefaultMessage(), "Invalid value")
            ))
            .toList();

        problem.setProperty("errors", errors);
        return handleExceptionInternal(ex, problem, headers, status, request);
    }
}

Important nuance: method-level validation can raise HandlerMethodValidationException. Do not assume every MVC validation failure becomes MethodArgumentNotValidException.

08

ResponseEntityExceptionHandler: do not reinvent Spring MVC errors

ResponseEntityExceptionHandler is a convenient base class for global handling of Spring MVC exceptions. Extend it when you want one place for framework errors plus custom handlers for domain failures.

@RestControllerAdvice
public class ApiExceptionHandler extends ResponseEntityExceptionHandler {

    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail handleOrderNotFound(OrderNotFoundException ex) {
        return problem(
            HttpStatus.NOT_FOUND,
            "Order not found",
            ex.getMessage(),
            "ORDER_NOT_FOUND"
        );
    }
}
09

The Exception fallback must not leak the real cause

private static final Logger log = LoggerFactory.getLogger(ApiExceptionHandler.class);

@ExceptionHandler(Exception.class)
ProblemDetail handleUnexpected(Exception ex, HttpServletRequest request) {
    String errorId = UUID.randomUUID().toString();

    log.error("Unhandled API error id={} method={} path={}",
        errorId, request.getMethod(), request.getRequestURI(), ex);

    ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.INTERNAL_SERVER_ERROR);
    problem.setTitle("Internal server error");
    problem.setDetail("An unexpected error occurred");
    problem.setProperty("errorCode", "INTERNAL_ERROR");
    problem.setProperty("errorId", errorId);
    return problem;
}

The client gets a correlation id. Server logs keep the stack trace and technical context.

Never expose stack traces, SQL, table names, filesystem paths, secrets, tokens, internal hostnames, or raw infrastructure exception messages without review.

Complete example: clean domain, consistent API

public class OrderNotFoundException extends RuntimeException {
    public OrderNotFoundException(UUID id) {
        super("Order " + id + " does not exist");
    }
}

public class OrderStateConflictException extends RuntimeException {
    public OrderStateConflictException(UUID id, OrderStatus status) {
        super("Order " + id + " cannot be confirmed from " + status);
    }
}
@Service
public class OrderService {
    public Order findById(UUID id) {
        return repository.findById(id)
            .orElseThrow(() -> new OrderNotFoundException(id));
    }

    @Transactional
    public Order confirm(UUID id) {
        Order order = findById(id);
        if (order.getStatus() != OrderStatus.PENDING) {
            throw new OrderStateConflictException(id, order.getStatus());
        }
        order.confirm();
        return order;
    }
}
@RestControllerAdvice
public class ApiExceptionHandler extends ResponseEntityExceptionHandler {

    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail handleNotFound(OrderNotFoundException ex) {
        return problem(HttpStatus.NOT_FOUND,
            "Order not found", ex.getMessage(), "ORDER_NOT_FOUND");
    }

    @ExceptionHandler(OrderStateConflictException.class)
    ProblemDetail handleConflict(OrderStateConflictException ex) {
        return problem(HttpStatus.CONFLICT,
            "Order state conflict", ex.getMessage(), "ORDER_STATE_CONFLICT");
    }
}

The key benefit is not fewer lines. Each layer answers a different question: domain code explains what failed, the service owns the use case, and the advice owns the HTTP contract.

12

What about @ResponseStatus?

You can annotate an exception directly with @ResponseStatus(HttpStatus.NOT_FOUND). It is convenient for small applications, but it couples the exception to HTTP. If the same exception later appears in Kafka, batch processing, or a CLI, that coupling becomes less attractive.

Practical rule: for small APIs it may be enough. For reusable domain layers or a rich consistent error contract, translating exceptions in advice scales better.

13

Common mistakes

try/catch in every endpoint

Duplicates HTTP policy and hides the happy path.

200 with {"success": false}

Breaks HTTP semantics and hurts clients, metrics and proxies.

500 for every failure

Makes client errors, business conflicts and server bugs indistinguishable.

Messages as contract

Human text changes; clients should depend on stable error codes.

Leaking ex.getMessage()

Technical exceptions may contain sensitive internal information.

One error DTO per controller

Forces consumers to learn multiple formats for one API.

14

How I would explain it in an interview

“In a Spring Boot API I separate domain exceptions from their HTTP representation. Controllers stay focused on the happy path, while a @RestControllerAdvice with @ExceptionHandler translates failures into consistent HTTP statuses. I prefer ProblemDetail for the response body because it follows RFC 9457, and I add stable error codes when clients need programmatic behavior. Validation, conflicts and missing resources are explicit, while a final 500 handler logs the stack trace without exposing implementation details.”

15

Production checklist

  • The same problem produces the same status and body shape across endpoints.
  • The error body uses a documented structure.
  • Clients depend on stable errorCode values, not human-readable messages.
  • Validation responses identify concrete fields when useful.
  • 500 responses do not leak stack traces or infrastructure details.
  • Unexpected failures include a correlation id for investigation.
  • Logging severity distinguishes expected behavior from operational incidents.
  • Error paths are covered by integration/contract tests, not only happy paths.
