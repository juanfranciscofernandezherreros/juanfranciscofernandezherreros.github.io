Hello World con ArgoCD

Editas un fichero, lo subes a GitHub, y unos segundos después una app real está corriendo en un clúster real — nadie escribió un comando de despliegue. 00

El modelo mental de 60 segundos

Piénsalo como la cocina de un restaurante que nunca deja de revisar su propio recetario.

Todavía sin jerga — solo la forma de la idea. Cada término técnico de más abajo corresponde a una de estas tres cosas.

El recetario

Lo que debería existir

Una descripción escrita y versionada del plato — ingredientes, cantidades, pasos. Cualquiera puede leerla y saber exactamente qué se supone que se está cocinando.

en la vida real: el repo de Git
El chef principal

No deja de comprobar

Pasa por el recetario cada pocos minutos. Si la cocina no coincide con el libro, lo arregla — sin excepciones, sin "más o menos vale".

en la vida real: ArgoCD
La cocina

Donde de verdad se cocina

Fogones, zonas de preparación, platos. El lugar físico donde el plato se hace y se mantiene caliente, listo para servir.

en la vida real: el clúster de Kubernetes

Esa es toda la idea. Nunca entras en la cocina a cocinar a mano — editas el recetario, y el chef se asegura de que la cocina se ponga al día. La sección 03 le da a este bucle su nombre real y su comportamiento real.

01

Conoce las piezas

Las mismas ideas de arriba, ahora con sus nombres reales — en el orden en que realmente te las vas a encontrar.

Dónde vive tu código

Git
Una herramienta que guarda un historial de cada cambio en tus ficheros. Cada cambio guardado es un commit — siempre puedes volver a uno anterior.
Repositorio (repo)
Una carpeta de código controlada por Git, con su propio historial. Este proyecto usa dos: hello-world-argocd y gitops-config.
GitHub
Una web que aloja la copia "oficial" de un repo en la nube. git push sube tus commits ahí; git pull los baja.
Commit
Una foto fija de tus cambios, con un mensaje explicando qué y por qué. Es la unidad más pequeña de historial en Git.

Empaquetar la app

Microservicio
Una app pequeña e independiente que hace una sola cosa — aquí, responder Hello World — y se despliega por separado.
Docker
Empaqueta una app junto con todo lo que necesita para correr (Java, librerías) en una caja cerrada que se comporta igual en cualquier máquina.
Imagen de Docker
La "plantilla" empaquetada y congelada (hello-world:local en este caso). Se construye una vez con docker build.
Contenedor
Una imagen de Docker que está corriendo de verdad. Puedes arrancar varios contenedores desde la misma imagen.

Ejecutarlo en Kubernetes (la cocina)

Kubernetes (k8s)
Un sistema que mantiene vivos muchos contenedores: si uno se cae, lo reinicia; si pides 3 copias, vigila que siempre haya 3.
Clúster
El conjunto de máquinas (nodos) donde corre Kubernetes. El nuestro se llama hello-world.
kind
Una herramienta que simula un clúster de Kubernetes completo dentro de Docker, en tu propio portátil — sin nube, ideal para aprender y probar.
kubectl
El comando que usas para hablar con Kubernetes: crear, listar o borrar cosas en el clúster (por ejemplo, kubectl get pods).
Namespace
Una "carpeta" lógica dentro del clúster que agrupa los recursos de un proyecto. Hello-world vive en el namespace hello-world.
Pod
Lo más pequeño que corre en Kubernetes. Normalmente envuelve un único contenedor.
Deployment
La receta que le dice a Kubernetes qué imagen usar y cuántas copias (réplicas) del Pod mantener siempre vivas.
Service
Una "puerta" fija para llegar a los Pods, aunque se reinicien y sus direcciones internas cambien por debajo.
Manifiesto / YAML
El fichero de texto que describe lo que quieres que exista (un Deployment, un Service...). Es el formulario de pedido que Kubernetes rellena.

Se despliega solo (el chef principal)

ArgoCD
Una aplicación que vive dentro del propio clúster, vigila un repo de Git, y aplica cualquier cambio que vea ahí — sola.
GitOps
La práctica de tratar Git como la única fuente de verdad: nunca tocas el clúster a mano, editas el repo y una herramienta (Argo) lo aplica.
Application (de Argo)
El manifiesto que le dice a Argo "vigila este repo, esta carpeta, y despliégalo en este namespace" — ver applications/hello-world.yaml.
Sync / selfHeal / prune
Las tres acciones de reconciliación de Argo — explicadas en detalle en la sección 03.
02

Arquitectura — tres piezas independientes

Ninguna de las tres sabe construir a las otras dos. Solo se comunican a través de Git y de la API de Kubernetes.

Repo de código

hello-world-argocd

Java 21 / Spring Boot 3.2. Un endpoint, GET /hello. No contiene ni un manifiesto de Kubernetes ni configuración de Argo.

github.com/.../hello-world-argocd →
Repo de configuración

gitops-config

El "recetario": manifiestos de Deployment/Service más el objeto Application que registra el servicio en Argo.

github.com/.../gitops-config →
el Deployment de gitops-config referencia el nombre de imagen que produce el Dockerfile de hello-world-argocd
Dentro del clúster (kind-hello-world)

ArgoCD → namespace hello-world

Argo lee gitops-config, lo compara contra el estado real del clúster, y aplica la diferencia. El resultado: el Deployment hello-world, corriendo en su propio namespace.

03

El bucle de reconciliación

Git es la única fuente de verdad. Nadie ejecuta nunca kubectl apply a mano — editas el repo, y Argo corrige la diferencia solo.

sync
El repo tiene algo que el clúster no tiene → Argo lo crea.
prune
El clúster tiene algo que ya no está en el repo → Argo lo borra.
selfHeal
Alguien edita algo a mano en el clúster (kubectl edit) → Argo lo revierte para que vuelva a coincidir con Git.
refresh
Cada ~3 minutos, o bajo demanda, Argo vuelve a comparar repo contra clúster aunque nada haya cambiado.
04

Levantar todo — tras un reinicio, o desde cero

La sección 05 asume que el clúster y ArgoCD ya existen. Aquí tienes cómo llegar ahí de verdad, en una máquina nueva o después de cerrar Docker Desktop.

"Iniciar" Argo y "configurar" Argo son dos cosas distintas

Instalarlo (los comandos de abajo) es solo aplicar un manifiesto de Kubernetes — ArgoCD no es un programa que se lanza, es un puñado de Deployments y un StatefulSet que Kubernetes programa igual que cualquier otra app. En cuanto esos pods están en Running, Argo ya está "iniciado" — y sin vigilar nada todavía.

Configurar qué vigila es un paso aparte: crear un recurso Application (applications/hello-world.yaml, aplicado en el camino "empezando desde cero" de abajo). Esa es la única "configuración" que toca esta guía — los dos ConfigMaps que configuran el comportamiento del propio ArgoCD (argocd-cm, argocd-rbac-cm) se dejan con sus valores por defecto, algo normal para una instalación de este tamaño.

solo reanudando

El clúster todavía existe — Docker Desktop (o la máquina) simplemente estuvo cerrado un rato.

1 You Arranca Docker Desktop y espera a que su motor esté realmente listo — docker ps debería dejar de dar error.
2 kind El contenedor del clúster tiene una política de reinicio, así que vuelve solo en cuanto el motor de Docker está arriba — no hace falta kind create cluster. Confírmalo con kubectl get nodes; si apunta al clúster equivocado, kubectl config use-context kind-hello-world.
3 Kubernetes + Argo Los pods que muestran Unknown justo después del reinicio vuelven solos a Running en aproximadamente un minuto — es kubelet reconectando, no un fallo real. No hace falta hacer nada, solo espera y vuelve a comprobar con kubectl get pods -n argocd.
4 You Lo que no vuelve solo: los dos procesos kubectl port-forward del panel "En local". Vuelve a lanzar ambos: 
kubectl -n argocd port-forward svc/argocd-server 8081:443 &
kubectl -n hello-world port-forward svc/hello-world 8080:8080 &

Si un port-forward da error con unable to listen on any of the requested ports, uno antiguo de antes del reinicio todavía lo está ocupando — encuentra y mata ese proceso primero, y reinténtalo.

empezando desde cero

Todavía no existe ningún clúster — primera vez en esta máquina, o has ejecutado kind delete cluster.

1 You Clona los dos repos — todo lo de abajo asume que estás dentro de ellos: 
git clone https://github.com/juanfranciscofernandezherreros/hello-world-argocd.git
git clone https://github.com/juanfranciscofernandezherreros/gitops-config.git
2 You Arranca Docker Desktop, y luego crea el clúster: 
kind create cluster --name hello-world
3 You Instala ArgoCD dentro: 
kubectl create namespace argocd
kubectl apply -n argocd --server-side --force-conflicts \
  -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
kubectl -n argocd rollout status deploy/argocd-server

--server-side importa: un apply normal falla aquí porque el CRD de ApplicationSet supera el límite de 262144 bytes de la anotación last-applied-configuration que escribe un apply normal.

4 You El clúster y ArgoCD ya están listos, pero la app en sí todavía no está corriendo. Esa es la siguiente sección — la 05, justo debajo — desde dentro de tu clon de hello-world-argocd: construye el jar, construye la imagen, cárgala en kind, y luego desde tu clon de gitops-config, regístrala en Argo — con la salida real de cada paso.
5 You Una vez hecho eso, abre las dos puertas: los mismos dos comandos port-forward del camino "solo reanudando" de arriba, y luego curl http://localhost:8080/hello para confirmarlo.
05

Recorrido por la terminal — cada comando, de verdad

Los pasos 0 y 0b son la configuración de una sola vez de la sección 04, ya hecha aquí. Los pasos 1-6 son el bucle repetible — construir, cargar, sincronizar, verificar — con la salida real de terminal de cada uno. Las capturas de la sección 06 muestran este mismo resultado en el navegador; los comandos sueltos, para copiar rápido, están en la sección 09.

0 — configuración de una sola vez, ya hecha

El clúster existe y está Ready

kind get clusters lista el clúster; kubectl get nodes confirma que Kubernetes en sí está arriba.

0b — Argo está instalado

Los 7 pods de ArgoCD en Running

ArgoCD en sí es solo un puñado de pods viviendo en el namespace argocd — el application-controller, el repo-server, el servidor de la UI, y algunos ayudantes.

1 — construir el jar

mvn clean package

Compila la app Spring Boot, corre su único test, y produce hello-world-0.0.1-SNAPSHOT.jar en target/.

2 — construir la imagen

docker build -t hello-world:local app

Envuelve ese jar y un JRE en la imagen hello-world:local, usando app/Dockerfile. Las capas quedan en caché, así que volver a ejecutarlo tras un cambio de código es rápido.

3 — meter la imagen en el clúster

kind load docker-image

No hay registry en esta base, así que la imagen se inyecta directamente en el nodo de kind. El ID cambia cada vez que reconstruyes, por eso aquí dice "not yet present".

4 — registrar (o volver a registrar) en Argo

kubectl apply -f applications/hello-world.yaml

Aquí dice unchanged porque el Application ya existía de una ejecución anterior — es lo esperado y está bien. En una primera ejecución diría created.

5 — sincronizar bajo demanda

argocd app sync hello-world

Fuerza la comparación en vez de esperar al refresh automático de ~3 minutos. La tabla de abajo es el informe recurso por recurso de Argo: Namespace, Service, Deployment — todos Synced.

6 — prueba final

kubectl get pods + curl

El Pod está Running, y el endpoint responde. Es el mismo resultado que la captura de la sección 06, paso 1 — solo que visto desde la terminal en vez del navegador.

06

Probado en una máquina real — capturas reales

Nada de esto es teórico: son capturas reales, tomadas justo después de reconstruir el clúster hello-world desde cero.

Paso 1 — el microservicio responde

GET http://localhost:8080/hello

El navegador llega al Pod a través del Service (vía kubectl port-forward). Confirma que el contenedor arrancó y Spring Boot está sirviendo peticiones.

Paso 2 — la pantalla de login de Argo

https://localhost:8081

ArgoCD trae su propia interfaz web, separada de Kubernetes. Entra con el usuario admin y el password inicial (comando en el panel "En local" de arriba).

Paso 3 — ya dentro, el panel de Applications

hello-world · Healthy · Synced

La vista principal de Argo: cada tarjeta es un Application que vigila. Se ve el repo (gitops-config), la carpeta (manifests/hello-world), y el estado.

Paso 4 — el árbol de recursos

Namespace → Service → Deployment → Pod

Al abrir la tarjeta, Argo dibuja todo lo que creó a partir del YAML: el Namespace, el Service, el Deployment, y colgando de él, el Pod real corriendo. Todo en verde = completamente sincronizado y sano.

07

Secuencia — cambiar el despliegue

100% automático

Ejemplo: pasar de 1 a 3 réplicas editando gitops-config/manifests/hello-world/deployment.yaml.

1 You Edita el YAML y haz git push a gitops-config.
2 ArgoCD Ejecuta git fetch en el repo y compara HEAD contra el estado real del clúster.se repite cada ~3 min, o al forzar un refresh
3 Kubernetes API Argo aplica la diferencia: crea, actualiza o borra recursos según haga falta.
4 hello-world Pod Se crean los pods que faltan. El readinessProbe confirma que están listos.
5 ArgoCD Marca el Application como Synced · Healthy. Listo — nadie tocó kubectl.
08

Secuencia — cambiar el código

manual en esta base

Todavía no hay CI ni registry, así que construir y publicar la imagen nueva depende de ti.

1 You mvn package en hello-world-argocd/app.
2 You docker build -t hello-world:local app.
3 You kind load docker-image hello-world:local --name hello-world — la imagen no viene de ningún registry, se inyecta directamente en los nodos del clúster.
4 You kubectl rollout restart deploy/hello-world -n hello-world — Argo no detecta este cambio solo porque el tag de la imagen nunca cambió.
5 hello-world Pod Se recrea con la imagen nueva y vuelve a quedar Ready.
