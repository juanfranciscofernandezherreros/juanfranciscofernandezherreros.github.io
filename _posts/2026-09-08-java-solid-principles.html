SOLID principles in Java

Five design principles that help object-oriented code remain understandable, testable, and adaptable as requirements change.

01

What does SOLID mean?

SOLID is a set of five object-oriented design principles: Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, and Dependency Inversion. They guide how responsibilities and dependencies are divided so that a change has a small, predictable impact.

SOLID is not a rule that every class must satisfy mechanically. It is a vocabulary for recognizing design pressure. Apply a principle when it makes change safer or testing easier; unnecessary abstractions can make a small system harder to understand.

S

Single Responsibility Principle

A module should have one reason to change. This is about grouping code by responsibility, not forcing every class to contain only one method. If invoice calculation and email delivery change for different business reasons, they belong in different components.

public class InvoiceService {
    private final InvoiceRepository repository;
    private final EmailSender emailSender;

    public Invoice create(Order order) {
        Invoice invoice = Invoice.from(order);
        repository.save(invoice);
        emailSender.send(invoice);
        return invoice;
    }
}

The orchestration remains in InvoiceService, while persistence and delivery have their own responsibilities. A warning sign is a class that changes whenever unrelated concerns—database, pricing, formatting, or notifications—change.

O

Open/Closed Principle

Software entities should be open for extension but closed for modification. New behavior should often be added through a stable abstraction instead of repeatedly editing a large conditional.

public interface DiscountPolicy {
    BigDecimal apply(BigDecimal price);
}

public final class VipDiscount implements DiscountPolicy {
    public BigDecimal apply(BigDecimal price) {
        return price.multiply(new BigDecimal("0.90"));
    }
}

A new discount can implement DiscountPolicy without changing the calculator that consumes it. This does not mean existing code must never change; it means protecting stable behavior from every new variation.

L

Liskov Substitution Principle

An implementation must be usable wherever its abstraction is expected without breaking the promised behavior. A subtype must honor the contract: it should not require stronger preconditions, produce weaker results, or introduce surprising failures.

public interface PaymentMethod {
    Receipt pay(Money amount);
}

public final class CardPayment implements PaymentMethod {
    public Receipt pay(Money amount) {
        return gateway.charge(amount);
    }
}

If an implementation throws UnsupportedOperationException for normal calls permitted by PaymentMethod, the abstraction is probably incorrect. LSP is about behavioral compatibility, not merely sharing a parent type.

I

Interface Segregation Principle

Clients should not depend on methods they do not use. Prefer small, role-focused interfaces to one large interface that forces implementations to provide meaningless methods.

public interface Printable {
    void print(Document document);
}

public interface Scannable {
    Document scan();
}

A basic printer implements only Printable; a multifunction device can implement both. Warning signs include empty methods and methods that always throw because a class cannot support part of its interface.

D

Dependency Inversion Principle

High-level policy should not depend directly on low-level details; both should depend on abstractions. The abstraction is normally owned by the business need, while infrastructure supplies an implementation.

public interface OrderRepository {
    void save(Order order);
}

public class CheckoutService {
    private final OrderRepository repository;

    public CheckoutService(OrderRepository repository) {
        this.repository = repository;
    }
}

CheckoutService does not know whether orders are stored with JPA, JDBC, or in memory. Constructor injection is a mechanism that supports DIP, but simply using an interface does not guarantee a useful design.

07

How the principles work together

Change

SRP limits why a module changes; OCP lets new variations be added behind stable contracts.

Contracts

LSP keeps implementations trustworthy; ISP keeps each contract focused on its clients.

Dependencies

DIP points source-code dependencies toward business abstractions rather than infrastructure details.

Balance

Use evidence of change and coupling. Do not add an interface or pattern when it solves no current design problem.

Practical test: when a requirement changes, ask how many unrelated files must change, whether behavior can be tested in isolation, and whether implementations still honor their contracts.

08

The interview answer

“SOLID groups five object-oriented design principles. SRP separates reasons to change; OCP favors extending behavior through stable abstractions; LSP requires implementations to preserve their contracts; ISP keeps interfaces small and client-specific; and DIP makes high-level policy depend on abstractions instead of infrastructure details. Together they reduce coupling and make code easier to change and test. I apply them pragmatically, because extra abstractions also have a cost.”

A strong answer explains the design outcome and gives one concrete example. Naming all five principles without showing how they affect change is less useful than describing a real refactoring.
