Configuration in Spring Boot

Configuration looks simple until one property has four different values: one in application.yml, another in a profile, another in an environment variable and another on the command line. In an interview, understanding which one wins and why is more valuable than memorizing where to type a key.

00

The short interview answer

Spring Boot externalizes configuration so the same application artifact can run in different environments. It reads properties from files, environment variables, system properties, command-line arguments and other sources. Those sources have defined precedence, so higher-priority sources can override earlier values. Profiles activate configuration variants, and @ConfigurationProperties provides structured, typed and validated binding.

The key idea is separating code from deployment configuration. A Docker image or JAR should not need recompilation because production uses a different hostname, timeout or pool size.

01

Externalized Configuration: one artifact, multiple environments

# application.yml
orders:
  client:
    base-url: https://orders.example
    connect-timeout: 2s
    read-timeout: 5s

The same code can start in local development, CI, staging or production while values come from outside. This supports promoting the same binary and reduces accidental environment-specific builds.

Code

Defines stable behavior and types. It is versioned, compiled and tested.

Configuration

Defines deployment-specific endpoints, limits, flags, referenced credentials and operational parameters.

02

Property sources and precedence

Spring Boot builds an Environment from multiple PropertySource instances. They do not have equal priority. A useful model is that external and more explicit configuration can usually override packaged defaults.

ExampleTypical useRelative priority
Packaged application.ymlDefaultsBase
application-prod.ymlProfile valuesOverrides base within config data
External fileDeployment configHigher than packaged
Environment variableContainers / platformHigher than config data
Java system propertyJVM startupHigher than environment variables
--key=valueExplicit overrideVery high
# application.yml
server:
  port: 8080

# environment variable
SERVER_PORT=9090

# command line
java -jar app.jar --server.port=7070

With those inputs, the command-line argument wins and the server starts on 7070.

Do not memorize a list without understanding the rule. In production the useful skill is tracing where a value came from. Forgotten overrides explain many differences between supposedly identical environments.

03

Profiles: activate coherent groups of configuration or beans

A profile represents a logical context such as local, test or prod. Spring Boot can load application-prod.yml in addition to the base file.

# application.yml
orders:
  client:
    base-url: http://localhost:8081

# application-prod.yml
orders:
  client:
    base-url: https://orders.internal.example
SPRING_PROFILES_ACTIVE=prod
java -jar app.jar

# or
java -jar app.jar --spring.profiles.active=prod

@Profile can also restrict bean registration:

@Bean
@Profile("local")
PaymentGateway fakePaymentGateway() {
    return new InMemoryPaymentGateway();
}

Good use: real environment or infrastructure differences. Poor use: an explosion of profiles acting as feature flags, customers or hard-to-test combinations.

04

@Value vs @ConfigurationProperties

@Value is convenient for one or two isolated values:

@Value("${orders.client.base-url}")
private String baseUrl;

When configuration forms a cohesive unit, @ConfigurationProperties provides grouping, type conversion, relaxed binding and validation.

@ConfigurationProperties(prefix = "orders.client")
@Validated
public record OrdersClientProperties(
    @NotNull URI baseUrl,
    @NotNull Duration connectTimeout,
    @NotNull Duration readTimeout,
    @Min(1) int maxRetries
) {}
orders:
  client:
    base-url: https://orders.example
    connect-timeout: 2s
    read-timeout: 5s
    max-retries: 3

Configuration now has a contract. If a required value is missing or max-retries is invalid, failing at startup is better than discovering the problem under production traffic.

05

Registering @ConfigurationProperties

One option is scanning property classes:

@SpringBootApplication
@ConfigurationPropertiesScan
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}

Another is explicitly registering selected classes:

@Configuration
@EnableConfigurationProperties(OrdersClientProperties.class)
class OrdersClientConfiguration { }

A configuration-properties class should represent environment data. Do not turn it into a service full of business dependencies and behavior.

06

Environment variables and relaxed binding

Kubernetes, OpenShift and container platforms commonly supply configuration through environment variables:

ORDERS_CLIENT_BASE_URL=https://orders.internal
ORDERS_CLIENT_MAX_RETRIES=5

Spring Boot can bind these to orders.client.base-url and orders.client.max-retries. This flexibility is part of its relaxed binding conventions.

The image contains code; a Deployment, Helm chart, ConfigMap, Secret or platform supplies environment-specific values.

07

Configuration does not mean committing secrets

Passwords, tokens, private keys and database credentials should not live in a versioned application-prod.yml. The repository can define the property contract or placeholders; the actual secret should arrive from an appropriate runtime mechanism.

spring:
  datasource:
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}

A placeholder does not protect a secret if the real value is committed elsewhere. Secret management includes storage, access, rotation, auditing and revocation.

08

spring.config.import and modular configuration

Spring Boot can import additional configuration using spring.config.import.

spring:
  config:
    import: "optional:file:./config/orders.yml"

optional: means startup may continue if the resource is missing. Without it, a missing required location is a configuration error.

Also distinguish spring.config.location from spring.config.additional-location: the first can replace default locations while the second adds more. These are processed early, so they must come from sources available before normal config data is loaded.

09

Configuration in tests

Tests should not accidentally depend on a developer's laptop environment.

@SpringBootTest(properties = {
    "orders.client.base-url=http://localhost:9999",
    "orders.client.max-retries=1"
})
class OrdersApplicationTest { }

With Testcontainers, @DynamicPropertySource is useful when values only exist after a container starts:

@DynamicPropertySource
static void databaseProperties(DynamicPropertyRegistry registry) {
    registry.add("spring.datasource.url", postgres::getJdbcUrl);
    registry.add("spring.datasource.username", postgres::getUsername);
    registry.add("spring.datasource.password", postgres::getPassword);
}

The principle is explicitness: the test describes the environment it needs instead of relying on invisible global values.

10

Common mistakes

@Value everywhere

Scatters string keys and hides a component's configuration contract.

One profile per feature

Creates hard-to-test combinations. Profiles work best for coherent contexts.

Dangerous defaults

Critical credentials or endpoints should not silently fall back to another environment.

Secrets in YAML

Committed secrets spread through clones, history, forks, caches and logs.

No validation

A deployment mistake survives startup and fails later under load.

Unknown override source

Without understanding precedence, two apparently identical deployments can behave differently.

11

Interview questions

What is the difference between application.yml and application-prod.yml?

The first contains general configuration; the second is a variant considered when prod is active and can override base values.

Which wins: YAML or an environment variable?

In the normal ordering, an environment variable has higher precedence than packaged config data.

When would you use @Value?

For isolated values. For structured groups that benefit from types and validation, I prefer @ConfigurationProperties.

What is relaxed binding?

The ability to map naming variants—kebab-case, camelCase or uppercase underscore forms depending on the source—to the same configuration model.

Where would you store secrets?

In the platform's secret mechanism or a suitable secret manager, injected at runtime; not in Git.

Why validate configuration properties?

To turn a deployment mistake into an early and explicit startup failure.

12

How I would answer at senior level

“I want the same artifact to be promotable across environments, with differences arriving through external configuration. I use application.yml for safe defaults, profiles for coherent variants, and environment or external sources for deployment values. For structured configuration I prefer typed, validated @ConfigurationProperties. I understand precedence because an override often explains environment drift. Secrets do not live in Git and tests declare their properties explicitly. My goal is to fail fast on invalid configuration and make the source of each important value traceable.”

Key idea: Spring Boot configuration is not just YAML. It is a system of property sources, precedence, binding, validation and activation that lets the same code run predictably across environments.
