Cargar 100.000 filas en PostgreSQL

Prepara almacenamiento persistente, crea el esquema, genera datos deterministas dentro de PostgreSQL y demuestra que están completos antes de arrancar el servicio limitado en memoria.

Motor
PostgreSQL 16
Filas
100.000
Almacenamiento
PVC de 2Gi
00

Por qué la base de datos va primero

La prueba solo es significativa si los datos existen independientemente del proceso Java. Generar un millón de objetos al iniciar la aplicación mezclaría la creación del fixture con el fallo que queremos estudiar y podría agotar el heap antes de que el endpoint HTTP estuviera disponible. Aquí PostgreSQL posee los datos; Spring Boot únicamente los consulta.

1 · Aprovisionar

Crea PostgreSQL, su Service y el volumen persistente.

2 · Cargar

Crea la tabla y genera 100.000 filas en el servidor.

3 · Verificar

Comprueba cantidad y límites antes de desplegar la API.

Este orden también aclara el diagnóstico. Si la consulta de validación devuelve 100.000 filas y después la petición HTTP agota el heap, el fallo está al materializar el resultado, no al crear los datos.

01

Recursos persistentes de PostgreSQL

Un StatefulSet da identidad estable a la base de datos. Un Service ClusterIP ofrece el nombre DNS postgresql a los clientes del namespace, y un PersistentVolumeClaim conserva PGDATA si se recrea el pod.

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgresql-data
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 2Gi
---
apiVersion: v1
kind: Service
metadata:
  name: postgresql
spec:
  selector:
    app: postgresql
  ports:
    - port: 5432
      targetPort: 5432

El StatefulSet usa postgres:16-alpine y define POSTGRES_DB=goodbye, POSTGRES_USER=goodbye y la contraseña del laboratorio. En un repositorio de producción, guarda las credenciales en un Secret o gestor externo, no en un ConfigMap ni en un artículo.

kubectl get statefulset,pod,svc,pvc -n godbyemicroservices-postgres-oom
kubectl wait --for=condition=Ready pod/postgresql-0 \
  -n godbyemicroservices-postgres-oom --timeout=180s
02

Crea la tabla

El esquema es pequeño de forma deliberada. La clave primaria numérica facilita comprobar los extremos, mientras que el payload obliga al driver JDBC y al heap Java a conservar un valor real por fila.

CREATE TABLE IF NOT EXISTS goodbye_record (
    id      BIGINT PRIMARY KEY,
    payload VARCHAR(64) NOT NULL
);

IF NOT EXISTS permite repetir la sentencia sin destruir datos. No sustituye a una estrategia de migraciones; usa Flyway o Liquibase cuando el ejemplo evolucione más allá de este laboratorio controlado.

03

Genera 100.000 filas en el servidor

La función generate_series de PostgreSQL crea todos los identificadores dentro del motor. Un único INSERT ... SELECT evita 100.000 viajes de red y no construye una lista en el cliente.

INSERT INTO goodbye_record (id, payload)
SELECT value, 'goodbye-' || value
FROM generate_series(1, 100000) AS value
ON CONFLICT (id) DO NOTHING;

El dataset es determinista: el ID 1 siempre contiene goodbye-1 y el ID 100000 contiene goodbye-100000. ON CONFLICT DO NOTHING hace segura la repetición cuando esas claves ya existen.

Ejecuta la operación completa dentro del pod PostgreSQL:

kubectl exec -i -n godbyemicroservices-postgres-oom postgresql-0 -- \
  psql -U goodbye -d goodbye -v ON_ERROR_STOP=1 -c \
  "CREATE TABLE IF NOT EXISTS goodbye_record (id BIGINT PRIMARY KEY, payload VARCHAR(64) NOT NULL); INSERT INTO goodbye_record (id, payload) SELECT value, 'goodbye-' || value FROM generate_series(1, 100000) AS value ON CONFLICT (id) DO NOTHING;"

-v ON_ERROR_STOP=1 obliga a psql a terminar con error en cuanto falle una sentencia. Es importante para scripts y controles de despliegue.

04

Verifica sin descargar la tabla

Agrega dentro de PostgreSQL y devuelve una sola fila compacta. Contar desde Java, DBeaver o una consola exigiría transferir antes todos los datos y podría reproducir el problema de memoria que queremos aislar.

kubectl exec -n godbyemicroservices-postgres-oom postgresql-0 -- \
  psql -U goodbye -d goodbye -c \
  "SELECT COUNT(*) AS total, MIN(id) AS first_id, MAX(id) AS last_id FROM goodbye_record;"

 total  | first_id | last_id
--------+----------+---------
 100000 |        1 |  100000
Condición de aceptación: total=100000, first_id=1 y last_id=100000. Solo después debe arrancar el pod de Spring Boot.

Para inspeccionar contenido, pide una página limitada:

SELECT id, payload
FROM goodbye_record
ORDER BY id
LIMIT 20;
05

Trampas de inicialización y persistencia

Los scripts init se ejecutan una vez

/docker-entrypoint-initdb.d solo se procesa cuando PostgreSQL inicializa un directorio vacío.

El PVC sobrevive al pod

Eliminar el pod no vacía la base. Cambiar el ConfigMap init no recarga un volumen existente.

Esquema antes que servicio

Usa readiness y validación explícita para no arrancar silenciosamente contra una tabla vacía.

Consultas de inspección acotadas

Usa agregados o LIMIT. No representes todo el dataset en un cliente de administración.

Para un PVC existente, aplica migraciones o ejecuta explícitamente la carga idempotente. Elimina el PVC solo cuando quieras reiniciar este laboratorio desechable, ya que esa operación destruye los datos.

06

De 100.000 al dataset OOM

El ejercicio solicitado aquí termina en 100.000 filas. La variante OOM desplegada utiliza después el mismo SQL con un límite de 1000000. Ese fixture mayor hace determinista el agotamiento con el heap de solo -Xmx18m.

-- Escala del laboratorio OOM: mismo método, diez veces más filas
SELECT value, 'goodbye-' || value
FROM generate_series(1, 1000000) AS value;

La cantidad de filas no es un umbral de memoria universal. El diseño de objetos, columnas, driver JDBC, versión de Java, límite de heap y estrategia de lectura cambian el resultado. Es un fixture reproducible para este servicio, no una fórmula general de OOM.
