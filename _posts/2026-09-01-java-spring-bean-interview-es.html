Spring Beans en profundidad

Cómo registra Spring los beans, cómo resuelve sus dependencias y qué ocurre desde que arranca el contexto hasta que se destruye cada instancia.

01

Qué es exactamente un Spring Bean

Un Spring Bean es un objeto registrado y gestionado por el contenedor IoC de Spring. El contenedor mantiene su definición, decide cuándo crearlo, resuelve sus dependencias, aplica postprocesadores y proxies, controla su scope y ejecuta los callbacks de su ciclo de vida.

El contenedor se expone normalmente mediante ApplicationContext. Internamente trabaja con metadatos llamados BeanDefinition, que describen el tipo del bean, su nombre, su scope, si debe inicializarse de forma diferida y cuáles son sus dependencias.

BeanDefinition→Creación→Inyección→Postprocesado→Bean disponible
02

Cómo se registra un Spring Bean

Spring puede descubrir nuestras clases mediante component scanning. @Component es la anotación general; @Service, @Repository y @Controller expresan responsabilidades más concretas.

@Service
public class EmailService {
    public void enviar(String mensaje) {
        System.out.println(mensaje);
    }
}

También podemos declarar un bean explícitamente con @Bean dentro de una clase @Configuration. Es especialmente útil para clases de librerías externas que no podemos anotar.

@Configuration
public class AppConfig {
    @Bean
    public ObjectMapper objectMapper() {
        return new ObjectMapper();
    }
}

El nombre predeterminado del bean será objectMapper, igual que el método. Podemos cambiarlo con @Bean("apiObjectMapper"). Con @Component, el nombre predeterminado se deriva del nombre del tipo.

Auto-configuración de Spring Boot

Los starters también pueden registrar beans según las clases disponibles, las propiedades y los beans que ya existan. Una auto-configuración suele combinar @ConditionalOnClass, @ConditionalOnProperty y @ConditionalOnMissingBean.

@Bean
@ConditionalOnMissingBean
public PaymentClient paymentClient(PaymentProperties properties) {
    return new HttpPaymentClient(properties.baseUrl());
}

Si la aplicación declara su propio PaymentClient, la condición evita registrar el bean por defecto. Así se puede personalizar una auto-configuración sin modificar la librería.

03

Resolución e inyección de dependencias

La inyección por constructor deja explícitas las dependencias, permite usar campos final y facilita las pruebas. Si hay un único constructor, Spring no necesita que añadamos @Autowired.

@RestController
public class UsuarioController {
    private final EmailService emailService;

    public UsuarioController(EmailService emailService) {
        this.emailService = emailService;
    }
}
Spring escanea configuración→Crea los beans→Resuelve dependencias→Inyecta objetos listos

La resolución se realiza principalmente por tipo. Si no hay ningún candidato, Spring lanza normalmente NoSuchBeanDefinitionException. Si hay varios y no puede elegir uno, lanza NoUniqueBeanDefinitionException.

Varios beans del mismo tipo

public interface NotificationSender {
    void send(String message);
}

@Component("emailSender")
class EmailSender implements NotificationSender { /* ... */ }

@Component("smsSender")
class SmsSender implements NotificationSender { /* ... */ }

@Service
class AlertService {
    private final NotificationSender sender;

    AlertService(@Qualifier("smsSender") NotificationSender sender) {
        this.sender = sender;
    }
}

@Qualifier selecciona un candidato concreto. @Primary marca el candidato preferido cuando no hay qualifier. También podemos inyectar todos los candidatos como List<NotificationSender> o Map<String, NotificationSender>.

04

Ciclo de vida completo

  1. Spring lee la configuración y registra las definiciones de beans.
  2. Los BeanFactoryPostProcessor pueden modificar esas definiciones.
  3. Spring instancia el bean y resuelve sus dependencias.
  4. Ejecuta callbacks Aware, si el bean los implementa.
  5. Los BeanPostProcessor actúan antes de la inicialización.
  6. Se ejecutan @PostConstruct, afterPropertiesSet() o el método configurado con initMethod.
  7. Los postprocesadores actúan después de la inicialización y pueden devolver un proxy.
  8. Al cerrar el contexto se ejecutan @PreDestroy, destroy() o destroyMethod.
@Component
public class ExchangeRateCache {
    @PostConstruct
    void loadRates() {
        // Las dependencias ya están inyectadas.
    }

    @PreDestroy
    void clearResources() {
        // Liberar conexiones, hilos o recursos propios.
    }
}

Importante: evita operaciones remotas frágiles o demasiado pesadas en @PostConstruct. Un fallo impide crear el bean y puede detener el arranque completo.

05

Scopes y duración de las instancias

singleton

Una instancia por definición y por ApplicationContext. Es el scope predeterminado, pero no significa una instancia única en toda la JVM.

prototype

Una instancia cada vez que se solicita. Spring la inicializa, pero no gestiona automáticamente su destrucción.

request

Una instancia por petición HTTP. Está disponible únicamente dentro de un contexto web.

session

Una instancia por sesión HTTP. Su uso requiere especial cuidado en aplicaciones distribuidas.

@Component
@Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
public class ReportJob { /* ... */ }

El problema de inyectar un prototype en un singleton

Si inyectamos directamente un prototype en un singleton, la resolución ocurre una sola vez al crear el singleton. Para obtener una instancia nueva en cada operación podemos utilizar ObjectProvider.

@Service
public class ReportService {
    private final ObjectProvider<ReportJob> jobs;

    public ReportService(ObjectProvider<ReportJob> jobs) {
        this.jobs = jobs;
    }

    public void generate() {
        ReportJob job = jobs.getObject();
        // Nueva instancia en cada llamada.
    }
}
06

Proxies y comportamiento añadido por Spring

Spring puede devolver un proxy en lugar de la instancia original para aplicar comportamiento transversal. Así funcionan características como @Transactional, @Async, caché, seguridad y aspectos personalizados.

@Service
public class PaymentService {
    @Transactional
    public void confirmPayment(Long paymentId) {
        // El proxy abre la transacción antes de entrar
        // y hace commit o rollback al terminar.
    }
}

Una llamada desde otro bean atraviesa el proxy. Una llamada interna mediante this.confirmPayment() no lo atraviesa; por eso la self-invocation puede hacer que @Transactional o @Async parezcan no funcionar.

La solución habitual es separar la operación interceptada en otro bean con una responsabilidad clara.

07

Singleton no significa thread-safe

Un bean singleton puede recibir llamadas simultáneas desde muchas peticiones. Spring no sincroniza sus métodos ni protege su estado. La opción más segura es que los servicios sean stateless.

@Service
public class UnsafeCounterService {
    private int counter = 0;

    public int next() {
        return ++counter; // Condición de carrera.
    }
}

El estado de negocio debería vivir en la base de datos, en una caché preparada para concurrencia o en otro sistema que ofrezca las garantías necesarias.

08

Pruebas de un bean

Con inyección por constructor, la lógica del bean puede probarse sin levantar Spring. Mockito proporciona las dependencias y la prueba se mantiene rápida.

@ExtendWith(MockitoExtension.class)
class TransferServiceTest {
    @Mock AccountRepository repository;
    @Mock AuditPublisher publisher;
    @InjectMocks TransferService service;

    @Test
    void publishesAuditAfterTransfer() {
        service.transfer(/* datos */);
        verify(publisher).publish(any());
    }
}

Usa @SpringBootTest cuando necesites verificar el wiring, la auto-configuración o varios beans trabajando juntos. Para una parte concreta existen slices como @WebMvcTest y @DataJpaTest.

09

Errores frecuentes

NoSuchBeanDefinitionException

No existe un candidato. Revisa el paquete escaneado, los perfiles, las condiciones y la configuración importada.

NoUniqueBeanDefinitionException

Hay varios candidatos. Utiliza @Qualifier, @Primary o inyecta la colección completa.

BeanCurrentlyInCreationException

Suele indicar una dependencia circular. La solución es separar responsabilidades, no esconder el ciclo con @Lazy.

BeanCreationException

Falló la construcción o inicialización. La causa útil suele encontrarse al final de la cadena de excepciones.

10

Resumen técnico

Un Spring Bean es un objeto cuya definición está registrada en el contenedor IoC. Spring controla su creación, resuelve e inyecta dependencias, aplica postprocesadores y proxies, determina su scope y ejecuta su ciclo de vida. Puede registrarse mediante component scanning, métodos @Bean o auto-configuración. Por defecto es singleton dentro de su ApplicationContext, pero eso no implica thread-safety.

En aplicaciones reales: utiliza inyección por constructor, mantén los singletons sin estado mutable, resuelve ambigüedades explícitamente, entiende cuándo intervienen los proxies y carga el contexto completo en pruebas solo cuando aporte valor.
