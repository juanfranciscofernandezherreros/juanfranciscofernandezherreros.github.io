Plataforma Kafka local

Ejecuta Kafka, ZooKeeper, Schema Registry, REST Proxy, Kafka UI y Redpanda Console en Kubernetes mientras Argo CD reconcilia continuamente el stack completo desde Git.

01

Propósito y componentes

La plataforma vive en el namespace devtools-kafka del clúster local kind-hello-world. Permite que los microservicios produzcan y consuman eventos, compartan contratos versionados y observen el sistema desde dos interfaces web.

ZooKeeper

Coordina la generación de Kafka utilizada. Servicio: zookeeper:2181.

Kafka

Broker que almacena y distribuye eventos. Servicio interno: kafka:29092.

Schema Registry

Versiona y valida contratos. API: schema-registry:8081.

REST Proxy

Traduce HTTP a operaciones Kafka. API: rest-proxy:8082.

Kafka UI

Visualiza brokers, topics, mensajes, consumidores, esquemas y ZooKeeper.

Redpanda Console

Segunda interfaz compatible con la API de Kafka y Schema Registry.

Importante: usar Redpanda Console no convierte el broker en Redpanda. El broker sigue siendo Kafka de la distribución Confluent; Console actúa como un cliente sin estado.

02

Arquitectura y flujo

Microservicios / UIs→Kafka→ZooKeeperUIs / REST Proxy→Schema Registry→topic _schemas

Dentro del namespace se usan nombres DNS cortos. Desde otro namespace, un microservicio puede conectarse a kafka.devtools-kafka.svc.cluster.local:29092 y http://schema-registry.devtools-kafka.svc.cluster.local:8081.

Kafka posee dos listeners PLAINTEXT. kafka:29092 se anuncia a los pods y localhost:9092 a clientes del equipo local que entren mediante port-forward. La dirección anunciada importa porque, tras el bootstrap, el broker devuelve al cliente los endpoints que utilizará en conexiones posteriores.

03

ZooKeeper, Kafka y los datos

El broker usa confluentinc/cp-kafka:7.4.4 en modo ZooKeeper. KAFKA_ZOOKEEPER_CONNECT=zookeeper:2181 enlaza ambos componentes. Kafka UI recibe también ese endpoint; Redpanda Console no consulta ZooKeeper directamente porque administra el sistema mediante la API estándar de Kafka.

Hay un solo broker, creación automática de topics y factores de réplica de offsets y transacciones establecidos en 1. Es una configuración ligera para desarrollo. Una futura migración a KRaft eliminaría ZooKeeper, pero requiere modificar el modo operativo y los metadatos de Kafka; no consiste simplemente en borrar su Deployment.

04

Contratos con Schema Registry

Schema Registry usa Kafka como almacenamiento a través del topic interno _schemas. Al terminar una sincronización, el hook PostSync register-demo-schemas espera a que la API responda y registra:

  • test-topic-key: una clave string.
  • test-topic-value: el registro DemoValue, con id entero y message string.

Los esquemas permiten que productores y consumidores compartan contratos versionados y que las interfaces deserialicen los mensajes correctamente.

05

Las interfaces visuales

Kafka UI

provectuslabs/kafka-ui:v0.7.2 se conecta a Kafka, Schema Registry y ZooKeeper. Muestra brokers, topics, particiones, mensajes, cabeceras, offsets, grupos, consumer lag y subjects. DYNAMIC_CONFIG_ENABLED=false mantiene Git como fuente de verdad.

Redpanda Console

docker.redpanda.com/redpandadata/console:v3.11.0 usa KAFKA_BROKERS=kafka:29092 y SCHEMAREGISTRY_URLS=http://schema-registry:8081. No se configura la Admin API de Redpanda porque el broker real es Kafka. Ambas UIs consultan el mismo clúster: no duplican brokers ni datos.

06

07

Acceso local

Los Services son ClusterIP. Cada túnel debe ejecutarse en una terminal distinta y permanece activo hasta pulsar Ctrl+C.

kubectl port-forward -n devtools-kafka svc/kafka-ui 18080:8080
kubectl port-forward -n devtools-kafka svc/redpanda-console 18083:8080
kubectl port-forward -n devtools-kafka svc/kafka 9092:9092
kubectl port-forward -n devtools-kafka svc/schema-registry 18081:8081
kubectl port-forward -n devtools-kafka svc/rest-proxy 18082:8082
  • Kafka UI: http://localhost:18080
  • Redpanda Console: http://localhost:18083
08

Validación y diagnóstico

kubectl get pods,deployments,svc -n devtools-kafka
kubectl logs -n devtools-kafka deployment/kafka
kubectl logs -n devtools-kafka deployment/schema-registry
kubectl logs -n devtools-kafka deployment/kafka-ui
kubectl logs -n devtools-kafka deployment/redpanda-console
kubectl get events -n devtools-kafka --sort-by=.lastTimestamp

Invoke-RestMethod http://localhost:18080/actuator/health
Invoke-RestMethod http://localhost:18083/admin/health
Invoke-RestMethod http://localhost:18081/subjects

Kafka UI debe responder UP, Redpanda Console debe informar una salud HTTP correcta y Schema Registry debe listar los dos subjects demo. El Job de registro debe estar Completed; no tiene que permanecer ejecutándose.

09

Seguridad y límites

Los contenedores ejecutan usuarios no-root, seccomp RuntimeDefault, sin elevación de privilegios y sin capabilities Linux. Las UIs fijan UID/GID 100:101. Las probes controlan disponibilidad y vida, y los requests/límites contienen el consumo.

El entorno no es una topología de producción: tiene un solo broker, réplica 1, almacenamiento no persistente, PLAINTEXT sin SASL/TLS, UIs sin autenticación y ninguna NetworkPolicy. Producción requiere persistencia, varios brokers, replicación, cifrado, autorización, copias de seguridad, métricas y alertas.

10

Manifiestos

La definición está separada en applications/devtools-kafka.yaml y los archivos de manifests/devtools-kafka/: ZooKeeper, Kafka, Schema Registry, REST Proxy, Kafka UI, Redpanda Console y el registrador PostSync. Git describe el estado deseado y Argo CD mantiene el clúster alineado con él.

Plataforma Kafka completada

La plataforma local de eventos ya es declarativa, observable y está lista para que los microservicios la utilicen mediante endpoints internos estables.
