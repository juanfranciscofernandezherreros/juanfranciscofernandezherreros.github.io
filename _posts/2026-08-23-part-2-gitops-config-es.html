Argo Real World Microservices — Parte 2 de la serie

El repo de configuración: gitops-config

La Parte 1 construyó el microservicio y dijo "los manifiestos viven en un repo aparte". Esta parte es ese repo: qué hay dentro de verdad, por qué tiene esa forma, y cómo añadir un segundo servicio sin adivinar.

00

Dónde encaja esto

Dos repos, dos trabajos — Parte 1, sección 02 lo cubre entero. Versión corta: hello-world-argocd es código, Java, Docker. gitops-config es el "recetario" — lo que debería existir en el clúster, y es el único repo al que apunta el Application de ArgoCD.

01

Dos carpetas, dos trabajos

Todo lo que hay en este repo es una de estas dos cosas.

applications/
Un YAML por microservicio — el recurso Application que le dice a Argo "vigila esta carpeta, despliégala aquí". Se aplica una vez con kubectl apply; a partir de ahí Argo lo relee del propio clúster, no de este repo.
manifests/<servicio>/
Los objetos reales de Kubernetes para ese servicio — Namespace, Deployment, Service. Es a esto a lo que apunta el Application, y lo que Argo mantiene sincronizado para siempre, cada vez que cambia.
02

applications/hello-world.yaml, línea a línea

El fichero entero — 21 líneas, nada oculto.

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: hello-world
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/juanfranciscofernandezherreros/gitops-config.git
    targetRevision: HEAD
    path: manifests/hello-world
  destination:
    server: https://kubernetes.default.svc
    namespace: hello-world
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
metadata.namespace
argocd — este objeto en sí vive donde vive Argo, no donde corre la app. Eso es un namespace distinto, tres líneas más abajo.
source.repoURL + path
Este mismo repo, carpeta manifests/hello-world — las dos carpetas de la sección 01, apuntándose entre sí.
destination.namespace
hello-world — donde corren de verdad los pods de la app. Se crea solo gracias a CreateNamespace=true de abajo.
syncPolicy.automated
prune y selfHeal — explicados a fondo en la Parte 1, sección 03. Sin este bloque, sincronizar necesitaría un argocd app sync manual cada vez.
03

manifests/hello-world/

Tres ficheros de Kubernetes normales — nada específico de Argo en ninguno. Funcionarían igual con un simple kubectl apply -f.

namespace.yaml

Namespace

Un objeto, una línea que importa: name: hello-world. Todo lo demás de esta carpeta vive dentro de él.

service.yaml

Service

ClusterIP en el puerto 8080 — la dirección estable que usa cualquier otra cosa dentro del clúster para llegar a la app, sin importar qué pod esté corriendo ahora mismo.

deployment.yaml

Deployment

El que merece leerse con calma: image: hello-world:local con imagePullPolicy: Never — no hay registry en esta base (ver Parte 1, sección 08), así que la imagen tiene que estar ya en el nodo vía kind load, y Kubernetes nunca debe intentar descargarla. También lleva el readinessProbe/livenessProbe apuntando a /actuator/health/* — lo que hace que la UI de ArgoCD muestre Healthy y no solo Synced.

04

Añadir un segundo servicio

Ningún concepto nuevo — solo repetir el patrón con un nombre distinto.

1 Tú Copia manifests/hello-world/ a manifests/<servicio-nuevo>/ y cambia cada aparición de hello-world por el nombre nuevo — namespace, labels, imagen, nombre del service.
2 Tú Copia applications/hello-world.yaml a applications/<servicio-nuevo>.yaml. Cambia tres campos: metadata.name, source.path, destination.namespace.
3 Tú git add . && git commit && git push.
4 Tú Regístralo: kubectl apply -f applications/<servicio-nuevo>.yaml.
5 ArgoCD Lo detecta, crea el namespace, lo despliega — el mismo bucle de reconciliación que hello-world, corriendo como un segundo Application completamente independiente.

A partir de 2-3 servicios, copiar y pegar un fichero entero por servicio cansa — para eso existe un ApplicationSet (genera un Application por carpeta automáticamente). No hace falta todavía con n=1.

05

Comandos de referencia

Registrar un servicio

kubectl apply -f applications/hello-world.yaml

Ver qué cree Argo que es verdad ahora mismo

kubectl get application hello-world -n argocd
kubectl get application hello-world -n argocd -o jsonpath='{.status.sync.status} {.status.health.status}'

Forzar una relectura en vez de esperar ~3 min

kubectl -n argocd annotate application hello-world argocd.argoproj.io/refresh=hard --overwrite
