Spring Security in interviews

In an interview, knowing how to write a SecurityFilterChain is not enough. A strong answer explains what happens from the moment a request arrives until Spring decides who the caller is, which permissions they have and whether the request may reach the controller.

Intermediate–advanced

00

The short interview answer

Spring Security protects servlet applications primarily through a chain of filters. Those filters extract credentials, authenticate the caller, store the result in a SecurityContext, and then authorize the request based on paths, roles, authorities or method rules. Authentication answers “who are you?” while authorization answers “are you allowed to do this?”.

This mental model unlocks most follow-up questions: where the authenticated principal lives, who validates a password or JWT, why an endpoint returns 401 or 403, and why disabling CSRF without understanding the client model can create a vulnerability.

01

The mental model: a filter chain before the controller

In a servlet application, a request does not jump directly into the DispatcherServlet. Spring Security integrates a FilterChainProxy that selects a matching SecurityFilterChain and runs its filters.

Client
  │
  ▼
Servlet FilterChain
  │
  ▼
DelegatingFilterProxy
  │
  ▼
FilterChainProxy
  │
  ▼
SecurityFilterChain
  ├─ CSRF / headers
  ├─ authentication
  ├─ SecurityContext
  └─ authorization
  │
  ▼
DispatcherServlet → Controller

Ordering matters: authentication must establish an identity before authorization can decide whether it has permission. You do not need to memorize every internal filter, but you should understand the sequence.

@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    return http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/public/**").permitAll()
            .requestMatchers("/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated())
        .httpBasic(Customizer.withDefaults())
        .build();
}

Common interview question: “What replaces WebSecurityConfigurerAdapter?” Bean-based configuration, typically one or more SecurityFilterChain beans.

02

Authentication: turn credentials into an identity

Spring Security represents authentication through Authentication. Before validation it may represent an authentication request; afterwards it represents the authenticated principal.

ComponentResponsibility
AuthenticationPrincipal, credentials and authorities.
AuthenticationManagerContract that attempts authentication.
ProviderManagerCommon implementation delegating to providers.
AuthenticationProviderUnderstands a concrete mechanism: username/password, JWT, etc.
SecurityContextContains current authentication.
SecurityContextHolderProvides access to the current execution's security context.

For username/password authentication, a common flow loads a user with UserDetailsService and verifies the password through PasswordEncoder.

@Bean
PasswordEncoder passwordEncoder() {
    return PasswordEncoderFactories.createDelegatingPasswordEncoder();
}

Do not confuse hashing with encryption. Passwords are normally stored with adaptive hashes; authentication does not require decrypting the stored value.

03

Authorization: identity does not imply permission

Authentication only establishes that Spring recognizes an identity. Authorization decides whether it may access a resource.

.authorizeHttpRequests(auth -> auth
    .requestMatchers(HttpMethod.GET, "/catalog/**").permitAll()
    .requestMatchers("/admin/**").hasRole("ADMIN")
    .requestMatchers("/orders/**").hasAuthority("orders:write")
    .anyRequest().authenticated()
)

hasRole("ADMIN") follows the ROLE_ADMIN convention; hasAuthority compares the stated authority. Authorization can also be applied to methods:

@EnableMethodSecurity
@Configuration
class SecurityConfig { }

@PreAuthorize("hasAuthority('orders:write')")
public Order cancel(UUID id) {
    ...
}

Request authorization protects the HTTP boundary; method security can protect an operation when it is reached through another internal path. They are complementary.

04

JWT: Spring Security does not become stateless by magic

A JWT is a signed token format. In a Resource Server API, a client commonly sends Authorization: Bearer .... Spring validates signature, time constraints and claims according to configuration, maps relevant claims to authorities and creates the authentication.

@Bean
SecurityFilterChain apiSecurity(HttpSecurity http) throws Exception {
    return http
        .sessionManagement(session -> session
            .sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/actuator/health").permitAll()
            .anyRequest().authenticated())
        .oauth2ResourceServer(oauth -> oauth.jwt(Customizer.withDefaults()))
        .build();
}

JWT is not encryption

A signed JWT provides integrity and authenticity, while its payload is commonly readable. Do not put secrets in it assuming the token hides them.

Stateless does not mean no state

The API may avoid login HttpSession state and still depend on external state for revocation, users, permissions, keys or business data.

Common mistake: writing a custom JWT filter for everything when Spring Security already provides OAuth2 Resource Server support. Custom filters need a concrete requirement.

05

Session vs JWT: there is no universal winner

AspectSessionBearer JWT
Login stateUsually server-sideMainly represented by the token
Immediate revocationEasy by invalidating the sessionMay require short expiry or additional strategy
Traditional browserExcellent fit with a secure cookiePossible, but storage and transport need care
Service-to-serviceLess commonCommon with OAuth2/OIDC

A mature answer is not “JWT always scales better”. The choice depends on clients, revocation, infrastructure, identity provider and threat model.

06

CSRF: why you should not disable it by reflex

CSRF exploits the fact that a browser can automatically attach credentials associated with another site, especially cookies. If an application authenticates using cookies and accepts state-changing requests, CSRF protection must be considered.

For an API that receives bearer tokens exclusively through an explicit header, the threat model changes. That is why many stateless APIs disable CSRF, but the correct reasoning is credential transport, not “because it is REST”.

http.csrf(csrf -> csrf.disable()); // only when the client model justifies it

Strong answer: “I decide CSRF based on how credentials travel. If a browser automatically sends an authenticated cookie, disabling it requires another justified mitigation.”

07

CORS does not authenticate or authorize

CORS is a browser policy for cross-origin requests. It does not prevent a non-browser client from calling your API and never replaces server-side authorization.

@Bean
CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration config = new CorsConfiguration();
    config.setAllowedOrigins(List.of("https://app.example.com"));
    config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE"));
    config.setAllowedHeaders(List.of("Authorization", "Content-Type"));
    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/**", config);
    return source;
}
08

401 vs 403

401 Unauthorized

The request requires valid authentication and does not have it. Conceptually it is an authentication problem.

403 Forbidden

A valid identity exists but lacks sufficient authorization.

In Spring Security, AuthenticationEntryPoint participates when credentials are required, while AccessDeniedHandler handles denied access.

09

Common mistakes in real projects

Overly broad permitAll

A generic matcher can expose more surface than intended.

Hard-coded roles

They tightly couple security and business logic and make permissions harder to evolve.

Storing JWTs anywhere

Browser storage choices change XSS and CSRF exposure.

Logging tokens

A bearer token is a credential and should not appear in logs or traces.

Trusting CORS

Non-browser clients ignore CORS; server authorization remains mandatory.

Inventing cryptography

Use established mechanisms instead of custom signing or hashing schemes.

10

Rapid interview questions

Where does Spring keep the authenticated user?

In an Authentication inside the SecurityContext, normally accessible through SecurityContextHolder.

Are authentication and authorization the same?

No. Authentication establishes identity; authorization decides what it can do.

What is SecurityFilterChain?

A chain of security filters applicable to a request. There can be multiple chains and Spring selects the matching one.

What does PasswordEncoder do?

It encodes and verifies passwords using suitable algorithms, comparing against a hash rather than plain text.

When 401 and when 403?

401 when valid authentication is missing; 403 when an authenticated caller lacks permission.

Would you disable CSRF for an API?

Only after analyzing credential transport; returning JSON is not sufficient reason.

11

How I would answer at senior level

“I start with the threat model and client type. In a servlet application Spring Security runs a filter chain before the controller. An authentication mechanism creates an Authentication, the result lives in the SecurityContext, and request or method authorization is evaluated afterwards. For OAuth2 APIs I prefer standard Resource Server support before custom JWT filters. I distinguish 401 from 403, decide CSRF from credential transport, and never treat CORS as server-side security. The technical configuration follows the security model, not the other way around.”

Key idea: memorizing annotations does not prove that you understand Spring Security. The important skill is tracing a request: filters → authentication → SecurityContext → authorization → application.
