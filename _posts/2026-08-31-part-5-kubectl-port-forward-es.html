00

El problema de red

Un Service de tipo ClusterIP tiene una dirección enrutable únicamente dentro de Kubernetes. El navegador, PowerShell, DBeaver y el resto de programas del equipo Windows no pueden conectarse directamente. Crear un LoadBalancer o un Ingress solo para una sesión local de diagnóstico añade infraestructura y exposición que no necesitamos.

kubectl port-forward abre un puerto TCP en el equipo local y transporta cada conexión a través de la conexión autenticada con la API de Kubernetes. Es temporal: no modifica el Service ni escribe nada en Git.

1 · Cliente

curl, navegador o DBeaver conecta con localhost.

2 · kubectl

El proceso en primer plano acepta la conexión TCP.

3 · API server

El túnel usa la identidad y el contexto del kubeconfig activo.

4 · Pod

El tráfico llega a un pod seleccionado por el Service.

El formato es PUERTO_LOCAL:PUERTO_REMOTO. En 8082:8080, el cliente usa 8082 en Windows y la aplicación continúa escuchando en 8080 dentro del pod.

01

Comprueba primero el destino

Verifica el clúster actual, los Services y sus endpoints antes de abrir un túnel. Un Service sin endpoints puede aceptar el comando, pero no tiene un backend preparado al que enviar la petición.

kubectl config current-context
# kind-hello-world

kubectl get svc,endpoints -n godbyemicroservices-postgres-oom
kubectl get pods -n godbyemicroservices-postgres-oom -o wide

El laboratorio expone Spring Boot en el puerto 8080 y PostgreSQL en el 5432. Argo CD está en el namespace argocd y ofrece HTTPS en el puerto 443 de su Service.

02

Por qué es necesario y cómo demostrarlo

La necesidad depende de dónde se ejecuta el cliente. Los Services de Spring Boot y PostgreSQL son ClusterIP: proporcionan descubrimiento estable y balanceo a las cargas que están dentro de Kubernetes, pero no publican un puerto en Windows. El navegador o DBeaver del equipo no tienen ningún socket local al que conectarse hasta que kubectl lo crea.

Equipo → ClusterIP

Port-forward es necesario para una conexión local temporal.

Pod → DNS del Service

No es necesario; dentro del namespace se usa postgresql:5432.

kubectl get/logs/exec

No es necesario; estos comandos ya utilizan la API de Kubernetes.

Ingress o LoadBalancer

No es necesario si el servicio se ha publicado intencionadamente.

Ejecuta esta prueba controlada sin ningún proceso anterior usando el puerto 8082. El primer resultado demuestra que la aplicación no está expuesta en el equipo:

Test-NetConnection localhost -Port 8082

# Resultado esperado antes del port-forward
TcpTestSucceeded : False

En la terminal 1, inicia el túnel y déjalo ejecutándose:

kubectl port-forward -n godbyemicroservices-postgres-oom \
  svc/godbyemicroservices-postgres-oom 8082:8080

# Resultado esperado
Forwarding from 127.0.0.1:8082 -> 8080

En la terminal 2, repite la prueba TCP:

Test-NetConnection localhost -Port 8082

# Resultado esperado mientras kubectl sigue activo
TcpTestSucceeded : True

Prueba de aceptación: False → True demuestra que kubectl creó la ruta local que faltaba. Pulsa Ctrl+C en la terminal 1 y el resultado vuelve a False. Esto demuestra que el túnel es temporal y no modifica el Service.

Finalmente, la petición HTTP demuestra el recorrido completo y no solo un socket TCP abierto:

curl.exe -v http://localhost:8082/godbyemicroservices

En este laboratorio, llegar al controller hace que Java cargue deliberadamente toda la tabla PostgreSQL. La conexión puede cerrarse cuando ExitOnOutOfMemoryError termina la JVM. El log OOM y el pod fallido demuestran que la petición cruzó el túnel y llegó al servicio; son el resultado esperado de la aplicación, no un fallo de conectividad.

RESULTADO

Resultado observado

La prueba se ejecutó contra kind-hello-world. Produjo False → True → False, estableció la conexión HTTP y después terminó el proceso Java limitado exactamente como estaba previsto:

* Established connection to localhost (::1 port 8082)
curl: (52) Empty reply from server

godbyemicroservices-postgres-oom   0/1   Error   0
Argo CD                            Synced · Degraded

GET query is loading every PostgreSQL record into one in-memory list
Terminating due to java.lang.OutOfMemoryError: Java heap space

PostgreSQL permaneció Running. Así quedan separados los tres hechos: port-forward proporcionó conectividad, la petición llegó al controller y la aplicación falló después por la causa de memoria prevista.

03

Abre los tres túneles

Ejecuta cada comando persistente en su propia ventana de PowerShell. La línea Forwarding from 127.0.0.1... significa que ya escucha; no significa que el comando haya terminado.

# Interfaz de Argo CD: https://localhost:8081
kubectl port-forward -n argocd svc/argocd-server 8081:443

# API Goodbye: http://localhost:8082
kubectl port-forward -n godbyemicroservices-postgres-oom svc/godbyemicroservices-postgres-oom 8082:8080

# PostgreSQL para DBeaver: localhost:5433
kubectl port-forward -n godbyemicroservices-postgres-oom svc/postgresql 5433:5432

Mantén abierta esa terminal. Pulsar Ctrl+C, cerrar la ventana, suspender el equipo o perder el clúster destruye el túnel. El error posterior curl: (7) Failed to connect es el resultado normal si el proceso ya no está ejecutándose.

04

Llama correctamente al servicio

Deja el port-forward ejecutándose y abre una segunda ventana de PowerShell para el cliente. Pasa una URL literal a curl.exe; la sintaxis Markdown [http://...](http://...) sirve para documentación, pero no es una URL válida en la consola.

curl.exe -v http://localhost:8082/godbyemicroservices

En este laboratorio, el endpoint carga deliberadamente en un ArrayList todo el resultado de PostgreSQL. La llamada esperada puede terminar la JVM con java.lang.OutOfMemoryError: Java heap space. Después, el pod independiente queda Failed, no reinicia y el Service pierde su backend. Que el siguiente curl falle forma parte de la prueba.

kubectl get pod -n godbyemicroservices-postgres-oom
kubectl get application godbyemicroservices-postgres-oom -n argocd
kubectl logs -n godbyemicroservices-postgres-oom godbyemicroservices-postgres-oom
05

Conecta DBeaver

Con el túnel de PostgreSQL activo, crea una conexión PostgreSQL normal en DBeaver. El cliente de escritorio no usa los nombres DNS internos de Kubernetes porque se conecta al extremo local del túnel.

Host

localhost

Puerto

5433

Base / usuario

goodbye / goodbye

Contraseña

goodbye

SELECT COUNT(*) AS total FROM goodbye_record;
SELECT id, payload FROM goodbye_record ORDER BY id LIMIT 20;

Usa SELECT COUNT(*) para validar. Pedir a DBeaver que represente todas las filas malgasta memoria en el cliente y no comprueba el comportamiento de la JVM del servicio.

06

Guía de diagnóstico

Connection refused

El port-forward terminó o nunca mostró “Forwarding”. Arráncalo otra vez y mantenlo abierto.

Address already in use

Otro proceso ocupa el puerto local. Elige otro, por ejemplo 8083:8080.

Sin endpoints

Revisa selector del Service, etiquetas, readiness y puerto de destino.

El túnel cae tras el OOM

El backend seleccionado murió. Revisa el pod y la salud de Argo antes de recrearlo.

# Cambia solo el puerto local; la aplicación continúa en 8080
kubectl port-forward -n godbyemicroservices-postgres-oom svc/godbyemicroservices-postgres-oom 8083:8080
curl.exe http://localhost:8083/godbyemicroservices

Por defecto, kubectl escucha únicamente en loopback, así que solo el equipo local puede usar el túnel. Mantén ese valor para bases de datos y credenciales. Port-forward sirve para desarrollo y diagnóstico, no para exponer servicios en producción.
