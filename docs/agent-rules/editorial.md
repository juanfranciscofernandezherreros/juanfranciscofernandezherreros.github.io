# Reglas editoriales

## Norte editorial

Cada publicación debe cumplir al menos una función clara: enseñar algo aplicable, explicar bien algo que suele explicarse mal, documentar una experiencia real, comparar alternativas con criterios concretos o construir una idea paso a paso hasta una conclusión útil.

No publiques relleno. El blog debe transmitir experiencia práctica: ejemplos reales, decisiones, trade-offs, errores, límites y aprendizajes tienen prioridad sobre texto genérico.

## Regla de interés

Cada artículo necesita una razón para seguir leyendo. Siempre que encaje, usa uno de estos motores narrativos:

- problema → investigación → solución → consecuencias;
- hipótesis → experimento → resultado → aprendizaje;
- antes → cambio → después;
- error real → diagnóstico → causa raíz → prevención;
- comparación → criterios → decisión → cuándo elegir otra cosa;
- concepto abstracto → ejemplo concreto → modelo mental reutilizable.

La introducción debe llegar rápido al problema o promesa. Evita aperturas genéricas. En las primeras pantallas debe quedar claro qué se resuelve, por qué importa y qué obtendrá el lector.

## Voz y estilo

- Explica el porqué, no solo el cómo.
- Usa frases concretas y verbos activos.
- Elimina introducciones largas, repeticiones y conclusiones que solo repiten.
- Explica costes, excepciones, límites y trade-offs.
- Si un fallo enseña algo, no lo ocultes.
- No uses marketing vacío ni exageres resultados.
- No inventes comandos ejecutados, benchmarks, errores, capturas, versiones ni resultados.
- Verifica datos que puedan haber cambiado.
- Prefiere ejemplos de producción frente a foo/bar cuando el dominio permita algo mejor.

## Densidad de valor

Cada sección debe justificar su espacio. Alterna explicación, ejemplo, evidencia real, interpretación y siguiente decisión. No encadenes bloques de código sin explicar qué cambia. No insertes diagramas decorativos ni tablas innecesarias.

## Estándar técnico

Comprueba nombres de herramientas y APIs, comandos válidos, coherencia de rutas/puertos/namespaces/versiones, código compilable o marcado como pseudocódigo, límites importantes y ausencia de contradicciones entre texto, código, tablas y diagramas.

Si hay repositorio o ZIP de ejemplo, debe contar la misma historia que el artículo. Si muestras salida de terminal, indica si es real, abreviada o representativa.

## Estructura recomendada

1. Hook útil.
2. Contexto mínimo.
3. Objetivo.
4. Desarrollo.
5. Momento clave, trade-off o fallo.
6. Resultado y comprobación.
7. Lecciones reutilizables.
8. Siguiente paso natural.

Los tutoriales largos deben poder escanearse con buenos h2, h3, código, tablas o callouts cuando aporten valor.

## Regla final

No optimices para producir más páginas. Optimiza para producir páginas que un desarrollador quiera guardar, compartir o consultar de nuevo. Entre cantidad y profundidad, elige profundidad; entre sofisticación aparente y claridad, elige claridad; entre explicación genérica y experiencia concreta, elige experiencia concreta.
