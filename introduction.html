Argo Real World Microservices — Introduction

The Theory Behind This Series

Before Part 0 has you installing anything, this article explains the ideas those tools implement: what a microservice is, what a container is, what Kubernetes is actually managing, and how CI/CD and GitOps differ as ways of getting code into production. No commands, no installs — just the mental model.

00

What this article is — and isn't

It's a concept map: the vocabulary and the reasoning behind it, so that when Part 0 tells you to install kind or the ArgoCD CLI, you already know what job each one is doing and why it exists. It isn't a tutorial — there's no terminal, no YAML to write, and nothing to verify. If you already know what a container, a Kubernetes cluster, and GitOps are, skip straight to Part 0.

01

Microservices

A microservice is a small, independently deployable service that owns one piece of business capability — orders, payments, a product catalog — and talks to other services over the network, usually HTTP or messaging, instead of sharing code or a database. That's the opposite of a monolith, where every capability lives in one codebase and one deployable unit.

The appeal isn't the size of the codebase, it's independence: each service can be built, tested, deployed, scaled, and even rewritten on its own schedule, without coordinating a release with every other team. The cost is operational — you now have many small moving parts instead of one big one, each with its own deployment, its own failure modes, and its own version. Everything else in this article exists to manage that cost: containers make each service portable, Kubernetes makes many of them runnable together, and CI/CD or GitOps make deploying them repeatable instead of manual.

02

Containers and Docker

A container packages an application together with everything it needs to run — the runtime, libraries, configuration — into one unit that behaves the same on a laptop, a test server, or a production cluster. It's not a virtual machine: containers share the host machine's operating system kernel and isolate processes, filesystems, and networking from each other, which makes them far lighter and faster to start than a VM.

Docker is the tool most people mean when they say "containers" — it builds container images (a read-only snapshot: your app plus its dependencies, described by a Dockerfile) and runs containers from them (a running instance of an image). An image is versioned and pushed to a registry — a server that stores images by name and tag — so that any machine that can reach the registry can pull the exact same image and run an identical container from it.

This is the first piece of the microservices story: a container image is what makes "the same service, built once" runnable anywhere. Kubernetes is what runs many of those containers reliably, at scale, across many machines.

03

Kubernetes

Kubernetes (often "k8s") is a system for running containers across a group of machines — a cluster — and keeping them running the way you asked. You don't tell Kubernetes "start this container on that machine"; you describe the outcome you want — "three copies of this image should always be running" — and Kubernetes continuously works to make reality match that description. If a container crashes, a machine dies, or a copy disappears, Kubernetes notices and starts a replacement without anyone intervening. That continuous "keep reality matching the request" behavior is called a control loop, and it's the same idea GitOps and ArgoCD build on later in this article — just applied one layer up, to entire applications instead of individual containers.

Kubernetes describes everything — what to run, how many copies, what network access it gets — as objects. The ones you'll meet constantly:

Cluster
The group of machines (nodes) Kubernetes manages as one unit — one or more control-plane nodes that make decisions, and worker nodes that actually run containers.
Node
One machine, physical or virtual, that's part of the cluster and has containers scheduled onto it.
Pod
The smallest deployable unit in Kubernetes — one or more tightly coupled containers that always run together on the same node, sharing network and storage.
Deployment
A description of how many identical Pods of a given container image should be running, and how to roll out changes to them without downtime.
Service
A stable network address for a group of Pods, so other things can reach them even as individual Pods are replaced.
Namespace
A named partition inside a cluster used to separate groups of objects — different teams, environments, or applications — from each other.
04

CI/CD

Continuous Integration (CI) is the practice of merging code changes frequently and having a machine automatically build and test every change, instead of discovering integration problems weeks later. Continuous Delivery/Deployment (CD) extends that pipeline to also package and ship the result — building the container image, and then deploying it somewhere.

The detail that matters for the rest of this article is how that deployment step usually works: a traditional CD pipeline runs outside the cluster and pushes changes into it — it authenticates to the cluster, runs a deploy command, and if that command fails partway or the pipeline's credentials are compromised, the cluster can end up in an unclear or exposed state. GitOps, next, is a different answer to that same "how do changes reach the cluster" question.

05

GitOps

GitOps is the practice of keeping the desired state of a system — which applications, which versions, how many replicas, what configuration — declared entirely as files in a Git repository, and having an automated process inside the cluster continuously reconcile the live system to match what's in Git. Git becomes the single source of truth: to change what's running, you don't run a deploy command, you change a file and commit it.

The key structural difference from a traditional CD pipeline is pull vs. push: instead of an external pipeline pushing changes into the cluster with standing credentials, an agent running inside the cluster pulls the desired state from Git and applies it. That agent already has to be inside the cluster to do its job, so no external system needs deploy credentials to it — and because Git holds the desired state, every change is a commit: reviewed, versioned, and revertible with git revert instead of a manual rollback.

Push-based CD

  • An external pipeline holds credentials to the cluster and runs deploy commands against it.
  • The pipeline's run log is the record of what happened — the cluster itself doesn't say what it should look like.
  • If a change is made by hand later (a hotfix), nothing notices the drift from what the pipeline last deployed.

Pull-based GitOps

  • An agent inside the cluster pulls desired state from Git — no external system needs cluster credentials.
  • Git is the record: the repository's current state is what should be running.
  • A manual change that drifts from Git is detected — and can be automatically reverted — on the next reconciliation.
06

ArgoCD

ArgoCD is the agent that implements GitOps for Kubernetes: it runs inside the cluster, watches one or more Git repositories for the manifests that describe an application, and continuously compares that desired state (what's in Git) against the live state (what's actually running in the cluster). ArgoCD models each application it manages as its own object, so its status — in sync or out of sync, healthy or degraded — is something you can see per application, not just infer from logs.

When desired and live state differ, ArgoCD can report the difference and wait for a human to approve a sync, or apply it automatically — including reverting manual changes that weren't made through Git, which is what makes GitOps self-healing rather than just "deployment via commit." Everything ArgoCD does through its CLI or automation can also be done by clicking through its web UI, since both are just two interfaces onto the same reconciliation loop.
