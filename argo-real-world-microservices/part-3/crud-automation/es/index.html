Qué cubre esta parte

Construir hello-world-argocd a mano en la Parte 1 tenía sentido — es cómo aprendes qué hace de verdad cada fichero. Pero un equipo real no escribe a mano cada microservicio desde cero. Esta parte usa crud-automation, un generador en Python, para producir un servicio nuevo con exactamente la misma forma, y lo lleva por la misma integración de la Parte 2 — copiar el patrón de manifiestos, registrar el Application, listo.

01

El generador: --architecture minimal

crud-automation normalmente genera microservicios CRUD completos — Postgres, Flyway, MapStruct, seguridad, observabilidad. Su arquitectura minimal es la excepción: ignora por completo los campos de la entidad y produce el mismo esqueleto desnudo que hello-world-argocd — un endpoint, sin base de datos, sin seguridad, sin observabilidad. Pensada exactamente para esto: un servicio nuevo que se va a enganchar a GitOps, no una API CRUD.

Nombre de la entidad
Se convierte en la carpeta del proyecto (crud-<nombre>-minimal), los nombres de las clases Java, y la ruta del único endpoint. Aquí: GodbyeMicroservices.
Campos
Siguen siendo obligatorios por la sintaxis del comando, pero esta arquitectura los ignora por completo — no hay CRUD en el que meterlos.
02

Recorrido por la terminal — generar, verificar, publicar, integrar

Cada captura de abajo es salida real de generar este mismo servicio, justo antes de escribir esta página — en el mismo orden en que lo ejecutarías.

1 — generarlo

generate_crud.py GodbyeMicroservices "id:int" --architecture minimal

Un solo comando. Los campos (id:int) solo están para cumplir la sintaxis del CLI — esta arquitectura nunca los lee.

2 — lo que salió

8 ficheros, todos bajo app/

La misma forma que hello-world-argocd: pom.xml, una clase Application, un Controller, un test, un Dockerfile. Nada más.

3 — compila y pasa de verdad

mvn test

El código generado no vale nada si no compila. El contexto de Spring arranca, el único test del controller pasa, código de salida 0.

4 — construir la imagen

docker build -t godbyemicroservices:local app

El mismo paso que la Parte 1, sección 05 — solo cambia el nombre de la imagen.

5 — meterla en el clúster

kind load docker-image godbyemicroservices:local --name hello-world

El mismo clúster que hello-world — un único clúster de kind corriendo felizmente dos servicios independientes.

6 — publicar el repo de código

crud_generator.github_repo.push_to_github(...)

La misma función que llama --github en el CLI, ejecutada directamente porque el proyecto ya existía: git init + commit + gh repo create --push, más el arreglo de permisos de Actions del repo nuevo.

7 — registrarlo en Argo

kubectl apply -f applications/godbyemicroservices.yaml

Exactamente el patrón de la Parte 2, sección 04: una copia de manifests/hello-world/ y applications/hello-world.yaml, tres campos cambiados. Synced y Healthy en segundos.

8 — prueba final

kubectl get pods + curl

El pod está Running, y el endpoint generado responde con el propio nombre de la entidad incrustado — prueba de que esto no es una copia de hello-world, es un servicio generado distinto.

03

Prueba de que funciona — en el navegador

La misma comprobación del paso 8, esta vez desde un navegador real contra el servicio con port-forward.

GET http://localhost:8082/godbyemicroservices

{"message":"Hello from GodbyeMicroservices"}

Un segundo microservicio, independiente — distinto código, distinto repo, distinto nombre — corriendo en el mismo clúster, desplegado por el mismo ArgoCD, siguiendo el mismo bucle GitOps de la Parte 1, sección 03.

04

La integración, como secuencia

1 Tú Copia manifests/hello-world/ a manifests/godbyemicroservices/ en gitops-config, renombra cada campo.
2 Tú Copia applications/hello-world.yaml igual — metadata.name, source.path, destination.namespace.
3 Tú git push, y luego kubectl apply -f applications/godbyemicroservices.yaml.
4 ArgoCD Lo detecta como un segundo Application completamente independiente — mismo bucle de reconciliación, mismo aislamiento por namespace.

Nada aquí es específico de un servicio generado — son exactamente los mismos cuatro pasos que describe la Parte 2 para cualquier servicio nuevo, escrito a mano o generado.

05

Comandos de referencia

Generar

python generate_crud.py GodbyeMicroservices "id:int" --architecture minimal

Construir + cargar

mvn -f app/pom.xml clean package
docker build -t godbyemicroservices:local app
kind load docker-image godbyemicroservices:local --name hello-world

Publicar

python -c "from crud_generator.github_repo import push_to_github; print(push_to_github('crud-godbyemicroservices-minimal'))"

Integrar + verificar

kubectl apply -f applications/godbyemicroservices.yaml
kubectl -n godbyemicroservices get pods
kubectl -n godbyemicroservices port-forward svc/godbyemicroservices 8082:8080
curl http://localhost:8082/godbyemicroservices
